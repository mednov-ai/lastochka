# Смена концепции: локальная реализация

Этот отчёт фиксирует локальный этап до поставки. Последующая отдельно разрешённая
[серверная поставка 0.8.0](deployment/2026-10-23-admin-concept.md) выполнена и проверена.
Локальные проверки выполнялись на собственном контейнере
`lastochka-concept-postgres`, отдельной БД `lastochka_concept` и Testcontainers.
Новая схема — V11; основной результат — публичная заявка и ADMIN без почты.

## Решение об удалении

При запуске apply пользователь отдельно поручил удалить обычных пользователей,
а затем выбрал удаление связанных карточек детей и старых записей. Это заменяет
исходный план сохранения семей. V10 сохраняет ADMIN/их хеши и ключи, расписание и
контент; удаляет PARENT/детей/Booking и зависимости. V11 обновляет пять точных
устаревших стандартных инструкций шагов/FAQ и согласованную ревизию документа,
сохраняя остальные тексты/блоки/изображения. Старые сессии, challenge,
VERIFY/RESET, attendance, move preview и command replay отзываются для всех.
Ни один родитель не повышается до администратора. Новые заявки не создаются из Booking.

| Поверхность | Владелец | Новое поведение |

| password-stage/me/csrf/logout | identity | Логин/пароль; только явно допущенный ADMIN, отдельная cookie/CSRF/auth_version/generation |

| children/families | customers/bookings | Прежние контроллеры исключены из действующего профиля; семейные данные удаляет V10 |
| bookings/participants/move-preview/move-previews | bookings | Старые HTTP-команды закрыты; старые workers не запускаются |
| booking-confirmation | bookings | Не выдаётся, прежние разрешения удалены; публичный экран нейтрален |

## Подтверждённые результаты

- V9 fixture содержит ADMIN/PARENT/ребёнка/Booking/занятие/ключи и прежние разрешения.
  Приёмочный тест мигрирует её через настоящий Flyway в V11 и сверяет границу удаления.
- Локальная копия V9 создана старым JAR, сохранена в `artifacts/admin-concept/pre-v10.dump`
  и восстановлена в отдельную БД `lastochka_restore`. Затем целевая тестовая БД
  мигрирована новым JAR; приватная операторская configure-процедура назначила логин,
  не меняя старого административного хеша.
- Автоматические backend-проверки покрывают вход/сброс/отзыв допуска, CSRF/права,
  закрытие старого API, атомарный rollback заявки при отказе очереди, конкурентный
  повтор, изменённый контекст занятия, конфликт публикации ресурсов, DRAFT/копейки/
  версии, 429/размер/origin и отказ неверного marker.
- Локальный HTTP-имитатор Telegram проверяет message_id, буквальный текст без
  parse_mode/предпросмотра ссылок, 429/retry_after, окончательный отказ, ручной
  повтор и завершение попыток после истечения lease. Настоящей доставки это не доказывает.

## Кандидат и пределы готовности

Локально подготовлена пара **backend/frontend 0.8.0**, PostgreSQL **V11**:
`artifacts/release-0.8.0/application-images.tar.gz`, manifest и DELIVERY.md.
Runtime Java 25/Node 24.22.1 повторно использован из принятых образов с проверкой
неизменных frontend dependencies; npm lockfile не менялся. Сборка не зависит от info/.
Это кандидат поставки, а не опубликованный релиз.

HTTPS обнаружил и подтвердил исправление восстановления внешних Host/protocol
за proxy: штатный POST теперь проходит проверку origin, форма работает без JS.
Серверные секреты бота не передаются frontend. Telegram проверен только локальным
HTTP-имитатором; настоящего бота/chat_id и внешней доставки нет. Без настройки
заявка сохраняется, очередь ждёт настройки. Выбор платёжного провайдера и выпуск
настоящих ссылок намеренно отложены; доступен только черновик.

На описанном здесь локальном этапе серверная V9 и исходные семьи не менялись.
После отдельного поручения выполнена [поставка 0.8.0/V11](deployment/2026-10-23-admin-concept.md):
шесть PARENT и один ребёнок удалены после проверенного backup/restore, три ADMIN
сохранены. Фактические серверные результаты приведены в отчёте поставки.
Не восстанавливать старый dump поверх новых заявок и не публиковать старую пару
0.7.0/0.6.1 как штатный откат.

Полный порядок эксплуатации — [admin-concept-operations.md](admin-concept-operations.md).
После отдельного поручения изменение архивировано и main specs синхронизированы
с поставленной новой концепцией. Apply завершён: **40/40 задач**. Строгая проверка изменения и всех основных specs:
**14 passed, 0 failed**; результат — `artifacts/admin-concept/openspec-final.log`.
