# Календарь и подтверждение «Приду»: эксплуатация

Изменение реализовано локально в `improve-calendar-and-client-confirmation`.
Этот документ описывает конфигурацию и порядок поставки. По отдельному поручению
23.10.2026 выполнена поставка 0.5.0:
[результаты и откат](deployment/2026-10-23-calendar-confirmation.md).

## Конфигурация

Обычная конфигурация по умолчанию: `ATTENDANCE_CONFIRMATION_ENABLED=false`.
Календарь, кабинеты и прежние команды продолжают работать. Новые ссылки не
выдаются, публичные операции подтверждения отвечают `CONFIRMATION_UNAVAILABLE`.

Для включения необходимы:

| Настройка | Назначение |
| --- | --- |
| `ATTENDANCE_CONFIRMATION_ENABLED=true` | Включение выдачи и обработки ссылок |
| `ATTENDANCE_CONFIRMATION_GENERATION` | UUID поколения разрешений, хранится вне БД |
| `ATTENDANCE_MAIL_KEYS` | Keyring `key-id:base64[,previous-id:base64]`, каждый ключ — 32 случайных байта |
| `ATTENDANCE_MAIL_ACTIVE_KEY` | ID ключа для новых payload; предыдущие остаются для доставки очереди |
| `ATTENDANCE_MAILHOG_API_URL` | Закрытый API MailHog для очистки; допустим localhost/loopback либо имя `mailhog` внутренней сети |
| `PUBLIC_APP_URL`, `WEBAUTHN_ORIGIN`, `WEBAUTHN_RP_ID` | Согласованные публичный URL, origin и домен; для удалённого размещения HTTPS |
| `COOKIE_SECURE=true` | Обязательно для удалённого HTTPS; HTTP разрешён только явно локальному loopback |

Ключи генерируются и хранятся внешним хранилищем секретов или закрытым файлом
конфигурации с правами 0600. Не помещать их в исходники, образ, командную строку,
отчёт или логи. Generation — отдельный несекретный UUID, не шифровальный ключ.
Шаблон `.env.calendar.example` не содержит рабочих ключей. Ошибочная конфигурация
ключа, generation или удалённых Secure cookies блокирует запуск с безопасной причиной.

HTTP-ссылка допустима только в изолированном локальном стенде. На сервере ссылки
строятся из доверенного `PUBLIC_APP_URL`, не из Host запроса, с `/lastochka/`.
MailHog остаётся тестовым захватом, RuSender и реальная доставка не подключены.

Лимиты задаются Spring-свойствами `lastochka.attendance-confirmation.*-limit`:
bootstrap — 30/IP/мин, exchange — 10/IP/мин, confirm — 10/контекст/мин;
resend-minute — 1/запись/мин, resend-hour — 5/запись/час, resend-admin — 20/ADMIN/час.
Все значения положительные. Счётчики в PostgreSQL переживают рестарт и общие
для экземпляров. По умолчанию используется непосредственный peer IP; за proxy
нельзя доверять произвольному X-Forwarded-For. До настройки доверенной цепочки
несколько клиентов могут делить один консервативный IP-лимит.

## Поведение и диагностика

- Одобрение ADMIN и ответ клиента независимы. Нет ответа — запись/место сохраняются.
- Ссылка действует до 72 часов и максимум до начала. Контекст — до 15 минут.
- Перенос ребёнка или изменение времени/названия/формата занятия отзывает ссылки
  и сбрасывает ответ. Закрытие приёма или изменение одной вместимости не сбрасывает его.
- После переноса письмо с новой ссылкой получает каждая CONFIRMED; PENDING получает
  только своё письмо о переносе. Два ребёнка одной семьи означают два события.
- Пересланная ссылка передаёт ограниченное право ответа. Аудит указывает способ
  «по ссылке, отправленной родителю» и не утверждает проверенную личность.
- Повторную отправку выполняет ADMIN из панели записи. Она отзывает прежние
  ссылки/контексты, сохраняет полученный ответ на те же условия и имеет лимиты.
- В новом браузере использованная ссылка не открывает сведения повторно. Уже
  допущенный контекст получает результат до своего TTL, пока условия актуальны.

Безопасная диагностика использует eventId, статусы, attempts и last_error:
`SMTP_UNAVAILABLE` — доставка не завершилась; `SENSITIVE_PAYLOAD_UNAVAILABLE` —
нет ключа либо нарушена целостность payload. Тело, secret, cookie и CSRF не логируются.
`SKIPPED` означает заведомо устаревшее письмо и не блокирует очередь последующих событий.
Не выводить `encrypted_payload`, расшифрованное тело и заголовки с cookie при отладке.

SMTP retry сохраняет eventId/Message-ID/секрет и не продлевает срок. При потерянном
SMTP-ответе возможны две копии письма; второго бизнес-действия не происходит.
Письмо, уже переданное SMTP во время переноса, нельзя отозвать, но ссылка отклоняется.

## Очистка и ротация

Worker раз в минуту очищает encrypted payload: до 24 часов после CAPTURED;
недоставленный — до 24 часов после expiry/revocation. Остаются безопасные метаданные.
Истёкшие browser-контексты удаляются, устаревшие previews удаляются после окна
идемпотентности. Уже полученный ответ от очистки не меняется.

MailHog retention проходит постранично и удаляет только письма с заголовком
`X-Lastochka-Attendance: 1` возрастом около семи суток (с минутным запасом).
Посторонние письма не удаляются. UI/API доступны оператору через loopback/SSH,
внешняя пересылка остаётся заблокированной внутренней сетью Compose.
При выключенных workers автоматической очистки нет; перед включением приёмки
проверить их работу и безопасное предупреждение о недоступности retention API.

Ротация ключа: добавить новый ID, сделать его активным, сохранить старые ключи
до завершения/очистки использующих их событий. Не переиспользовать ID для другого
ключа. Если ключ потерян, выключить функцию, отозвать поколение, подготовить новый
keyring и явно перевыпустить нужные приглашения после включения; не восстанавливать
сырой secret из hash и не продлевать старые ссылки.

## Восстановление и будущая поставка

1. Перед восстановлением остановить writers/workers и выключить функцию.
2. Восстановить данные в отдельную БД и сверить отпечатки/миграции/очередь.
3. До включения обязательно задать новый UUID generation вне восстановленного backup.
   Разрешения/контексты старого поколения не принимаются; при запуске включённого
   backend старые grants получают persisted revoked_at для своевременной очистки.
4. Настроить keyring и закрытый MailHog. Если ключи недоступны, не пытаться доставить
   старые payload; очистить их по политике и выдать новые приглашения явным ADMIN действием.
5. Проверить старую ссылку и старую открытую страницу: ни просмотра, ни подтверждения.
   Существующие бизнес-ответы остаются историей; восстановленный backup сам по себе
   не является основанием массово отправлять письма или менять занятость.

Будущий rollout по отдельному поручению: backup → новый backend с выключенной
выдачей → совместимый frontend с публичным маршрутом → секреты/generation → включение
→ синтетическая HTTPS-приёмка. Seed и массовая отправка существующим семьям не нужны.
Старый frontend поддерживается новым backend; прежние PUT/action тоже отзывают ссылки.

Перед откатом frontend на сборку без маршрута подтверждения выключить функцию
и отозвать поколение. Для клиентов это временная недоступность с контактом
администратора. Перед возвратом на старый backend также отозвать поколение;
перед последующим включением — новый UUID. Аддитивную миграцию V8 не удалять,
ответы/аудит не стирать, destructive down-migration не выполнять.

## Изолированный локальный стенд

Сервисы: `compose.calendar-test.yaml`, БД `calendar_test` на 55433, SMTP 11027,
MailHog API/UI 18027, backend 8181, frontend через gateway 5174. Все host-порты —
loopback, внутренний MailHog не имеет внешнего relay. Старые local/preview не используются.

После Java 25 bootJar и Node 24 production build:

```text
docker compose -f compose.calendar-test.yaml up -d --wait
python3 scripts/local-calendar-preview.py start
python3 scripts/calendar-browser-checks.py calendar-attendance.spec.ts
```

Helper сам создаёт закрытый `runtime-data/calendar-test/backend-env.json` с тестовым
keyring/generation. `restart` сохраняет их, cookie-контексты и БД; `stop` завершает
только свои процессы. Перед новым build остановить preview, после build запустить
заново, чтобы SSR не ссылался на уже заменённые chunks.

Дополнительные проверки:

- `calendar-compatibility-preview.py` — предыдущая сохранённая frontend-сборка
  на 5175/5176 с включённым/выключенным backend; затем `stop`.
- `calendar-https-preview.py` — self-signed loopback TLS на 18444; тест использует
  принудительное локальное разрешение play-and-say.ru; затем `stop`.
- `verify-calendar-migration.py` — отдельная БД, сохранённый V7 backend и переход к V8;
  не подходит без локального baseline JAR, который не входит в Git.
- `verify-calendar-restore.py` — собственный synthetic grant, рестарт, dump/restore
  в отдельную БД, новый generation и проверка отказа старой ссылки.
- `verify-calendar-config.py` — безопасный отказ запуска при неверных настройках.

Browser fixture calendar-attendance намеренно очищает только созданную для него
`calendar_test`, предварительно проверив её имя и loopback URL. На другую БД/сервер
его направлять нельзя. Без явного `TEST_APP_URL` этого стенда набор пропускается;
обычный CI не подключается к порту 5174 автоматически. Дампы, ключи, screenshots, cookies и test-results остаются
в исключённых из Git локальных каталогах; действующие токены в отчёт не переносить.
