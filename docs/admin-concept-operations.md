# Административная модель: подготовка и поставка

Это инструкция для новой концепции ADMIN_ENQUIRIES_V1 (схема V11). Первая отдельно порученная
поставка 0.8.0/V11 выполнена 23.10.2026: [отчёт](deployment/2026-10-23-admin-concept.md).
Далее описан переход с прежней V9, а также последующая эксплуатация и восстановление.

## Граница удаления

По поручению пользователя удаляются все аккаунты PARENT, связанные карточки детей
и их Booking любого статуса. V10 сначала удаляет зависимые grants/контексты,
команды, credentials, относящиеся к семьям письма очереди и аудит семейных агрегатов;
оставшиеся ссылки на удаляемого автора обнуляются. Таблицы не удаляются.
Администраторы, их исходные ID/хеши/ключи, занятия и опубликованный контент остаются. V11 точечно заменяет пять прежних стандартных инструкций
о кабинете/подтверждении/свободном времени; произвольный изменённый контент и изображения сохраняются.
Дополнительная DOCTOR снимается. Прежние сессии и разрешения отзываются для всех.

Нельзя запускать новый JAR на единственной рабочей V9 ради «проверки health»:
Flyway применяет V10/V11 при старте. Сначала проверяются backup/restore, состав удаления
и список оставляемых ADMIN на отдельной копии без исходящей доставки.

## Локальная проверка

- Сборка: Java 25, Node 24; backend `check`/`architectureCheck`/`:app:bootJar`,
  frontend `check:ui-language`, `typecheck`, `build`, генерация из реального OpenAPI.
- Backend integration suite самостоятельно создаёт отдельный Testcontainers PostgreSQL,
  начинает с V9 и проверяет миграцию на синтетических данных. Прежние сценарии
  родительской модели сохранены как история в `test-fixtures/legacy-tests` и
  `test-fixtures/legacy-browser`; они заменены проверками закрытия старого доступа.
- Browser matrix: `playwright.concept.config.ts`; требуется явно указанный
  `TEST_DATABASE_CONTAINER=lastochka-concept-postgres` и локальный синтетический
  fixture-admin. Этот набор не запускается против серверной или произвольной БД.
- Бот в автоматических тестах заменён локальным HTTP-имитатором. Вызовы настоящего
  Telegram, платёжного провайдера и RuSender не являются частью локальных тестов.

## Предварительные условия будущей поставки

1. Выполнить свежую инвентаризацию текущей среды и записать количества PARENT,
   связанных детей/Booking/зависимостей, сохраняемых ADMIN/credentials/занятий/контента.
2. Сделать приватный PostgreSQL backup и восстановить его в отдельной БД; сверить
   административные ID/хеши/ключи и расписание/контент, проверить V9→V11 на копии.
   Почтовый volume сохраняется закрытым; backup может содержать удалённые впоследствии
   тестовые данные и не публикуется.
3. Выбрать существующие ADMIN по стабильным ID и назначить уникальные логины
   `[a-z0-9._-]{3,64}`. PARENT не повышаются до ADMIN. По умолчанию после V10 ни один
   прежний аккаунт не допущен, пока оператор не выполнит адресную настройку.
4. Задать во внешней приватной env новый случайный `ADMIN_ACCESS_GENERATION` длиной
   не меньше 32 символов, Public URL, RP/origin и Secure cookie. Generation хранится
   вне backup БД и меняется после disaster restore. Не использовать example-значение.
5. Проверить оба образа перед публикацией и каждым откатом:
   `python3 scripts/check-concept-release.py BACKEND_IMAGE FRONTEND_IMAGE`.
   Образы без метки `org.lastochka.concept=ADMIN_ENQUIRIES_V1` отвергаются.

## Порядок переключения

1. Закрыть только входящий маршрут Lastochka на обслуживание. Остановить старые
   proxy/frontend/backend и дождаться завершения старых команд/SMTP workers.
   PostgreSQL, maildir, общие Nginx/TLS/ACME и соседние приложения не удалять.
2. Подготовить согласованную пару новых образов. Новый backend в закрытом окружении
   применяет V10 и V11; каждая миграция транзакционна. Старый frontend после этой границы больше не
   совместим: он не должен оставаться опубликованным ради старых полномочий.
3. Закрытой одноразовой процедурой назначить выбранному существующему ADMIN логин:
   передать `LASTOCHKA_ADMIN_ID`, `LASTOCHKA_ADMIN_LOGIN` через приватную env,
   запустить образ backend с `--lastochka.admin.configure=true --lastochka.workers.enabled=false`.
   Повтор с тем же логином не переписывает пароль и ключи; другой логин требует
   отдельного адресного решения, коллизия прерывает операцию.
4. Для нового заранее заданного ADMIN использовать закрытый bootstrap
   `--lastochka.admin.create=true --lastochka.workers.enabled=false` с приватными
   `LASTOCHKA_ADMIN_LOGIN`, `LASTOCHKA_ADMIN_NAME`, `LASTOCHKA_ADMIN_PASSWORD`.
   Пароль не передавать в аргументах команд и не записывать в отчёт.
5. Для сброса существующего пароля — та же адресная configure-процедура с ID и
   `LASTOCHKA_ADMIN_PASSWORD`. Она сохраняет ключи, меняет хеш/auth_version, отзывает
   challenge; прежние сессии не проходят проверку. Публичного сброса нет.
6. Публичный mail_hog_test закрывается новым proxy с пересозданием собственного
   контейнера для завершения существующих WSS. Оба варианта адреса/UI/API/assets
   дают 404. MailHog/mailhog-access теперь только опциональный профиль `mail-archive`;
   приложение не зависит от SMTP и не отправляет email. Не подключать старый
   публичный proxy-конфиг поверх нового и не удалять maildir/volume.
7. Проверить новый парольный вход/добровольный ключ, сохранность ADMIN/занятий/контента,
   фактическое удаление PARENT/детей/Booking/зависимостей, календарь, заявку и DRAFT.
   Проверить закрытие VERIFY/RESET/«Приду»/старого replay/семейного API и старой вкладки.
8. Только после проверки открыть новый frontend/proxy и входящий маршрут. Сверить
   соседние `/`, `/repair_demo/`, TLS/ACME. В отчёте отделить серверную приёмку
   от ранее выполненной локальной, удалить только синтетические fixtures.

## Telegram и оплата

`TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` задаются только в приватной серверной env.
Получатель — личный чат или группа, где бот имеет право отправлять сообщения.
Боту не нужен публичный webhook: реализован только исходящий sendMessage.
Собственный proxy перезаписывает X-Forwarded-For по доверенному адресу, форма SSR
передаёт его backend для лимита посетителя; backend/Node не должны иметь публичных портов.
Внешний HTTPS-прокси передаёт исходные Host и X-Forwarded-Proto, собственный proxy
перезаписывает forwarded host и убирает посторонние Forwarded/port. Node доверяет
только loopback/частной сети. Это необходимо для проверки origin серверной формы.
Без настройки заявки сохраняются, очередь ждёт, кабинет показывает ожидание
настройки. Сбой не отменяет заявку. После настройки отдельной синтетической
заявкой подтвердить реальное сообщение/номер в нужном чате; имитатор этого не доказывает.

Временные ошибки/429 повторяются с задержкой, окончательный отказ виден ADMIN и
может быть повторён адресно. Неоднозначный сетевой результат может дать вторую
копию с тем же номером; сама заявка не создаётся повторно. Диагностика не пишет
ключ бота, URL с ключом и тело сообщения.

Оплата ограничена DRAFT/RUB/целыми копейками. Настоящей ссылки/статуса оплаты нет;
API выпуска отвечает PAYMENT_PROVIDER_NOT_CONFIGURED. Провайдер, webhook,
возвраты, доставка ссылки клиенту — следующее отдельное изменение.

## Откат и восстановление

Обычный откат — только на образ, поддерживающий новую концепцию и схему. Перед
сменой остановить новые команды/worker, сохранить новые заявки/очередь/DRAFT,
проверить обе метки образов. Не выполнять down-migration, down -v или восстановление
старого dump поверх новых данных. 0.7.0/0.6.1 не являются допустимой парой отката
после V10: у них нет нового API/состояний/эпохи доступа. Их возврат требует отдельного
плана и закрытого публичного входа, не считается штатным восстановлением.

Disaster restore выполняется в изолированную БД с новой внешней generation,
проверкой marker и версии схемы до открытия доступа. Старый backup не возвращает
силу прежним сессиям и ссылкам. Отдельно сверяются новые заявки и очередь, а при
восстановлении V9 снова выполняются согласованная миграция и допуск ADMIN.
