# Переход на корневые адреса — подготовка

## Production — выпуск 9 ноября 2026

По отдельной отмашке production переведён на корневой путь. До выпуска повторно
проверены актуальные образы test, SHA-256 подготовленных файлов, `nginx -t`,
состояние сервисов, ночные backup и TLS. После PIN сайт открывается на `/`,
новые и прежние прямые URL без gate-сессии остаются закрыты; старый адрес
заявки после входа перенаправляется на корневой. Внешние Chromium с клавиатурой
и мобильная эмуляция WebKit подтвердили PIN и изоляцию cookie от test. Test
остался публичным в корне; TLS 1.2 принимается, TLS 1.3 отклоняется на обоих
доменах. Физические устройства, скринридер, вход администратора production и
реальные операции с Альфа-Банком отдельно не проверялись. Изменение пути cookie
может потребовать повторного входа в кабинет.

Перед выпуском и после него роль `lastochka-agent` на чтение получила одинаковые
отпечатки 29 доступных не-session таблиц в каждой зоне. Недоступные этой роли
таблицы и таблицы сессий не сравнивались. SHA-256 пяти production backup и
идентификаторы контейнеров и томов обеих PostgreSQL совпали; БД не
перезапускались, миграции и восстановление не выполнялись. Работают Nginx,
Docker, Fail2ban и таймер backup. На момент проверки доступно около 526 MiB RAM,
swap 250 MiB; это не нагрузочное испытание.

Production использует проверенные образы, перечисленные ниже. До переключения
сохранён vhost `/etc/lastochka/production/nginx-backups/pre-root-vhost-97cx3ii_`;
операторская конфигурация production содержит `"app_base":"/"`. Для обеих зон
используется `/opt/lastochka/releases/root-20261107/scripts/apply-maintenance-mode.py`.
При откате возвращать только совместимые прежние образы и сохранённый vhost,
оставляя TLS 1.2, закрытый production, актуальные БД и backup; фактический
откат production не выполнялся. Дальнейшие выпуски — после новой отмашки.

## Статус после test

Test переведён на `https://test.lastochka-gym.ru/` без заглушки. Проверены вход
`kines`, root-cookie, RP ID WebAuthn, серверная заявка, отказ анонимному
административному API, старые URL с 308 и отдельное включение режима работ с
PIN и его последующее выключение. TLS 1.2 принимается, TLS 1.3 отклоняется.
В изолированном окружении Chromium и мобильный WebKit проверили новый сайт,
заявку без JavaScript, CSRF, сохранение ключа незавершённой команды, старые
файлы и настоящую открытую вкладку прежней сборки. Вкладка получает указание
обновить документ при навигации; старый изменяющий запрос сохраняет метод и
тело. На test также сверен SHA-256 JavaScript-файла из прежнего образа после
перенаправления и проверена работа серверной формы без JavaScript в эмуляции
мобильного WebKit. Физические телефоны и реальные банковские операции не проверялись.

До и после test роль только для чтения сравнила отпечатки 29 доступных таблиц
в каждой зоне, кроме таблиц сессий: production совпал полностью; на test
изменились `auth_limits` и `webauthn_challenges` после проверки входа и запроса
параметров ключа, остальные 27 таблиц совпали. Недоступные роли таблицы не
сравнивались. Контрольные суммы трёх production backup совпали, PostgreSQL обеих
зон не перезапускались. Миграции и восстановление рабочих БД не выполнялись.

Кандидат построен вне VPS и проверен из тех же образов: backend
`sha256:60439484b60601e8caca0ed0863b28036d2347259b3c4e21066a91f588c07647`,
frontend `sha256:25cf94a87958ce0a57d93f60ba9030a2c1a36f5845345fbd4380bfff5beca109`,
gate `sha256:db72e4724fbeb69f67d3bf87fc3049945cbdbbb39a098955cb5c2c8c96a686e0`.
Архивы сборки лежат локально в игнорируемом `runtime-data/root-release/`.
Предыдущий test vhost сохранён в
`/etc/lastochka/test/nginx-backups/pre-root-vhost-euyra4uu`; предыдущие образы,
секреты и база сохранены. После перехода приложение может попросить
администратора войти повторно: прежняя cookie имела Path `/lastochka`.

## Подготовка до выпуска production

На этапе подготовки production оставался с прежним подпутём и PIN-gate.
Кандидат и его не содержащая секретов конфигурация подготовлены на VPS;
проверены Compose, полный теневой `nginx -t` и ограничение TLS 1.2. Точный
операторский сценарий `scripts/deploy-production-root.py` требует явный флаг и
PIN через stdin. Он проверяет target и volume, не запускает Flyway, меняет
только backend/frontend/proxy/gate production, сохраняет vhost, проверяет PIN,
защищённые маршруты и test и при ошибке пытается вернуть предыдущие сервисы и
закрытый vhost. Приложение может быть кратковременно недоступно; gate не должен
открывать его при отказе. Выполненная после отмашки команда:

```sh
ssh lastochka-production 'python3 /opt/lastochka/releases/root-20261107/scripts/deploy-production-root.py --approve-production' < .env/maintenance/maintenance-production.pin
```

Внешняя приёмка описана выше. При отказе сохранять production БД,
тома и backup; откат включает прежние совместимые образы и защищённый vhost,
**с TLS 1.2**. Реальный откат production пока не выполнялся.

## Предварительный анализ

7 ноября 2026 года новый VPS обслуживает два отдельных домена: production под
защищённой заглушкой и открытый test. Приложение в обеих зонах использует
`/lastochka/`; старый общий стенд `play-and-say.ru` использует тот же подпуть,
но в этот выпуск не входит. Изменение его требований и конфигурации должно
учитывать область действия домена, а не удалять поддержку подпути повсеместно.

Префикс участвует в сборке React Router и Vite, настройках frontend, контексте
Spring, cookie сессии, маршрутах внутреннего proxy, готовности backend, ручных
URL редактора и проверке обратного адреса тестового эквайринга. В Nginx корень
сейчас всегда направляется на gate или делает redirect на подпуть. После входа
gate тоже направляет на подпуть. Origin и RP ID WebAuthn зависят от доменов, а
не от этого пути; их значения и учётные записи менять не требуется.

План кандидата: собрать frontend для `/`, оставить возможность сборки старого
подпути для прежнего стенда, поддержать backend-контекст `/` без миграции БД,
передавать API и frontend через внутренний proxy, проверять доступ на внешнем
Nginx до любого перенаправления прежних адресов. Прежние `/lastochka/...` в
совместимом окружении переводятся на соответствующий корневой путь с сохранением
метода и тела; старые статические ресурсы остаются доступны из архива. Маршрут
возврата Альфа-Банка должен поддерживать оба проверенных пути на том же origin.

Существующая cookie приложения имеет Path `/lastochka`: браузер не отправит её
на `/`. Базу сессий и пользователей изменение не удаляет, однако бесшовное
сохранение входа нельзя считать доказанным: после переключения может
потребоваться повторный вход. Это нужно проверить и сообщить до production.
Сессии gate и их лимиты независимы; старые вкладки и неизвестный исход команд
нужно проверять отдельно, сохраняя ключи идемпотентности.

Проверять на вновь созданной изолированной синтетической БД и test; не запускать
миграции на существующих БД, не удалять рабочие данные, тома или резервные
копии. До production подготовить возвращение совместимых образов и vhost и
получить новую отмашку. При выпуске и откате сохранять только TLS 1.2, закрытый
production и публичный test. Последующее согласование основных specs должно
учитывать сохранение старого общего стенда и корневые адреса нового VPS.
