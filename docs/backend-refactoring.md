# Рефакторинг backend: исходное состояние и локальная проверка

Изменение: `refactor-backend-repository-and-common`. Этот отчёт описывает локальный этап. Последующая отдельно разрешённая
[серверная поставка backend 0.7.0](deployment/2026-10-23-backend-refactoring.md)
выполнена 23.10.2026.

## Исходное состояние

Снимок 23.10.2026: 82 production Kotlin файла, 4973 строки, 8 внутренних модулей;
53 вызова `.sql(...)` в 15 классах вне repo. Полная карта владельцев и причины
изменений находятся в design изменения. В исходном рабочем дереве были 306
изменённых/добавленных записей Git; они сохранены. Частные baseline-файлы,
исходный JAR, OpenAPI и SHA256 исходников — `runtime-data/backend-refactoring/`.
Секреты и локальные данные не добавляются в Git.

Исходные backend-тесты и bootJar на Java 25 прошли. Отдельная измерительная
проверка выполняет реальные JDBC-запросы в собственном Testcontainers PostgreSQL;
счётчик охватывает JPA и JDBC, фоновые задачи выключены. Нет запросов на сервер.
Для 100 элементов: дети — 102 запроса, записи — 302, календарь — 201.
Измерения 1/20/100 сохранены в baseline-query-counts.csv; fingerprint измеряется
без создания целевого занятия внутри измеряемой операции.

Языковой контроль уже реализован соседним change и подключён к frontend build;
он анализирует Kotlin и properties рекурсивно, поэтому перенос общего каталога
не должен исключить его из проверки. Соседние исходники не откатываются.

## План сохранения поведения

Миграции V1–V9 не меняются. Контракты HTTP/OpenAPI, сериализованные состояния,
блокировки, независимые транзакции ограничений/challenge, очередь, шифрование,
TTL/generation и безопасность сообщений проверяются до завершения задач.

## Результаты реализации

Локальная реализация и проверки завершены; результаты и ограничения приведены ниже.

## Реализованная структура

- Все 54 текущих вызова `.sql(...)` находятся в `repo`; вне `repo` — **0** вместо исходных 53. Дополнительная выборка нужна для пакетного получения детей семей. Чтение, binding и mapping не передаются обратно сервисам. Миграции V1–V9 сохранены по SHA256.
- Новый library-модуль `common` доступен всем модулям и не зависит от предметных модулей/app. В нём находятся Metadata, ApiError/MessageResponse, единый advice, фабрика/каталоги сообщений и технические команды/audit/idempotency/studio lock. Предметные DTO и entities остались у владельцев.
- 18 файлов repo (включая четыре прежних JPA repositories) описывают операции владельцев. Поиск родителей находится в identity; attendance получает immutable AccountAccess через сервис identity с блокировкой в вызывающей транзакции. WebAuthn repositories скрыты адаптером identity/repo.
- Очистка attendance contexts и move previews перенесена в worker bookings. Два явно разрешённых чтения через границы таблиц: поиск целей переноса bookings+studio_sessions и проверка revoked grants при очистке encrypted outbox. Чужие таблицы эти запросы не изменяют.
- Существующий advice перенесён из app и покрывает все контроллеры, включая отдельный импортированный тестовый контроллер вне корневого пакета. Security использует ту же фабрику. Common больше не импортирует DTO/политику пароля/config identity; коды полевых ограничений берутся из проверенного constraint template без чтения пароля.
- Gradle starters/JPA plugin подключаются по фактическому использованию. Common/payments/notifications/content больше не получают JPA plugin автоматически; payments остаётся без операций. App — единственный bootJar.

## Metadata и понятный код

Группы Metadata: ошибки/поля, результаты действий и письма, роли/защита, запись,
расписание, уведомления, команды, HTTP/маршруты, configuration expressions,
ограничения, время, криптографические параметры и правила контента. У сроков и
размеров есть единицы измерения. Разные TTL с одинаковым значением не объединены
одной константой. Working keys/generation/passwords/URL остаются внешней конфигурацией.

`messages.properties` — единственный каталог публичных ошибок;
`user-messages.properties` — результаты действий и шаблоны писем. Для ошибок
сохранены только разрешённые числовые параметры; текстовые параметры писем
использует отдельный UserMessages. Точный формат строк, переносы, начальный пробел
перед «(МСК)» и имя с апострофом проверены тестом. Языковой сканер продолжает
проверять оба common-каталога и корректно различает property escapes/URL-шаблоны
и текст; английская инструкция в новом common resource реально отклоняется.

Удалено/объединено:

| Место | Результат |

## Обязательные правила и команды

Основная проверка: `backend/gradlew -p backend architectureCheck` (Java 25).
Она автоматически находит production Kotlin во внутренних модулях и анализирует
Kotlin PSI в отдельном процессе. Compiler — build/test dependency: в итоговом JAR
его нет. `buildSrc` — инструменты сборки, не production-модуль. Добавление production
Java отклоняется до появления правил его анализа; это не исключение для Java SQL.

Проверяются DB API/SQL-фрагменты/ресурсы вне repo, типы/импорты чужих repo/entities,
common→domain/app и циклы Gradle, root packages, единственность advice, новые
смысловые литералы/числа/шаблоны/аннотации и наличие сообщений каталога. Контекстные
исключения — SQL grammar, bind/column names в repo, индексы 0/1 и разбиение строки
на две части; широкого baseline старых нарушений нет. Configuration может связывать
готовые инфраструктурные beans; это не разрешает выполнять SQL вне repo.

Контроль включён в корневой check, module check, app bootJar, build-release и
package-release. С уже собранным JAR временный SQL в сервисе отклонён каждым из
шести входов **до упаковки/Docker**. После удаления нарушения положительная
локальная упаковка прошла. Тесты самого анализатора:
`backend/gradlew -p backend/buildSrc test`.

Статический анализ не доказывает отсутствие ошибок произвольной рефлексии или
семантическую простоту кода. Для изменения правил обязательны отрицательные
примеры и ревью. Удаление бизнес-проверки нельзя оправдать одной зелёной проверкой
структуры. Для будущего CI используются эти же команды; удалённый CI не запускался,
удалённый репозиторий здесь не настроен.

## Проверки и совместимость

- **57 backend-тестов**, оба режима attendance, PostgreSQL Testcontainers, root check и bootJar — успешно.
- **8 тестов анализатора** с отрицательными/положительными примерами alias, qualified names, строковых шаблонов, SQL wrapper/resources, нового модуля, ownership rules, нового литерала/лимита, advice/root package и catalog — успешно. Циклы реального графа отдельно проверяет Gradle task; тесты source checker не подменяют проверку графа.
- **6 реальных отрицательных запусков** сборки/упаковки — ожидаемо отклонены по SQL_OWNER; положительная упаковка Linux/amd64 прошла.
- **103 различных browser-сценария**: 30 auth/security/booking/calendar, один старый backend→новый→старый и 72 Chromium/WebKit × en-US/ru-RU × 375/1440. Дополнительно повторены реальный restart, сценарий форм и два финальных SMTP/register/reset smoke на итоговом JAR.
- Первое выполнение форм выявило гонку в тестовом выборе из перезагружаемого списка; тест теперь ожидает окончание загрузки и непустое выбранное значение, повтор прошёл. Restart-тест получил явный путь к собственному preview runner: готовность чужого процесса не принимается за состоявшийся restart.
- Совместимость: сохранённые старым backend session, WebAuthn challenge (завершён новым backend), command replay и move preview прочитаны новым; затем прежний backend запущен на той же V9 и прочитал результаты/сессию/ключ. Массовых отзывов, миграций и пересоздания данных не было.
- Нормализованный OpenAPI **полностью равен исходному**; api:generate, frontend typecheck/build/format и 4 теста языкового контроля прошли. Существующие `frontend/app/**`, OpenAPI и миграции сохранены по исходным SHA256.
- Итоговый локальный JAR запущен на Java 25; health/readiness/liveness — UP, реальные SMTP-письма приняты изолированным MailHog при включённых workers.
- Локальные образы: `lastochka-backend:backend-refactoring-local` и `lastochka-frontend:backend-refactoring-local`; пакет — `artifacts/release-backend-refactoring-local/` (игнорируется Git). Это локальные проверочные имена, не поставка и не изменение публичной версии.

Частные логи/снимки/CSV/контрольные суммы находятся в
`runtime-data/backend-refactoring/`. Основной localhost PostgreSQL/MailHog,
соседний preview, Flowable и сервер не изменялись. Для браузеров создан отдельный
Compose project `lastochka-refactoring-test`; данные проверки не смешивались с
пользовательскими данными.

Сохранились диагностические предупреждения toolchain: Kotlin PSI использует
устаревающий Unsafe на JDK 25, Gradle сообщает о deprecated API для будущего Gradle
10, frontend build — об имеющемся одновременно static/dynamic import auth-form.
Они не препятствуют текущим проверкам и не являются основанием обновлять стек в
этом рефакторинге.
