# Проверка тестового шлюза Альфа-Банка — 06.11.2026

Проверка выполнена с тестового сервера на документированном тестовом адресе
`alfa.rbsuat.com`, с TLS и проверкой имени сервера, только с тестовыми
API-реквизитами из письма. Реквизиты передавались в теле запроса через защищённое
соединение, не в URL, аргументах команды или журнале. Тестовая настройка в
«Ласточке» не включалась; её база не использовалась для создания банковских
заказов. В поддержку запрос не отправлялся.

## Фактические ответы банка

- Для случайного номера `getOrderStatusExtended.do` вернул код `5` с намеренно
  неверным паролем и код `6` с предоставленными тестовыми реквизитами. Это
  практическое подтверждение различающегося поведения в конкретной проверке,
  но не доказательство прав на все операции.
- `register.do` с явной валютой `643` вернул код `3` и сообщение «Неизвестная
  валюта»; заказа с этим номером по последующей сверке не найдено. При регистрации
  без необязательного параметра валюты банк создал тестовые заказы, вернул
  `orderId` и `formUrl` без поля `errorCode`; `getOrderStatusExtended.do` вернул
  сумму 100 копеек, валюту `810` и статус `0`. Платёжная страница и страница
  подтверждения показывают **1,00 RUB**. Документация банка также приводит пример
  статуса с валютой `810`; это не основание считать произвольную другую валюту
  рублём. Возвращённый тестовый домен платёжной страницы — `uatpayment2way.com`;
  документация Альфа-Банка ссылается на этот домен для тестовой платёжной
  инфраструктуры, но конкретный набор разрешённых доменов для интеграции ещё
  следует оформить и проверить.
- Проверка формы проводилась в Chromium с опубликованными банком тестовыми картами;
  реальная карта не использовалась. Три попытки не дали подтверждённой оплаты:
  в одной браузер был закрыт до завершения подтверждения, в другой введён
  опубликованный тестовый пароль, в третьей использовалась тестовая карта с
  бесшовной аутентификацией. Во всех трёх последующий запрос статуса вернул `6`
  и `actionCode=-2013`. Банк описывает этот код как ограничение попыток или
  повторное открытие формы. Причина в данном запуске не установлена, в том числе
  не исключается влияние автоматизации; успешный тестовый платёж не заявлен.
- На отдельном новом неоплаченном тестовом заказе `decline.do` с `merchantLogin`,
  образованным удалением суффикса `-api` из API-логина, вернул код `8` и
  сообщение «Пользователь не имеет разрешения на отклонение заказов». Последующая
  сверка вернула статус `0`: заказ остаётся неоплаченным в тестовом шлюзе.
  Это результат для использованного имени мерчанта и выданной учётной записи,
  а не доказательство настроек любого другого мерчанта. Операция отмены оплаты
  или возврата не выполнялась.
- На экране 3-D Secure в поле продавца отображалось `VK.RU/CLUB242641091`.
  В тестовом письме и проверенных ответах адрес `lastochka-gym.ru` не обнаружен;
  будущую привязку домена к магазину по этому установить нельзя. В пробном
  заказе `returnUrl` указывал на страницу возврата действующего тестового стенда.

Идентификаторы заказов, ответы и конфиденциальные ссылки сохранены с правами 0600
в игнорируемом Git каталоге `alfa-payments/test-run/`; до истечения срока
действия они являются ссылками доступа и не должны публиковаться.

## Значение для реализации

Текущий клиент отправляет `currency=643`; на данном тестовом мерчанте это
приводит к отказу. Логика регистрации принимает как успешный только ответ с
`errorCode=0`, хотя фактический успешный ответ поля не содержал. Сверка сейчас
отклоняет валюту `810`. Эти три наблюдения требуют исправления и регрессионных
проверок до включения интеграции. Не заменять серверную сверку возвратом браузера;
не запускать регистрацию повторно после неоднозначного результата.

Сервер остаётся на backend 0.19.2 / frontend 0.19.1 / V21; банковский режим,
активация и callback выключены. `admin1` активен, проверка фактического входа не
проводилась. Рабочая среда и настоящие банковские карты не использовались.

## Локальные проверки

Прошли 18 тестов модуля оплат, 12 интеграционных тестов оплат, ротации ключа и
отсутствующего ключа и 8 сценариев конкурентности/перезапуска, включая проверку
отказа контекста до Flyway при неверном адресе БД. Для последних использован
Testcontainers и дополнительный запрет подключения к портам существующих
локальных БД; запрещение IPv4 и IPv6 проверено отдельно. Прежний опасный тест
остаётся в карантине, а исправленный вариант проверяет эффективный datasource
до создания бинов и передаёт настройки перезапуска аргументами высокого
приоритета. Дополнительно реальный backend 0.19.2 с новой синтетической
PostgreSQL работал в двух контейнерах с общей сетевой средой `network=none`:
проверены CSRF, шифрование кандидата, запрет выпуска при выключенном банке,
пагинация активных 20+1 и пустой архив. Эти проверки не доказывают успешного
платежа на реальном тестовом шлюзе.
