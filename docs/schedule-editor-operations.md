# Редактор расписания: эксплуатация

## Работа администратора

В кабинете раздел «Сайт · Расписание» открывает действующий /admin/schedule.
Новый сеанс сохраняется как невидимый посетителю черновик. Дата берётся из выбранного дня;
длительность по умолчанию50минут изменяется вручную. Индивидуальный формат имеет одно место.
Возрастной диапазон необязателен и служит рекомендацией, не запретом заявки ребёнка другого возраста.

Для опубликованного занятия «Сохранить черновик» сохраняет отдельные неопубликованные параметры;
на сайте остаются прежние условия. Предпросмотр использует общее представление карточки.
«Опубликовать изменения» требует проверки и явного подтверждения. При конфликте сначала
сравните актуальные условия; «Принять актуальную основу и сохранить мой ввод» меняет основу,
но само по себе не публикует и не сохраняет введённые данные. Следующий шаг — сохранить черновик.

Закрытие приёма не публикует черновик, а публикация параметров закрытого занятия не открывает приём.
После смены приёма основание сохранённого черновика может устареть и требует проверки.
Отмена требует причины. История позволяет подготовить новый черновик прежних параметров;
она не отменяет прошлые заявки и не восстанавливает активность отменённого занятия.

## Заявка посетителя

Общая кнопка открывает подбор из будущих опубликованных OPEN-занятий, либо «Помогите подобрать время».
Кнопка конкретной карточки предзаполняет занятие без повторного выбора; «Изменить» сохраняет контакты.
Подбор, смена периода и отправка работают через серверные действия без JavaScript.
Enter выполняет отправку с обычной проверкой полей, а не действие подбора.
При изменении/закрытии/отмене занятия пользователь должен явно пересмотреть пожелание.
Заявка не резервирует места. Никакой автоматической записи, платежа или почтового события не создаётся.

## Хранение и совместимость

V13 аддитивна: nullable age_from/age_to и session_edit_drafts с независимой монотонной версией.
Опубликованная версия остаётся в studio_sessions.version. Существующие снимки заявок не пересчитываются.
Новый контракт явно очищает возраст через replaceAgeRange=true и обе null-границы;
прежний PUT без возрастных полей сохраняет существующий возраст. Старый PUT остаётся прямым обновлением,
поэтому может сделать основу нового черновика устаревшей. История проецируется из audit_events.

## Поставка и откат

Основная поставка: backend/frontend0.10.0; узкая поправка оформления — frontend0.10.1.
Источник Compose остаётся /opt/lastochka/releases/0.9.0/compose.preview.yaml,
рабочая env — /opt/lastochka/shared/.env.preview, project lastochka-preview.
Не выводить env/пароли/cookies в отчёты и аргументы процессов.

Для поправки оформления допустим возврат frontend0.10.0: меняется только FRONTEND_IMAGE,
выполняется up -d --no-deps --wait frontend, затем пересоздаётся собственный proxy для Docker DNS.
Общий Nginx, TLS, PostgreSQL и backend не пересоздаются.
Для возврата к прежнему интерфейсу подготовлен lastochka-frontend:0.9.10-schema13 —
код принятого0.9.10 с отдельной меткой совместимости V13, проверенный с новым backend.
Исходный immutable tag0.9.10 не переопределён. Gate требует концепцию ADMIN_ENQUIRIES_V1
и поддержку13 у согласованной пары. backend0.9.0 нельзя штатно возвращать после V13.

Резервная копия основной поставки:
/opt/lastochka/backups/pre-0.10.0-20261025T195314Z/.
Она проверена восстановлением; локальная копия мигрировала V12→V13 с сохранением13 отпечатков.
Старый dump не накладывается поверх новых заявок. Disaster restore — отдельная процедура
с новой внешней ADMIN_ACCESS_GENERATION. Приватные данные резервной копии не публикуются.

Перед каждой будущей поставкой заново проверять версии, схему, readiness, backup/restore,
допустимость отката и сохранность ADMIN/ключей/заявок/очереди/платёжных черновиков.
