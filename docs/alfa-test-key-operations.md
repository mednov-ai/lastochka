# Тестовый эквайринг: ключ шифрования

Эти действия относятся только к тестовой интеграции. Ключи и реквизиты не входят в Git,
образы, обычную копию БД, отчёты или сообщения. Сама эта инструкция не подтверждает,
что интеграция, её активация или тестовый мерчант проверены банком.

## Хранение и резервирование

Backend читает `lastochka.alfa.key-directory` и `lastochka.alfa.key-id`; в каталоге
должен находиться файл `<key-id>.key`, содержащий Base64 от 32 криптографически
случайных байтов. Key ID состоит только из букв латинского алфавита, цифр, `_` и `-`.
Файл доступен только необходимому backend UID; соответствие владельца, прав и
фактической читаемости проверяют внутри контейнера. Не выводить содержимое файла и
не передавать его в аргументах процесса. Без действующего ключа создание/чтение
банковых секретов недоступно; остальные функции приложения должны продолжать работу.

До изменения ключей сохранить проверяемый backup БД и отдельно защитить резервные
копии всех нужных файлов ключей и их идентификаторов. Копию ключей хранят отдельно
от backup БД, с ограниченным доступом и отдельной процедурой восстановления.
Проверка восстановления выполняется на изолированной копии БД с соответствующими
копиями ключей; одного успешного создания backup недостаточно.

## Замена ключа

1. Подготовить новый уникальный ID и новый независимый ключ в отдельном защищённом
   файле этого же каталога. Не перезаписывать старый файл. Проверить его доступность
   backend и наличие защищённой копии до запуска ротации.
2. Имея действующую ADMIN-сессию с недавним подтверждением пароля и CSRF, вызвать
   `POST /api/v1/admin/alfa-config/rotate-key` с `{"keyId":"<новый-id>"}`. Содержимое
   ключа в запрос не передаётся. Операция работает под общей блокировкой записи,
   проверяет доступность обоих ключей и атомарно перешифровывает все сохранённые
   версии реквизитов и ссылки. При ошибке транзакция отменяется; повтор возможен
   только после выяснения причины.
3. После успешной транзакции процессы со старым `key-id` отказывают в новых банковских
   операциях и новых зашифрованных записях. Контролируемо переключить все backend-процессы
   на новый ID, убедиться в их готовности и проверить чтение на изолированной копии.
   Не считать автоматический откат на процесс со старым ID безопасным включением банка.
4. Старый ключ и его защищённую копию не удалять, пока отдельно не проверено
   восстановление соответствующих ранее созданных backup БД. Старые backup могут
   требовать старый ключ даже после успешной ротации действующей БД.

При неоднозначном результате операции сначала проверить состояние БД и доступность
обоих ключей; не повторять вслепую и не восстанавливать старую БД поверх новых
данных. Фактическое восстановление, ротация на стенде и все ограничения фиксируются
в отчёте поставки без секретов.
