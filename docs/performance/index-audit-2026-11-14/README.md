# Аудит индексов PostgreSQL — 14.11.2026

## Вывод

Основной кандидат — `payment_requests(created_at DESC, id DESC)` для страниц оплат. Второй — частичный индекс очереди проверки банковских операций. Оба дали выигрыш на синтетических данных, но это ещё не свидетельство заметной задержки на действующем стенде: размеры таблиц, частота запросов и планы на нём не измерялись. Миграция не создана, на test и production индексы не добавлялись.

Для `studio_sessions(ends_at)` есть выигрыш в одном сценарии подготовки постоянного расписания; рекомендовать индекс пока рано. Индексы очередей уведомлений для сортировки в этой выборке планировщик не выбрал. Публичное расписание и список заявок уже используют подходящие индексы.

## Условия

- Исходный код: `develop`, HEAD `8ebd047f08ceecb0ae7a629dbf5ddb659be6ea44`, включая имеющиеся незакоммиченные изменения заявок и миграцию V29. Никакие имеющиеся изменения рабочего каталога не изменялись.
- Отдельный локальный кластер PostgreSQL 17.11, без TCP; PostgreSQL проекта в compose — 17.6. На пустой базе последовательно исполнены SQL-миграции V1–V27, SQL-часть V28 и V29. V28 исполнялась напрямую только для построения пустой синтетической схемы, без запуска Java-проверки ключей; это не проверка штатного процесса миграции.
- Два синтетических набора: 100 000 и 1 000 оплат и заявок; 90 000 и 900 банковских попыток, соответственно. Из попыток 90% архивные, 10% открытые; ещё 10% платежей без попытки. Заявки и очереди по 100 000 / 1 000 строк, из них 1% в PENDING, половина PENDING готова к отправке. 100 000 / 1 000 занятий с шагом 1 час с 2020 года. Данные не отражают реальное распределение, количество или частоту операций.
- `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON, TIMING OFF)`, семь повторов, медиана времени исполнения сервера; планы и посещённые блоки — в приложенных результатах. Прогретый кэш, без сетевой задержки, приложения и параллельной нагрузки. Запросы обновления откатывались в транзакции. Для начального общего списка оплат запрошено 25 строк, для активных/архивных — 20, как в коде. Первая страница. Каждый кандидат создавался одновременно с остальными; замеры показывают выбранный план, а не изолированное влияние каждого индекса на общую нагрузку.

## Кандидаты

### 1. Сортировка оплат

Запросы `list`, `listActive`, `listArchived` в `PaymentRepository.kt` сортируют по времени и ID, а отдельного индекса на этот порядок в схеме нет:

```sql
CREATE INDEX payment_requests_created_id_idx
    ON payment_requests (created_at DESC, id DESC);
```

В эксперименте индекс занял около 4,7 МиБ при 100 000 исходных строках; это приближённая оценка, поскольку тестовые многократно откатываемые вставки раздувают индекс. Вставка 2 000 синтетических оплат в одной операции: 9,068 → 10,514 мс (+16%); на малом наборе 7,327 → 8,507 мс. Это лабораторная проверка накладных расходов, а не оценка стоимости отдельных HTTP-запросов или всех обновлений.

### 2. Банковская очередь

`due` и `dueProduction` в `PaymentRepository.kt` выбирают по среде, сроку, состоянию, архиву и callback. Прежний `alfa_test_attempts_pending(next_check_at)` покрывает только `operation_state NOT IN ('PAID','CANCELLED')` и не соответствует ветке `OR callback_pending=true`. Кандидат:

```sql
CREATE INDEX alfa_attempts_due_environment_idx
    ON alfa_test_attempts (environment, next_check_at, payment_id)
    WHERE (archived = false AND operation_state NOT IN ('PAID', 'CANCELLED'))
       OR callback_pending = true;
```

В эксперименте около 456 КиБ. Индекс выбран и для принудительного generic-плана с параметром времени. Важно повторно проверить фактически генерируемые параметры, распределение очереди и нагрузку обновлений состояний: изменение полей предиката или времени проверки меняет индекс. Банковская интеграция и workers на test ранее были выключены; их текущее состояние здесь не проверялось. Старый индекс автоматически не удалять: его использование другими запросами и стоимость на реальной нагрузке нужно оценить отдельно.

### 3. Окончание занятия — предварительная гипотеза

`busyFuture` в `PermanentScheduleRepository.kt` фильтрует по `ends_at`, сортирует по `starts_at,id` и ограничивает результат. Экспериментальный `CREATE INDEX ... ON studio_sessions (ends_at)` в большом наборе уменьшил время 6,307 → 2,158 мс, но требует сортировки. Для календарного пересечения интервалов PostgreSQL продолжил читать существующий индекс начала и прошёл значительную историю; одного нового B-tree индекса недостаточно для устойчивого решения обоих запросов. Проверить интервалы, распределение прошлых/будущих занятий, планы и частоту подготовки расписания; при необходимости отдельно исследовать переписывание запроса или индекс интервалов. Не добавлять только по этому замеру.

### 4. Очереди уведомлений

Частичные индексы `(created_at, enquiry_id) WHERE status IN ('PENDING','RETRY_WAIT')` испытывались отдельно для Telegram и push, чтобы соответствовать порядку захвата. Планировщик выбрал имеющиеся индексы `(status,next_attempt_at)`, и заметного ускорения не получено. Другие доли готовых/отложенных задач, конкуренция `SKIP LOCKED` и большие накопления отложенных задач не проверялись. Основания добавлять индексы сейчас нет.

## Границы и дальнейшая проверка

Результаты относятся к отдельным SQL-командам, а не полной загрузке страницы, и не показывают холодный кэш, потребление CPU под нагрузкой, конкуренцию транзакций или задержки сети. Не замерялись insert/update банковских и push/telegram строк, стоимость создания индекса и блокировок на сервере, актуальные статистики и реальные размеры таблиц. Перед внедрением стоит безопасно снять агрегированную статистику с test или с отдельной копии, проверить планы при типичных объёмах и с параметрами приложения, сравнить нагрузку на запись и согласовать отдельную миграцию и выпуск по процедурам проекта. Никаких персональных данных для этого эксперимента не использовано.
