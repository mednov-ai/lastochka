## Браузерное сравнение

Две раздельные production-сборки из исходного и изменённого исходника, Node 24.22.0, Chromium 156.0.8078.4 в новых контекстах с реальным пользовательским User-Agent. Размеры 1440×900 и 390×844, 7 запусков каждой версии с чередованием, одинаковая фикстура. Прокси намеренно задерживает каждый запрос JS-ресурса на 900 мс, фикстура публичных API — на 250 мс; локальный прокси использует HTTP/1.1, что вместе с задержкой отдельных файлов может создавать очередь запросов; сеть, данные и машина одинаковы для обеих версий. Кеш браузера в каждом измерении новый; CPU и браузерные устройства не замедлялись. Начальная неделя содержала 14 занятий; отдельный синтетический стрессовый набор — 126 занятий на двух страницах. Искусственные интервалы набора не моделируют реальную загруженность тренера.

Момент результата — появление видимой таблицы или мобильного списка при наличии всех строк выбранной недели; время с начала навигации. Медианы в миллисекундах:

| Сценарий | Исходная версия | Новая версия |
|---|---:|---:|
| 14 занятий, компьютер | 3 606 | 1 574 |
| 14 занятий, телефон | 3 605 | 371 |
| 126 занятий, компьютер | 3 598 | 1 106 |
| 126 занятий, телефон | 3 600 | 1 103 |

На обычном наборе TTFB документа: компьютер 267 → 276 мс, телефон 266 → 274 мс. После подключения клиентского интерфейса медиана перехода на другую неделю: компьютер 299 → 296 мс, телефон 296 → 298 мс; семь последовательных переключений в каждом контексте. Раннее отображение не означает, что JavaScript уже загружен: кнопки выбора недели до подключения клиента отключены. В отдельной серии из трёх открытий на каждый размер кнопки включались через 3,04–3,07 с от навигации в том же искусственном профиле; [замеры](schedule-interaction.json). Следовательно, ускорение относится к появлению расписания, а не к готовности кнопок. `X-Accel-Buffering: no` и `Cache-Control: no-store` присутствуют в локальном ответе; прохождение потока через реальный Nginx и поведение на пользовательском устройстве не проверены.

[Все замеры обычной недели](schedule-filled.json), [недели на 126 занятий](schedule-paged.json), [переключения](schedule-switch.json); [программа сравнения](compare.mjs.txt), [программа переключения](switch.mjs.txt), [прокси](proxy.mjs.txt) и [фикстура](fixture.mjs.txt) сохранены как записи эксперимента с локальными путями/портами, а не как готовые к применению скрипты. Такой контролируемый профиль показывает разницу в выбранных условиях и не является прогнозом времени на test/production. В 3 из 7 мобильных и 4 из 7 компьютерных запусков обычной недели новая версия показывала результат примерно за 1,6 с, остальные — около 0,3–0,4 с; разброс сохранён в сырых данных.

Для обычных браузеров сервер начинает загрузку выбранной недели параллельно со справочником и потоково передаёт её, не дожидаясь JS. Для User-Agent, распознанного `isbot`, React Router по умолчанию ждёт все потоковые границы; для сохранения независимости главной этот сценарий использует прежнюю загрузку расписания после подключения клиента. Проверены задержка источника, ранняя выдача, отсутствие повторного запроса первой недели, страницы >100, поздний ответ, коррекция недели при несовпадении часов, переход начала занятия, возврат к вкладке и no-JS. Физические устройства и реальные условия сети отдельно не проверены.

## Локальное применение, резервирование и откат

1. Реальный Flyway ранее собранного backend создал отдельную пустую базу до V29. Копия этого JAR с единственным добавленным SQL V30 прошла Flyway до V30 и запустилась. Это проверка упакованной миграции. Позднее она повторена на JDK 25: старый JAR мигрировал отдельную БД до V29, копия JAR с V30 — до V30, прежний JAR снова стартовал с предупреждением Flyway. После этого JAR, штатно собранный из текущего локального дерева на JDK 25, проверил все 30 миграций и запустился на V30. Реальная поставка требует отдельной проверки.
2. 100 000 синтетических занятий в этой базе сохранили количество и отпечаток ID `533e6a62d6642db03d50adf994917bc9`. Прежний JAR повторно запустился на V30 с предупреждением Flyway о будущей версии, публичный запрос вернул HTTP 200. Рабочий откат на сервере и бизнес-операции оплаты не проверены.
3. Отдельная синтетическая V29 с 1 000 записей была сохранена `pg_dump -Fc`, восстановлена в новую локальную базу, затем к восстановленной копии применён SQL V30. В пяти таблицах совпали количества и отпечатки ID, включая 900 попыток. Это проверка копии в локальном окружении, не действующего backup сервера и не сравнение всех полей/таблиц.
4. Перед поставкой на test проверить целевой сервер/зону и фактическую версию V29, исходники и уникальность версии миграции, наличие свежего backup с проверенным restore и свободное место. Оценить время построения на копии сопоставимого объёма и согласовать период: обычный `CREATE INDEX` выполняется в транзакции Flyway и блокирует запись в соответствующие таблицы на время построения. Не подменять его на `CONCURRENTLY` внутри транзакции. Убедиться, что механизм выпуска умеет применять именно V30 и сохранять остальные миграции/индексы; test-применение и проверка отката отдельно не выполнены.
5. После поставки проверить наличие и валидность индексов, работу API, очередей и совместимость приложения, не удаляя индексы и не восстанавливая базу поверх рабочей. При откате приложения оставить аддитивные индексы на месте и использовать проверенную совместимую версию. Production требует отдельной отмашки, релизной ветки и действующих процедур; TLS остаётся только 1.2.
