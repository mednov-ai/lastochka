## Совместимость

Новый backend применяет V15 и поддерживает `RECURRING_GROUPS_V1` вместе с
`ADMIN_ENQUIRIES_V1` и `PASSWORD_LIFECYCLE_V1`. Штатная упаковка backend записывает
эти признаки в `compatibility.json`; упаковка frontend требует схему 15,
`PASSWORD_LIFECYCLE_V1` и `requiredScheduleCapability: RECURRING_GROUPS_V1`.
Сама смена номера схемы не подтверждает правильную обработку одиночных исключений
и инвалидацию серийных планов.

Новый UI требует новый backend. Старый frontend0.12.1 (подготовленный тег0.12.1-schema15) проверен против нового
backend: одиночное изменение сохраняет связь, формирует исключение и инвалидирует
план. Такой откат оформления возможен только с сохранением нового backend/V15
и после сверки конкретного пакета. Уже сохранённые группы/серии/черновики останутся
в БД, хотя старый UI не даёт ими управлять.

После появления серий возврат к прежнему backend0.11.0 небезопасен: он не знает
новых связей, исключений и версий плана. Совместимый backend для отката обязан
поддерживать оба механизма `PASSWORD_LIFECYCLE_V1` и `RECURRING_GROUPS_V1`.
Не удалять V15 и не накатывать старый dump поверх новых бизнес-данных.

## Порядок следующих поставок

1. Отдельно согласовать поставку; назначить новые неизменяемые версии пакетов и
   проверить их содержимое/контракты. Версии0.13.0 уже заняты принятой поставкой; не перезаписывать их.
2. Зафиксировать исходные image ID, схему, параметры запуска и доступную полную
   ADMIN-сессию; сохранить резервную копию БД и файлов. Секреты и ключи в отчёт
   не выводить. Снять отпечатки исходных ADMIN/паролей/ключей/версий и бизнес-таблиц.
3. Восстановить копию в отдельную БД, применить V15 принятой сборкой, сравнить
   прежние данные. Проверить новый контракт и совместимость старого UI.
4. Обновлять только согласованные сервисы Ласточки. Сохранить прежние JS/CSS для
   прогретых вкладок, исходных ADMIN и данные; не менять shared Nginx/TLS/ACME и
   соседние приложения без отдельной необходимости.
5. После обновления принять создание/повторное открытие черновика, полный план,
   публикацию, разовое исключение и конфликт со старой вкладкой; проверить публичный
   `/#schedule`, выбор конкретной даты и серверную заявку без JS.
6. Сверить отпечатки, удалить только созданные для приёмки записи и сессии,
   сохранить отчёт/путь проверенной копии и конкретный совместимый откат.

При аварийном восстановлении использовать отдельную восстановленную БД и новую
внешнюю `ADMIN_ACCESS_GENERATION`, чтобы прежние сессии и ключи операций не давали
доступ к восстановленному состоянию. Не переключать на копию с устаревшей generation.

## Локальное воспроизведение

Backend-проверки запускаются на Java25 штатным `backend/gradlew -p backend test
architectureCheck bootJar`; Testcontainers создаёт отдельный PostgreSQL. Целевой
`RecurringGroupsIntegrationTest` проверяет V14→V15 и конкурентные операции.

На Node24 в `frontend/` выполняются `npm run api:generate`, `npm run typecheck`
и `npm run build`. OpenAPI сначала экспортируется из принятого backend штатным
механизмом проекта. Сгенерированный `app/api/schema.d.ts` вручную не редактировать.

Браузерная матрица запускается через
`npx playwright test -c playwright.recurring-calendar.config.ts`. Она предназначена
строго для отдельного localhost-стенда: proxy18100, backend8100, frontend5191,
контейнер `lastochka-recurring-postgres`, БД `lastochka_recurring`. Сценарии создают
собственные занятия/серии, входят тестовым ADMIN и очищают ограничитель входа только
этой одноразовой БД. Не перенаправлять эту конфигурацию на сервер или реальные данные.
При повторе выбирать свободный диапазон через `RECURRING_RUN_OFFSET` либо новую БД.

Для этой приёмки собственный PostgreSQL был опубликован только на127.0.0.1:55440.
Копия до V15 и восстановленная БД проверены отдельно. В момент миграции совпали
18 прежних таблиц; при последующем restore сравнивались 16 бизнес-/учётных таблиц,
без истекающих строк Spring Session. Копии имеют режим0600 и остаются локальными.
После приёмки собственные процессы остановлены и одноразовый контейнер удалён.

## Разбор рабочих ситуаций

- «План устарел»: сохранить ввод, прочитать актуальное состояние и заново рассчитать
  план. Не заменять ключ повторной отправки после неизвестного сетевого результата.
- «У занятия есть отдельный черновик»: открыть его в прежнем редакторе и осознанно
  завершить или отменить. Серийная публикация не должна обходить этот конфликт.
- Внешний или взаимный конфликт дат: исправить правило/занятость; отсутствие конфликта
  на первой странице не означает, что весь план можно публиковать.
- Снята среда, но отдельное перенесённое занятие осталось: это сохранённое исключение.
  Проверить строку плана и отменить конкретное занятие явно при необходимости.
- Группа переименована, а опубликованный заголовок прежний: значения занятия — снимок.
  Чтобы менять будущие занятия, требуется отдельный план и публикация серии.
- Сохранённый черновик не раскрывается из-за нового конфликта/занятости: календарь
  сообщает предупреждение; правило остаётся в разделе «Группы», его можно исправить.

Повторения не отправляют заявки, не бронируют места и не создают посещения.
Публичные обращения по-прежнему ссылаются на одну опубликованную дату и её снимок.
Настройка Telegram и платёжного провайдера этим изменением не выполнялась.
