# Индексы типовой недели после выкладки на test

20 ноября 2026 года, 07:41 МСК. На test версия `0.25.0-permanent-week-test-20261119`. Публичный API и PostgreSQL показали пять действующих категорий и ноль постоянных интервалов. Запросы выполнены от `lastochka_reader` в транзакции только для чтения. [Планы test и результаты сравнений](index-test-2026-11-20.txt)

| Проверка | Наблюдение |
| --- | --- |
| Чтение всех полей интервалов для афиши и редактора на test | Последовательное сканирование, 0 строк, 0,018 мс исполнения запроса PostgreSQL. Фильтрация по доступным категориям и сортировка происходят в приложении. |
| Поиск одного UUID на test | PostgreSQL выбрал первичный ключ, 0 строк, 0,058 мс. Таблица пуста, поэтому время поиска существующего интервала на стенде пока неизвестно. |
| Каталог test до замеров | Оба индекса готовы и действительны, по 8 КиБ каждый. Счётчики сканирований равны нулю, дата сброса статистики не указана. |

Для дополнительного сравнения использованы только московский день недели, время начала и продолжительность 43 записей из копии прежнего календаря test. В их числе ранее созданные тестовые занятия. Сумма SHA-256 исходной копии совпала с отчётом о выпуске. При сворачивании дат получилось 15 различных непересекающихся интервалов. Эти интервалы существовали только в локальном эксперименте. [Происхождение копии](../../deployment/2026-11-19-weekly-test.md)

В изолированном PostgreSQL 17.6 таблица создана по DDL V32 и проанализирована через ANALYZE. При чтении 15 строк с обоими индексами и после снятия обоих ограничений внутри откатываемой транзакции план был одинаковым: последовательное сканирование, один буферный блок. После первого прогрева семь повторов дали 0,003–0,006 мс в каждом варианте. Это измерение SQL на малом объёме.

Для проверки записи использованы отдельные контрольные примеры. При двух ограничениях PostgreSQL отклонил повтор UUID (23505) и наложение понедельника 00:10 на воскресенье 23:45–00:30 (23P01). Соседнее занятие с началом в 00:30 принято. После поочерёдного снятия ограничений база пропустила соответствующее нарушение. [Код чтения и редактирования](../../../backend/scheduling/src/main/kotlin/ru/lastochka/scheduling/service/WeeklyScheduleService.kt)

**Решение.** Сохранить `weekly_intervals_pkey` для идентичности интервалов и `weekly_intervals_no_overlap` для запрета пересечений. Для запроса полной недели дополнительный индекс по дню или времени не требуется. Скорость на фактически опубликованной заполненной неделе можно измерить после появления интервалов на test.
