# Пользователи и пароли: эксплуатация

Функция поставлена26.10.2026: backend/frontend0.11.0/V14. [Отчёт поставки](deployment/2026-10-26-user-passwords.md),24/24;3 исходных ADMIN и14 отпечатков сохранены. Действующие требования до архивирования — в `openspec/changes/archive/2026-10-27-add-user-provisioning-and-temporary-passwords/specs/`.

## Создание и восстановление

1. Войти постоянным паролем администратора. Открыть «Пользователи». Для создания/сброса подтвердить свой пароль не более 5 минут назад через ссылку на странице.
2. Нажать «Добавить пользователя», ввести имя, свободный логин и временный пароль. Сейчас создаётся только «Администратор» с доступом ко всем административным функциям после смены пароля. Иные роли сервером запрещены.
3. Логин — 3–64 латинских строчных буквы, цифры, `.`, `_`, `-`; внешние пробелы и регистр логина приводятся к единому виду. Пароль — 6–128 Unicode code points, минимум буква и цифра, без изменения пробелов/регистра/нормализации. В интерфейсе пароль скрыт; показать его можно только во время ввода.
4. Передать логин и назначенный пароль владельцу лично вне приложения. Секрет не сохраняется открытым, не выводится в списке и не отправляется почтой/ботом. Временный пароль действует 24 часа.
5. Владелец входит и выбирает новый пароль с подтверждением. До смены недоступны административное чтение, команды и операции с ключами. Ограниченная сессия истекает через 15 минут либо вместе с паролем; повторный вход возможен, пока пароль действует. После смены прежний временный пароль больше не принимается.
6. При потере/истечении временного пароля выбрать нужного пользователя, нажать «Назначить временный пароль», проверить логин и подтвердить завершение его прежних сеансов. Установить новое значение. Если данные изменились, обновить список и повторно открыть нужного пользователя. Сброс себе запрещён: использовать «Безопасность» → «Сменить пароль».

Если ответ на создание потерялся, сначала проверить список. Повтор с тем же логином даёт конфликт и не меняет созданный аккаунт. Если ответ на смену потерялся, попробовать новый пароль; автоматически повторять команду или возвращать старый пароль нельзя.

## Отзыв и аудит

Смена/сброс увеличивают `auth_version`, отзывают все прежние сессии и незавершённые WebAuthn challenge аккаунта. После собственной смены текущий браузер получает новую полную сессию и новый CSRF; другие устройства должны войти заново. Ключи и бизнес-история сохраняются. Ключ не заменяет обязательную смену. Проверка версии повторяется под общей транзакционной блокировкой команд, поэтому ожидавшая блокировку команда не выполняется после отзыва.

Аудит содержит цель, автора, тип и время, без паролей/хешей: `USER_CREATED`, `TEMPORARY_PASSWORD_ASSIGNED`, `TEMPORARY_PASSWORD_CHANGED`, `PASSWORD_CHANGED`. Ошибки полей, лимиты и CSRF сохраняют единый безопасный русский контракт. `403 PASSWORD_CHANGE_REQUIRED` означает необходимость смены; `401` — отсутствие/истечение/отзыв сессии. `429` требует ожидания `Retry-After`, а не обхода лимитов.

## Закрытое восстановление оператором

При потере доступа всеми ADMIN остаётся существующий `AdminAccessBootstrap`: адресное `lastochka.admin.configure=true` с ID, необязательным логином и новым временным паролем. Работать только с проверенным совместимым backend и защищённым локальным/server env-файлом с правами 0600, используя существующий операторский способ передачи окружения. Секрет не указывать в argv, истории команд, чате или выводе; `LASTOCHKA_ADMIN_PASSWORD` читается из окружения процесса. После адресной процедуры удалить временный защищённый источник и завершить обязательную смену обычным входом. Процедура не отправляет письма и не удаляет ключи. Повтор настройки логина без адресного пароля не меняет прежний хеш.

`AdminBootstrap` для первичного закрытого создания оператора остаётся отдельным первоначальным действием. Не запускать его повторно для существующего логина и не использовать для обхода пользовательской процедуры временного пароля.

## Совместимость и отдельно порученная поставка

Нужна схема V14 и backend с `org.lastochka.password-lifecycle=PASSWORD_LIFECYCLE_V1`. Все штатные новые образы также несут этот маркер, упаковка сохраняет его в сведениях об образах и `compatibility.json`. `python3 scripts/check-concept-release.py --self-test` проверяет положительный и отрицательные случаи; обычный вызов проверяет два конкретных образа. Граница схемы и concept marker продолжают проверяться.

**Backend0.10.0 и более ранние backend не являются безопасным откатом после включения временных паролей:** чтение аддитивной схемы не означает соблюдение обязательной смены. Откат backend разрешён только на образ с той же защитой. Старый интерфейс может не показывать форму смены, но сервер обязан блокировать его защищённые запросы; обновить страницу/интерфейс. Прежние постоянные ADMIN продолжают работать без принудительного сброса.

Перед отдельно порученной поставкой: повторить живой read-only preflight, проверить свежий backup восстановлением в отдельную БД, зафиксировать исходные аккаунты/хеши/ключи/сессии и бизнес-данные, собрать готовые Linux/amd64 образы локально и проверить маркеры. Не назначать временные пароли исходным ADMIN для приёмки. Принять цепочку на отдельных тестовых ADMIN, проверить сохранность прежней вкладки/ключей/расписания/заявок/очереди/DRAFT и удалить только свои fixtures/сессии. Не восстанавливать старый dump поверх новых данных; disaster restore требует новой внешней `ADMIN_ACCESS_GENERATION`.
