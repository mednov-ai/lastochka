# Автоматическое подтверждение email и обратная связь об ошибках

Локальная реализация `improve-auth-verification-and-error-feedback`, 23.10.2026.
Этот отчёт фиксирует локальный этап: сервер 0.5.0 и туннель 18027 тогда не менялись.
Последующая поставка по отдельному поручению —
[backend/frontend 0.6.0, V9 и сохранность](deployment/2026-10-23-auth-feedback.md).
Изменение архивировано 23.10.2026, действующие требования находятся в `openspec/specs/`.

## Реализованное поведение

Страница `/auth/verify#token=…` удаляет секрет из адреса до загрузки приложения,
читает его в память и автоматически выполняет CSRF-защищённый POST. GET не
подтверждает email. После успеха остаются результат и ссылка входа с проверенным
`next`, формы и кнопки «Подтвердить email» нет. Повтор после потерянного ответа
доступен явно; смена fragment в той же вкладке запускает проверку новой ссылки.
Устаревший результат не заменяет её состояние. Без JavaScript видна инструкция.
Ссылка сама не создаёт парольную сессию и не подменяет уже вошедшего пользователя;
ранее проверенная парольная сессия сохраняет прежние правила.

V9 добавляет nullable `auth_tokens.consumed_at` и частичный индекс срока VERIFY.
Проверка сериализуется блокировкой аккаунта и повторно проверяет действительность
токена после блокировки. Повтор успешен в исходные 24 часа, сохраняет первый
`verified_at`/`consumed_at` и не создаёт новых писем, аккаунтных сессий или действий.
Перевыпуск отзывает старую ссылку; периодическая очистка удаляет только истёкшие
VERIFY, в том числе после перезапуска. RESET остаётся одноразовым. «Приду» по-прежнему
требует явного нажатия.

Новый пароль: 6–128 Unicode code points, минимум одна буква категории L и одна
десятичная цифра Nd. Пробелы и символы допустимы; trim, normalize и изменение
регистра не выполняются. Общий серверный валидатор используется DTO и сервисными
register/reset/createAdmin/новыми preview fixtures. Слабый reset не расходует
ссылку, не меняет хеш/authVersion и не отзывает доступ. Вход по старому паролю
не получает новых требований состава или минимума. Поле браузера допускает
256 UTF-16 единиц; общий helper проверяет настоящую границу 128 code points.
Общие синтетические векторы: `test-fixtures/password-policy.json`.

Все серверные публичные ошибки получают title/detail/fieldErrors из UTF-8
`backend/app/src/main/resources/messages.properties`. `ApiErrorFactory` вызывается
advice и Security entry point/access-denied handler, включая CSRF. Сохранены
статусы, `application/problem+json`, поля ApiError и `Retry-After` для 429.
Парольные отказы: 400/VALIDATION_ERROR с конкретной причиной в fieldErrors.password.
Неизвестный ключ/исключение даёт безопасный fallback; исключение, SQL, отвергнутое
значение и произвольные параметры не включаются в публичные сообщения. Диагностика
500 содержит code/requestId, класс и место, без throwable/message/body.
[Карта кодов и вызовов](auth-error-inventory.md).

Один frontend-нормализатор предпочитает detail/fieldErrors своего API и передаёт
ошибку одному dispatcher. Произвольный Error.message/HTML не показывается; локальные
проверки используют явный UserFacingError. Повтор того же объекта ошибки подавлен,
новый запрос получает отдельное уведомление. Транспорт не показывает toast сам:
это делает актуальный UI catch после generation guard. Фоновый auth refresh,
отмена запроса и устаревший ответ периода не создают плашек.

Плашки справа внизу: максимум три, 6 секунд видимого времени, пауза hover/focus/
hidden, ручное закрытие, safe-area и отсутствие анимации при reduced-motion.
Портал использует постоянный DOM-контейнер, перемещаемый в верхний открытый native
dialog или body. Смена слоя не пересоздаёт плашку/таймер/announcement. Показ не
меняет фокус; Tab/Escape и возврат фокуса окна сохраняются. Host находится вне
AuthProvider и работает на публичной странице «Приду» без auth-запросов.
Постоянное состояние ошибки и полевые причины остаются после закрытия плашки;
auth и карточки детей связывают ошибки с полями через aria-describedby.

## Возможная будущая поставка и откат

Поставка отдельно разрешается пользователем. До неё нужен свежий backup и
отпечатки аккаунтов/хешей/ролей/ключей/бизнес-данных. Порядок: новый backend с V9,
проверка старого frontend, затем новый frontend и публичная HTTPS-приёмка. Seed
не запускать, существующие пароли и аккаунты не пересоздавать.

Откат frontend совместим с новым backend и возвращает ручную кнопку VERIFY.
V9 аддитивна: колонку/индекс при откате не удалять. Старый backend возвращает
прежнюю политику новых паролей и потребление VERIFY; его фактический rollback
и Flyway-поведение требуют отдельной проверки перед серверной поставкой.
Не восстанавливать backup поверх более новых пользовательских изменений.

Эта приёмка локальная: серверный HTTPS, новая поставка образов и физические
устройства WebAuthn в неё не входят. Приёмка интерфейса выполнена Chromium;
работа с VoiceOver и экранной клавиатурой физического телефона отдельно не заявляется.
