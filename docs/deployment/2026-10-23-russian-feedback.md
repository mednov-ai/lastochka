## Публичная HTTPS-приёмка

`scripts/remote-russian-feedback-acceptance.mjs` зафиксировал **190 проверок**:
3 совместимости старого UI, 2 старой вкладки, 182 нового поведения и 3 отдельной
проверки разрыва/восстановления WSS. Это публичные проверки, а не повторное
объявление ранее выполненных 72 локальных browser-сценариев и 54 backend-тестов.

Матрица нового UI: **Chromium/WebKit × en-US/ru-RU × 375/1440**, гость,
отдельные временные PARENT и ADMIN. Исходные пользователи и их пароли для тестов
не использовались; ADMIN назначен только собственному проверочному аккаунту.

Проверены:

- русские required/email-сообщения, aria-invalid/aria-describedby, постоянное
  объяснение поля и отсутствие блокировки после исправления;
- отправка Enter, модальное окно, переключение режима без старых ошибок,
  Escape/возврат фокуса, backend-ошибка по-русски над backdrop;
- реальная регистрация, SMTP-ссылка, автоматическое подтверждение почты,
  полноценный парольный вход и сохранение правильной работы правил пароля/API;
- корректное сохранение собственного ребёнка, будущая дата рождения и её
  исправление; латинское пользовательское имя осталось буквальным;
- русские подписи ключа доступа, обязательность названия занятия, вместимость,
  числовой шаг, дата переноса и причина отмены; повторное открытие панели без
  устаревшего custom validity;
- отсутствие горизонтального переполнения, понятные подсказки без JS;
- реальная временная одобренная запись и ограниченная ссылка «Приду»: явный
  ответ по-русски, без входа в аккаунт и доступа к данным семьи;
- почтовый UI «Подключено», дата ru-RU/МСК при английской локали, безопасный
  публичный просмотр, запрет DELETE и новое backend SMTP-письмо без reload;
- закрытие только WebSocket проверочного браузера: «Нет соединения» и
  автоматическое возвращение «Подключено» по WSS. SMTP/общий сервис ради этого
  не перезапускались.

Скриншоты публичного модального окна 375/1440 и почты 375 осмотрены. Предварительные

Сценарий исправлен; приложение ради приёмки не менялось. Перед повторами удалены
только собственные fixtures, исходные таблицы и письма каждый раз сверены.

Автоматическая защита исходников от английских подсказок/жаргона остаётся частью
локальной сборки, CI и упаковщиков; на сервере компиляторы/проверяющие инструменты

## Откат без потери новых данных

Для узкого отката frontend указать только FRONTEND_IMAGE=lastochka-frontend:0.6.0
в `/opt/lastochka/shared/.env.preview`, пересоздать frontend и затем собственный proxy.
Совместимость прежнего frontend с новым backend проверена на публичном HTTPS.

Для полного отката приложения указать BACKEND_IMAGE=lastochka-backend:0.6.0 и
FRONTEND_IMAGE=lastochka-frontend:0.6.0. Для почтового UI —
MAILHOG_PUBLIC_IMAGE=lastochka/mailhog-public:1.0.0 в отдельной public env.
Остальные параметры env, keyring/generation и публичный флаг сохранить.

Использовать те же действующие Compose/overlay, без конфигов из нового package:

```sh
docker compose -p lastochka-preview \
  --env-file /opt/lastochka/shared/.env.preview \
  --env-file /opt/lastochka/mailhog-public/shared/public.env \
  -f /opt/lastochka/releases/mailhog-websocket-20261023/compose.preview.yaml \
  -f /opt/lastochka/mailhog-public/current/compose.mailhog-public.yaml \
  up -d --no-deps --wait backend frontend mailhog-public
```

После изменения upstream пересоздать только proxy тем же вызовом с
`up -d --no-deps --force-recreate proxy`. Проверить readiness, вход, старую вкладку,
SMTP/WSS и соседние сайты. V9, БД, volumes и исходные письма не откатывать:
в 0.6.1 нет миграций, восстановление старого dump поверх новых данных не требуется.
Живой откат пользовательского сервера не выполнялся и не потребовался.
