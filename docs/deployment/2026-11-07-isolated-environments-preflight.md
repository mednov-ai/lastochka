# Подготовка двух окружений — 7 ноября 2026

Это исторический отчёт подготовки. После описанного этапа пользователь разрешил
начальный выпуск production; фактическое состояние — в
[`2026-11-07-initial-production.md`](2026-11-07-initial-production.md).

- Первичная проверка нового сервера: Ubuntu 24.04 LTS, 1 vCPU, 961 MiB RAM, swap 1 GiB. После установки Docker 29.1.3 и Compose 2.40.3 из репозитория Ubuntu было доступно около 414 MiB RAM, `/` 19 GiB, свободно около 14 GiB. SSH и Fail2ban активны. Память впоследствии увеличена, Nginx установлен (см. ниже).
- DNS на момент проверки: `lastochka-gym.ru` и созданный по решению пользователя `test.lastochka-gym.ru` указывают на новый сервер; `play-and-say.ru` — на прежний адрес. Тестовый сайт и HTTPS ещё не запущены.
- Исторический замер одной копии preview после старта — около 519 MiB, без нагрузочной приёмки (см. `2026-10-19-preview.md`); две текущие версии, обновление и backup не измерялись. Эти цифры нельзя использовать как измерение нового релиза или гарантию размера тарифа.
- На локальном Docker Desktop проверены изолированные контейнеры с отдельной синтетической БД без публикации портов: backend 0.19.3-flat (amd64 под эмуляцией), frontend 0.19.1 и PostgreSQL 17.6. При лимитах backend 384 MiB / frontend 128 MiB / PostgreSQL 128 MiB все службы достигли health, в покое заняли около 379 / 69 / 59 MiB; при лимите backend 256 MiB и MaxRAMPercentage=40 процесс был завершён по OOM (137). Эта оценка не является измерением на VPS, нагрузкой или проверкой резервирования. Созданные только для эксперимента контейнеры, сеть и пустой тестовый том удалены по метке проекта.
- На новом VPS те же версии запущены с отдельной синтетической БД, без публикации портов и без реального банка. При лимите backend 320 MiB службы достигли health и использовали около 310 / 91 / 65 MiB, swap хоста — 416 MiB. Повтор с backend 256 MiB также достиг health и показал около 253 / 63 / 76 MiB, swap хоста — 405 MiB; запас backend около 3 MiB. Это не нагрузочное испытание и не подтверждение работоспособности двух зон. После каждого прогона созданные только для него контейнеры, сеть и пустой том удалены по метке; SSH, Fail2ban и Docker активны. Образы приложения и PostgreSQL сохранены на VPS.
- После увеличения тарифа и перезапуска Ubuntu видит 1,9 GiB RAM и 1 vCPU. Два изолированных синтетических проекта с отдельными базами и без host-портов одновременно достигли health: суммарно около 911 MiB контейнерной памяти, около 885 MiB доступной памяти хоста и 298 MiB занятого swap в момент измерения. Лимиты backend — 320 и 256 MiB; занято около 311 и 251 MiB соответственно. Оба тестовых backend близки к пределам, запуск второго занял около 96 секунд. Реальная нагрузка, backup, сбои и выпускаемые окружения не проверены. По завершении удалены только синтетические проекты и их тома, службы SSH/Docker/Fail2ban активны.
- Пароль из локального файла соответствует проверенным ограничениям действующей политики (6–128 кодовых точек, буква и цифра); его значение не выводилось. На синтетической БД в отдельной Docker-сети проверены Flyway 12.4.0, разделение ролей и создание `kines` с паролем из файла; повторное создание завершилось отказом без смены хеша. В новой тестовой БД VPS `kines` также создан из файла, фактический вход по HTTPS прошёл.
- Попытки read-only SSH к прежнему стенду известными ключами отклонены; его состояние, текущие базы и ресурсы не подтверждены. По отчёту от 6 ноября там были backend 0.19.3 / frontend 0.19.1 / V21, но это исторические данные.
- Пользователь подтвердил пустой старт обеих баз, защиту production от действий агента и ночные сжатые backup на этом же VPS с лимитом 5 ГиБ; затем увеличил память VPS до 2 GiB. Локальный backup не переживёт потерю сервера. Нагрузочная проверка двух зон ещё не выполнена.
- По решению пользователя отдельные случайные пароли двух gate созданы локально в игнорируемых `.env/gate-production.password` и `.env/gate-test.password` с правами 0600; значения различаются. На VPS переданы только хеш и ключ сессии тестового gate. Тестовая страница доступна по HTTPS; тройное касание и вход проверены в мобильном Chromium, прямой запрос к API без gate-сессии перенаправляется на заглушку.
- После повторной проверки ресурсов VPS установлены Nginx и Certbot. Получен сертификат Let's Encrypt для обоих доменов, срок действия до 5 февраля 2027 года; таймер продления и тестовое продление проверены. Настроен HTTPS тестового домена; production HTTP отвечает 404 и production-сайт пока не опубликован.
- На полностью отдельной синтетической базе применены миграции V1–V21, создан `kines` из файла, повторный bootstrap не изменил пароль. Сжатая копия этой полной базы восстановлена в отдельном контейнере без сети. Под рабочей нагрузкой резервирование ещё не проверено.
- На VPS созданы отдельные чистые тестовая и рабочая БД: Flyway V1–V21 прошёл отдельной миграционной ролью, в каждой создан `kines`. Тестовый backend запущен без Flyway и без права CREATE, повторный baseline отвергается; вход администратора прошёл и после перезапуска backend. Роль чтения не имеет права DELETE. Порты БД/backend/frontend снаружи не опубликованы. Пользователь `lastochka-agent` использует отдельный SSH-ключ и не имеет доступа к sudo, Docker, секретам привилегированных ролей и каталогам резервирования. Команды `lastochka-db-read test` и `lastochka-db-read production` проверяют идентификатор БД и подключают роль только на чтение; обновление адресов выполняет отдельная служба. Проверены чтение обеих БД и отказ в DELETE и удалении volume. Root остаётся операторским аварийным доступом и технически способен обойти ограничения.
- Первая сжатая копия рабочей БД восстановлена в отдельном контейнере без сети; ключи обеих зон скопированы отдельно под root, расшифровка синтетического сообщения с копиями проверена. Таймер `lastochka-production-backup.timer` включён на 03:00 Europe/Moscow; предел копий БД 5 GiB, ротация и отказ при сбое проверены на синтетических файлах. Первый запуск службы выявил несовместимость жёсткой ссылки с изоляцией systemd; после исправления повторный запуск завершился успешно. При испытании второй копии восстановление завершилось ошибкой; прежний архив сохранён. После исправления ожидания TCP-готовности окончательного PostgreSQL вместо временного сокета копия и полное восстановление прошли одновременно с работающей второй синтетической зоной. Архивы и ключи находятся на том же VPS; уведомление об ошибке вне журнала systemd пока не настроено.
- Интеграция с Альфа-Банком и фоновые операции выключены, исходящая сеть backend закрыта. Реальные платежи и возврат банка на новом стенде не проверены. Ключи production и test независимы. После увеличения лимита тестового backend до 448 MiB он использовал около 389 MiB в моменте; нагрузка, одновременно работающий production backend и резервирование под нагрузкой не проверены.
- При работающих тестовой зоне и production PostgreSQL запущена отдельная синтетическая зона с backend/frontend и пустой БД в tmpfs; во время её работы выполнен production backup с полным восстановлением. Минимум доступной памяти составил 527 MiB, максимум занятого swap — 182 MiB; синтетический backend занял около 406 из 448 MiB. Измерены запуск и состояние без представительной пользовательской нагрузки. Это не гарантия работы под нагрузкой; синтетические контейнеры и сеть удалены только после сверки собственных меток.
- Сборки из одного и того же JAR и frontend build, с закреплёнными базовыми образами и нормализованными временными метками, дважды собраны без кеша и дали побайтно одинаковые архивы backend, frontend и gate. Backend JAR после повторной сборки исходников совпал побайтно; текущие файлы frontend совпали со старым образом, дополнительные 138 старых assets сохранены в томе. Тестовая зона обновлена на воспроизводимые образы; после обновления прошли вход `kines`, мобильное тройное касание и проверка RP ID `test.lastochka-gym.ru`. В томе проверено 170 статических ресурсов. `npm audit --omit=dev --omit=peer` по-прежнему сообщает одну высокую уязвимость транзитивного `body-parser`; она не устранялась и её эксплуатация отдельно не проверена.
