# Календарь и «Приду» — серверная поставка 0.5.0

23.10.2026 по отдельному поручению пользователя на
<https://play-and-say.ru/lastochka/> поставлены **backend 0.5.0 и frontend 0.5.0**.
Изменение `improve-calendar-and-client-confirmation` включено. Все семь исходных
аккаунтов, пароли, роли, ключи и контент сохранены; проверочные данные удалены.

Календарь показывает полный период, доступны панели и переносы с предпросмотром.
Клиент может открыть письмо и подтвердить «Приду» без аккаунтного входа.
Письма по-прежнему принимает **закрытый MailHog**: RuSender и внешняя доставка
не подключены. CAPTURED означает приём MailHog, а не доставку реальному клиенту.

## Подготовка и поставка

До поставки сервер имел семь аккаунтов, один документ контента и ноль детей,
занятий, записей и WebAuthn credentials. Сохранены pg_dump, maildir, закрытая env,
Nginx vhost/snippet и отпечатки исходных колонок бизнес-таблиц. Сопоставление
исходных колонок позволяет проверить сохранность строк после аддитивной V8.

- Backup до поставки: `/opt/lastochka/backups/pre-0.5.0-20261023T100712Z/` (700).
  Dump действительно восстановлен в отдельную временную БД того же PostgreSQL;
  отпечатки совпали, временная БД удалена. Рабочая БД не заменялась.
- Release: `/opt/lastochka/releases/0.5.0/`; на сервер переданы готовые образы,
  manifest, Compose/proxy и несекретные инструкции. Сборки на сервере не было.
- Рабочая конфигурация: `/opt/lastochka/shared/.env.preview` (600). Свежие keyring
  и generation созданы на сервере, находятся вне БД, образов и репозитория.
- Порядок: backend с выключенной функцией → проверка V8/данных → frontend →
  включение функции с внешними ключами → повторная readiness и публичная приёмка.
  Между пересозданиями upstream пересоздавался только собственный proxy.
- PostgreSQL, MailHog и mailhog-access сохранили прежние container ID/volumes.
  Seed и массовые приглашения существующим аккаунтам не запускались.

Linux/amd64 образы собраны из проверенных локальных JAR и SSR/client bundles.
Локальная приёмка исходников: 50 backend-тестов и 37 browser-сценариев, описанных
в [локальном отчёте](../calendar-attendance.md). Перед передачей оба amd64 image
отдельно запущены локально: health/readiness, версия frontend, публичная страница,
bootstrap включённой функции и security headers прошли. На той же отдельной V8
БД проверен запуск прежних backend 0.3.0/frontend 0.4.1 без down-migration.

## Публичная приёмка

`scripts/remote-calendar-acceptance.mjs` завершил **77 проверок** на настоящем
HTTPS, с письмами через настоящий SMTP в серверный MailHog. Проверочный родитель
имел уникальный адрес, вход ADMIN использовал существующий тестовый аккаунт
без изменения его пароля/роли/ключей. Парольный вход проверен у всех семи аккаунтов.

- Неделя из 35 занятий, включая выходные, отображается целиком в сетке/списке.
  Панель содержит 25 участников на страницах 20+5. Проверены 375/768/1440 px,
  отсутствие горизонтального переполнения и видимая форма с фокусом на телефоне.
- Отмена preview не меняет занятие. Подтверждённый перенос всего занятия меняет
  время для 25 записей, сбрасывает прежний ответ и отзывает уже открытую страницу.
- Перенос одного ребёнка в существующее индивидуальное занятие показывает
  предупреждение о формате, сохраняет ID/CONFIRMED, меняет место и сбрасывает ответ.
  Старая страница после переноса не может подтвердить новые условия.
- Письмо открыто в чистом браузере без входа. Явный ответ «Приду» появляется
  у родителя и ADMIN, не меняет одобрение и занятость. После обоих переносов
  работают новые письма. Отмена отзывает доступ и освобождает только отменённое место.
- У ограниченного контекста Secure/HttpOnly/SameSite=Strict cookie с отдельным Path;
  аккаунтная сессия не создаётся. Кабинет/ADMIN API недоступны, POST без отдельного
  CSRF отклоняется. Fragment удаляется из URL; storage/email родителя не раскрываются.
  Consumed ссылка не допускает новый браузер; существующий ADMIN-вход сохраняется.

Три предварительных операторских попытки выявили ошибки самого проверочного
сценария: отсутствующий GET admin/bookings/{id}, последующий конфликт оставшегося
fixture и слишком точное сопоставление подписи фильтра. Исправлен сценарий;
данные каждой попытки удалены точечно перед повтором. Код работающего приложения
для прохождения приёмки не менялся. Финальный полный прогон прошёл.

Открытая до rollout вкладка получила прежний явный asset и выполнила переход
schedule.data → 200 без page errors. Отдельно проверены публичный доступ без
Basic Auth, prefix/query redirect 308, закрытые служебные URL и порты,
прежняя политика TLS. Play&Say `/` и RepairDevice `/repair_demo/` отвечают 200
и совпадают по SHA256 с исходным снимком; Nginx vhost/snippet не менялись,
`nginx -t` успешен, certbot.timer активен.

## Итог и сохранность

После точечной очистки итогового прогона удалены его временный родитель,
25 детей/записей, 35 занятий, grants/contexts/previews, собственные события/аудит
и 54 письма MailHog. Проверки очистки запрещают удаление занятия, если на него
ссылается чужая запись. Существующие строки и чужие письма не удалялись.
Секретные три outbox payload до очистки были ciphertext, plaintext ссылок в body
не было; backend-журналы не содержали ссылок с secret или предупреждений retention.

Отпечатки accounts, children, studio_sessions, bookings, user_credentials,
user_entities и landing_content совпали до поставки и после очистки. Итог:
7 аккаунтов, 0 детей/занятий/записей/credentials, исходный контент сохранён.
Сервис healthy; после приёмки доступно около 478 MiB RAM — это снимок,
а не оценка устойчивой нагрузки.

Итоговый dump: `/opt/lastochka/backups/lastochka/ready-for-testing-0.5.0-20261023.dump`
(600, 49 087 байт), `pg_restore --list` успешен. Ключи не помещены в dump;
при любом восстановлении обязательна новая внешняя generation до включения.

## Откат

Работать только с Compose `/opt/lastochka/releases/0.5.0/compose.preview.yaml`
и закрытой рабочей env. Сначала установить `ATTENDANCE_CONFIRMATION_ENABLED=false`
и новый UUID `ATTENDANCE_CONFIRMATION_GENERATION`, затем задать
`BACKEND_IMAGE=lastochka-backend:0.3.0` и `FRONTEND_IMAGE=lastochka-frontend:0.4.1`.
Пересоздать только backend/frontend (`up -d --no-deps --wait`), затем собственный
proxy (`up -d --no-deps --force-recreate proxy`), проверить readiness и соседние сайты.
V8, ответы и аудит сохранять; не делать down -v, down-migration или восстановление
backup поверх новых пользовательских данных. Перед повторным включением — новый
generation и корректный keyring. Откат на сервере не понадобился.

Политика ключей, очистки и восстановления:
[операторский runbook](../calendar-attendance-operations.md).
Материалы вне Git — `artifacts/release-0.5.0/`, `artifacts/server-deploy/0.5.0/`
и `runtime-data/server-deploy/calendar-0.5.0/`. Физические телефоны/passkey, нагрузка
и внешняя доставка этим прогоном не проверялись. OpenSpec архивирован 23.10.2026; требования синхронизированы.

## Дополнение: MailHog Disconnected

После обращения пользователя воспроизведён HTTP 400 на WebSocket
`/api/v2/websocket` при работающем API списка писем. Причина — отсутствие
передачи Upgrade/Connection в закрытом Nginx mailhog-access. Пустой inbox был
отдельным корректным состоянием: письма приёмки удалены, новых событий outbox не было.

В `infra/mailhog-access.conf` добавлены map/Upgrade/Connection и часовой read timeout.
Конфигурация проверена `nginx -t`, затем пересоздан только mailhog-access с новым
config-release `/opt/lastochka/releases/mailhog-websocket-20261023/`. Остальные
container ID, БД, приложения, MailHog и volumes сохранены. Образы 0.5.0 и исходный
release-пакет не изменены. Backup прежнего proxy config и container IDs:
`/opt/lastochka/backups/mailhog-websocket-20261023T103150Z/`.

Через действующий пользовательский SSH-туннель на 18027 браузер показал Connected;
диагностическое письмо через приватный SMTP появилось автоматически без refresh.
WebSocket получил событие без socket errors. Одно письмо «Проверка MailHog —
соединение восстановлено» оставлено пользователю. UI по-прежнему привязан только
к loopback, внешняя доставка не включалась. Материалы проверки:
`artifacts/server-deploy/0.5.0/mailhog-websocket/`.
