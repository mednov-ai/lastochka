# Публичный лендинг и добровольный WebAuthn — релиз 0.3.0

19.10.2026 на <https://play-and-say.ru/lastochka/> развёрнуты отдельные frontend
и backend **0.3.0**. Лендинг, assets и опубликованное расписание доступны гостю.
Общий Basic Auth снят; кнопка «Войти» открывает модальное окно входа/регистрации.
Этот отчёт заменяет прежние инструкции доступа из [поставки 0.2.0](2026-10-19-preview.md).

## Поведение

- Подтверждённый email и пароль дают FULL для PARENT, ADMIN и ADMIN+DOCTOR.
  Ключи WebAuthn добровольны, парольный вход не требует их привязки или проверки.
  Парольная сессия не получает фиктивный FACTOR_WEBAUTHN.
- Модальное окно сохраняет фон/прокрутку, ограничивает фокус и взаимодействие
  диалогом, закрывается Esc/крестиком и возвращает фокус инициатору. В нём можно
  переключаться между входом, регистрацией и запросом восстановления пароля.
- Прямые auth-адреса и ссылки из писем работают; формы используют общий компонент
  и типизированный API. Выбранное занятие сохраняется при входе, места проверяются
  повторно. Заявка не отправляется автоматически без выбора ребёнка и действия родителя.
- После входа в «Безопасности» можно добавить ключ и добровольно проверить WebAuthn.
  Его отмена/недоступность не закрывает парольный доступ. Недавний парольный вход
  (5 минут) нужен для управления ключами; отзыв последнего пока запрещён.
- Подтверждение email, серверные роли/владение, CSRF, Secure/HttpOnly cookie,
  отзыв сессий при reset и сохранение passkey остаются включены. MailHog приватен,
  реальная доставка RuSender не подключалась.

Сохранены все семь тестовых аккаунтов: два ADMIN, один ADMIN+DOCTOR, четыре PARENT.
Пароль не менялся: локальный игнорируемый `info/password.txt` (600), логины и
инструкция — `info/test-accounts.md`. Общий браузерный логин `lastochka` больше
не нужен. Аккаунты не пересоздавались, bootstrap набора не запускался.

## Проверки

- **23 backend integration tests**, 0 failures/errors, отдельная Testcontainers БД:
  вход по паролю всех семи ролей, отсутствие фиктивного WebAuthn-фактора,
  неподтверждённый email/неверный пароль, CSRF и прежние сценарии записи/outbox.
- **12 целевых browser-сценариев** прошли после исправлений: модальное окно на
  375/1440 px, focus trap/возврат фокуса/скролла, регистрация и подтверждение,
  парольный вход без passkey, безопасный return URL и возврат к занятию,
  семьи/админка, восстановление с сохранением ключей, backend restart,
  добровольная привязка в двух парольных сессиях, отмена/неподдерживаемый WebAuthn,
  отклонение неверных origin/RP/signature/type/UV/replay.
- Первоначальная проверка выявила потерю фокуса при смене формы — исправлено.
  Старые ожидания обязательного WebAuthn в тестах приведены к новым требованиям.
  Prefix redirect проверяется отдельно в proxy на сервере, поскольку Vite dev
  не является production proxy.
- Frontend typecheck, production build и проверка Prettier прошли. OpenAPI повторно
  экспортирован без изменений; повторная генерация TypeScript не дала расхождений.
- Образы Linux/amd64 собраны локально. На сервере проверены SHA256 archive/manifest,
  image IDs и архитектура. SHA256 application-images.tar.gz:
  `5ed5d77a8ff318f646fd6232f82bba75e582770c3030949d42852ff4146c5312`.
- На публичном HTTPS прошла отдельная приёмка в новых browser contexts **без
  Authorization и Basic credentials**: лендинг 200, модальное окно 375/1440,
  парольный вход без ключей, приватные API гостю закрыты, все семь реальных
  тестовых аккаунтов входят с прежним паролем; admin API разрешены только ADMIN.
  Отдельный временный ADMIN добавил и криптографически проверил WebAuthn;
  отмена добровольной проверки сохранила парольный доступ. Временный PARENT
  работал без аутентификатора. Подтверждение email доставлено через MailHog.
- Серверный сценарий: PENDING с удержанием места, 409 при занятом последнем месте,
  одобрение → перенос → отмена, запрет admin API родителю, API JSON 404,
  cookie Secure/HttpOnly/Path=/lastochka, приватные данные отсутствуют в SSR.
  Админка после загрузки проверена на 375/1440 px; скриншот модального окна просмотрен.
- `/lastochka?probe=1` → 308 `/lastochka/?probe=1`. Корневой Play&Say и RepairDevice
  отвечают 200 с прежними SHA256 HTML. Валидный TLS 1.2 работает, TLS 1.3 отклонён
  согласно прежней политике хоста; certbot.timer активен. Служебные health/OpenAPI
  не опубликованы через frontend proxy; сервисные порты недоступны снаружи.
- Backend/frontend/PostgreSQL healthy, остальные сервисы работают. Во время снимка
  Lastochka занимала около 414 MiB суммарно, доступно около 665 MiB RAM на хосте.
  Это наблюдение после запуска, не нагрузочный тест.

Временные аккаунты приёмки, их ключ/сессии, дети, занятия, записи, audit/idempotency,

## Поставка, сохранность и откат

Рабочий release: `/opt/lastochka/releases/0.3.0/`, env по-прежнему
`/opt/lastochka/shared/.env.preview` (600). Инфраструктурные volumes/сети сохранились,
новых миграций БД в 0.3.0 нет. На сервере остановлен только собственный backend,
последовательно создан отдельный временный ADMIN, затем запущены новый backend,
frontend и пересоздан свой proxy для обновления upstream. Секретный файл
acceptance.env после bootstrap удалён. Исходники и инструменты сборки не передавались.

Общий vhost не изменялся: заменён только `/etc/nginx/snippets/lastochka-preview.conf`,
Basic Auth выключен директивой auth_basic off. Перед изменением сверены исходные
конфигурации с backup, перед reload выполнен nginx -t; исходные TLS/ACME и другие
маршруты сохранены. Старый htpasswd больше не используется.

Резервные копии до обновления (режим каталога 700):
`/opt/lastochka/backups/pre-0.3.0-20261019/` — текущие vhost/snippet/env и database.dump.
После очистки приёмки создан
`/opt/lastochka/backups/lastochka/ready-for-testing-0.3.0-20261019.dump` (600).

При необходимости отката вернуть теги обоих образов 0.2.0 в защищённой env,
пересоздать только backend/frontend, дождаться health и пересоздать свой proxy.
Восстановить только Lastochka snippet из pre-0.3.0 backup, проверить nginx -t
и reload; не заменять целиком общий vhost с возможными чужими новыми изменениями.
Откат возвращает прежние Basic Auth и обязательный WebAuthn, что нужно явно
сообщить тестировщику. Восстанавливать старую БД для отката бинарника не требуется;
не удалять volumes и не сбрасывать появившиеся пользовательские данные.
