## Доступ тестировщика

Первый браузерный запрос — Basic Auth, имя пользователя `lastochka`.
Его пароль совпадает с общим паролем семи тестовых аккаунтов и сохранён только
в игнорируемом `info/password.txt` с правами 600. Список логинов и инструкция —
`info/test-accounts.md` (также 600 и вне Git).

- `admin1@lastochka.test`, `admin2@lastochka.test` — ADMIN.
- `doctor1@lastochka.test` — ADMIN + DOCTOR.
- `client1@lastochka.test` … `client4@lastochka.test` — PARENT.

DOCTOR — дополнительная роль совмещённого администратора. Отдельных медицинских
операций и анкет версия не добавляет. Email этих синтетических аккаунтов уже
подтверждён. При первом входе после пароля тестировщик создаёт собственный passkey,
затем отдельно проходит WebAuthn. Привязка ключа сама по себе не завершает вход.
Рекомендуется добавить запасной ключ через «Безопасность»: сброс пароля не
восстанавливает утраченные passkey.

После очистки проверочных данных: **7 аккаунтов, 0 credentials, 0 детей,
0 занятий, 0 записей**. Родители добавляют детей, администраторы — занятия.
Этот снимок относится к моменту передачи среды: будущие данные тестировщика

## Что изменено на общем сервере

- Установлены Ubuntu `docker.io 29.1.3`, `docker-compose-v2 2.40.3`, containerd/runc;
  существующие пакеты не обновлялись и не удалялись. Docker включён в автозапуск.
- Создан отдельный Compose project `lastochka-preview`, собственная PostgreSQL 17.6,
  MailHog v1.0.1, volumes и сети. Существующая host PostgreSQL не использовалась.
- Backend `lastochka-backend:0.2.0` и frontend `lastochka-frontend:0.2.0` загружены
  из проверенного archive. Его SHA256:
  `fd82001726e52185d90132af264d9b9a82178dac5aef7c0497dfeca361c7c3ba`.
  Полный локальный manifest/image metadata: `artifacts/release-0.2.0/`.
- Рабочая директория — `/opt/lastochka/releases/0.2.0/`, секретная конфигурация —
  `/opt/lastochka/shared/.env.preview` (600), пароль БД отдельный случайный.
  Bootstrap-файлы с паролями удалены с сервера после одноразовых запусков.
- Backend bootstrap и основная JVM запускались последовательно. Основная JVM
  ограничена 768 MiB, frontend 256 MiB, PostgreSQL 256 MiB; логи ограничены.
  После запуска Lastochka потребляла около 519 MiB суммарно, на хосте доступно
  около 653 MiB из 1967 MiB, swap отсутствует. Нагрузочная приёмка не проводилась.
- Наружу приложения не открыты: Lastochka proxy только `127.0.0.1:18080`, MailHog
  access только `127.0.0.1:18026`. SMTP находится в закрытой internal-сети без
  внешней доставки. Backend/Node/PostgreSQL host-портов не имеют.
- В существующий HTTPS vhost добавлена одна строка
  `include /etc/nginx/snippets/lastochka-preview.conf;`.
  Snippet содержит только Lastochka locations, Basic Auth и proxy на loopback.
  Общий Basic Authorization не передаётся приложению.
  Сохранены root proxy, RepairDevice, TLS 1.2 и ACME; `certbot.timer` активен.
  До замены проверена кандидатная конфигурация, затем реальная; reload успешен.

  отказ при конфликте и вне preview; ранее существующие сценарии также прошли.

- TLS 1.2 с валидным сертификатом работает; TLS 1.3 отклоняется в соответствии

- `/` и `/repair_demo/` возвращают 200; SHA256 HTML полностью совпали со снимком
  до поставки. Nginx syntax check успешен. Все Lastochka services работают,
  backend/frontend/PostgreSQL health исправен.
- На реальном публичном URL пройден браузерный вход паролем и нативным WebAuthn
  с временным виртуальным аутентификатором, без обхода проверок подписи/origin/RP.
  До второго фактора доступ к детям запрещён. MailHog принял регистрационное письмо

## Backup и откат

Исходный vhost, слушатели, services, эффективная конфигурация Nginx, сетевые правила
и журнал установки Docker: `/opt/lastochka/backups/pre-deploy-20261019/` (700).
Готовая база после удаления временных аккаунтов:
`/opt/lastochka/backups/lastochka/ready-for-testing-20261019.dump` (600, pg_dump -Fc).
Более ранний initial-test-accounts dump содержит временного администратора приёмки;
для чистой передачи использовать именно ready-for-testing. Перед будущими
миграциями отдельно копировать env, БД и maildir по основному runbook.

Для отключения preview удалить **только** Lastochka include из текущего vhost,
проверить `nginx -t` и выполнить reload. Восстанавливать весь исходный vhost из
backup допустимо только если с момента поставки в нём не появилось других изменений.
Затем остановить только свой проект без удаления volumes:

```sh
cd /opt/lastochka/releases/0.2.0
docker compose --env-file /opt/lastochka/shared/.env.preview -f compose.preview.yaml stop
```

Не останавливать общие Nginx/PostgreSQL/RepairDevice, не применять `down -v`,
не удалять Docker/его сети при откате приложения. Независимый откат образов и
перенос описаны в [основном runbook](README.md).
