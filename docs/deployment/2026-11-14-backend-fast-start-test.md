# Ускорение старта backend: проверка и выпуск на test, 14.11.2026

## Результат

На test установлен только backend `0.23.2-fast-start-test-20261114` (`sha256:c3d90d074f60ae15b22eb3a7f30072b20725e6a7def058752ddf0d0a4ac1542a`). Frontend остаётся `0.23.1-schedule-index-test-20261114`, схема — V30. Production не выпускался.

Приложение при сборке распаковывается штатным Spring Boot jarmode и запускается из распакованного каталога. JVM-флаги, сборщик мусора, ограничения ресурсов и само приложение не изменены. Это ускорение упаковки и загрузки классов, а не настройка AOT Cache. [Основной Dockerfile](../../infra/backend/Dockerfile) обновлён, чтобы обычные последующие сборки сохраняли способ запуска.

Исходный установленный test-образ `0.23.1-schedule-index-test-20261114` (`sha256:6368c65697ebc3af8a5250a52bcf688b1aea566865e93f04221e949170e05281`) содержал код с ревизии `develop` `8ebd047f08ceecb0ae7a629dbf5ddb659be6ea44` и ранее зафиксированные незакоммиченные изменения заявки и расписания. Выпущенный образ получен от этого точного образа через [записанный Dockerfile](../performance/jvm-startup-2026-11-14/Dockerfile.test-derivation.txt). Сверены 48 классов и ресурсов приложения и 125 runtime-библиотек; все совпали. Утилита `spring-boot-jarmode-tools`, нужная для распаковки, штатно не входит в распакованный runtime. Настройки образа совпадают с исходными, кроме версии и команды запуска. Проверка release-контракта пройдена. Сжатый архив test-образа занял около 325 MiB против 253 MiB у прежнего: в образе сохранены исходный JAR и распакованные библиотеки; это расход диска, а не замер оперативной памяти.

Отдельно собран образ основным Dockerfile, в том числе повторная сборка на основе уже распакованного образа. Его 126 файлов распакованного приложения и существенные настройки образа совпали с тестовым кандидатом побайтно; это проверка эквивалентности, не утверждение о совпадении image ID.

## Локальное сравнение

Использован установленный test backend и полностью отдельный контейнер PostgreSQL с **синтетической** базой, временным хранилищем и закрытой внутренней сетью. Flyway и фоновые действия отключены. Каждый запуск — новый контейнер, лимиты 1 CPU / 480 MiB и `MaxRAMPercentage=32.5`, как у test для памяти JVM. Измерялся интервал от команды запуска контейнера до первого успешного readiness с доступной БД, а также сообщение Spring о старте. Проверены ответы API возрастных направлений и расписания. На Mac ARM исполнялся образ `linux/amd64` через эмуляцию; полученные цифры не являются прогнозом для VPS. Две серии выполнялись в обратном порядке; выборка мала.

| Вариант | Готовность, секунды | Spring, секунды |
| --- | --- | --- |
| Исходный JAR, Serial GC | 40,188; 38,487 | 36,098; 34,648 |
| Распакованный JAR, Serial GC | 33,794; 32,072 | 30,338; 29,607 |
| Распакованный JAR, G1 без AOT | 37,978; 37,727 | 35,058; 34,152 |
| Распакованный JAR, G1 + JVM AOT Cache | 30,995; 31,154 | 27,890; 28,305 |

Медиана готовности исходного и распакованного образов составила 39,34 и 32,93 с соответственно. Дополнительный локальный запуск именно выпускаемого образа дошёл до готовности за 31,74 с, API расписания и направлений вернули HTTP 200. Синтетические контейнер и сеть после опыта удалены; пользовательские БД и тома не затрагивались.

JVM на данном локальном лимите выбирает `UseSerialGC`. AOT-кеш, обученный с heap 156 MiB, при Serial GC не загрузился с ошибкой загрузки архивированных объектов; при принудительном G1 загрузился и был использован. Подготовленный кеш занимал 169 988 096 байт; первая попытка подготовки с лимитом 480 MiB не завершилась, причина завершения не установлена, последующая подготовка с увеличенным лимитом памяти и heap 156 MiB прошла. С учётом малого дополнительного выигрыша относительно распаковки и необходимости менять GC и сборку, AOT Cache на test не включён.

## Замеры на test и контроль выпуска

Одинаковые настройки Docker Compose, JVM и базы. Непосредственно перед переключением существующий backend перезапущен один раз и измерен; затем тем же способом запущен новый. `healthy` фиксировался по Docker healthcheck, который выполняется раз в 10 секунд и дополнительно проверяет подключение к БД. Это один последовательный запуск каждой версии; серверная нагрузка и попадание на интервал healthcheck влияют на результат.

| Показатель | До | После | Разница |
| --- | ---: | ---: | ---: |
| Сообщение Spring о завершении старта | 71,467 с | 60,091 с | −11,376 с, −15,9% |
| Время процесса по журналу Spring | 74,757 с | 61,711 с | −13,046 с, −17,5% |
| До фиксации Docker `healthy` | 83,195 с | 73,369 с | −9,826 с, −11,8% |

При предыдущей выкладке исходный backend сообщал о старте за 56,757 с; различие с повторным контрольным запуском показывает, что результат зависит от условий и не является гарантией ускорения каждого запуска. Память нового контейнера после проверки — 407,6 MiB из 480 MiB по `docker stats`; сопоставимый замер памяти прежнего контейнера в этой серии не проводился.

Test PostgreSQL, frontend, proxy, gate и alfa-proxy не пересоздавались; backend сохранил прежний IP. Compose-конфигурация сравнивалась с предыдущей и отличалась только образом backend. Runtime Flyway и фоновые уведомления оставались выключены. Миграций и намеренных изменений данных не выполнялось; новую копию БД для замены образа не создавали. Роль только для чтения видит 43 занятия, как после предыдущего выпуска; этот подсчёт не заменяет полную сверку данных.

На test проверены HTTP 200 публичного API: пять возрастных направлений и 14 занятий на 16–22 ноября. В мобильном WebKit через `playwright-cli` проверены переключение недели, шесть дней с занятиями и отсутствие ошибок консоли; автоматизированный контекст не принимал согласие за посетителя. Оба test-сервиса healthy; TLS 1.2 работает, TLS 1.3 отклонён. Реальные заявки, банковые операции, ADMIN-сессия, физические устройства, нагрузка и фактический откат не проверялись.

Для возврата оператор может восстановить прежние test env/manifest и пересоздать только test-backend из сохранённого прежнего образа; схема V30 совместима с ним. Предыдущие конфигурация и метаданные замера сохранены на сервере в `/opt/lastochka/releases/fast-start-test-20261114-v1/`. Автоматическое восстановление прежнего test backend предусмотрено при ошибке во время переключения; оно не потребовалось.
