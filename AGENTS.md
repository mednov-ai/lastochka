## Язык пользовательского интерфейса

- Все собственные пользовательские тексты писать по-русски: страницы, кнопки,
  пояснения, placeholder, title, aria-label, ошибки, уведомления, загрузка,
  пустые состояния и публичный просмотр тестовой почты. Обязательные сообщения
  проверки форм при работающем JS не должны зависеть от языка браузера.
- Использовать понятные слова вместо технического жаргона. Начальные замены:
  `Email` → «Электронная почта», `passkey` → «ключ доступа»,
  `preview` → «предпросмотр», `валидация` → «проверка данных»,
  `аутентификация` → «вход». Вместо «токен» описывать нужное пользователю
  действие: «код подтверждения», «ссылка подтверждения» или «ссылка восстановления»
  в зависимости от смысла. Внутренние идентификаторы и документы под это правило не подпадают.
- Названия продуктов и необходимые протоколы допустимы по явному списку
  исключений с обоснованием и областью применения. Пользовательские данные,
  адреса почты, URL, имена полей/коды API не переводить. Исключение для названия
  не разрешает английское предложение вокруг него.
- Повторяемые инструкции и сообщения брать из общего русского каталога;
  backend сохраняет собственный messages.properties. Не выводить пользователю
  сырой текст исключений или технические коды вместо понятного сообщения.
- Для изменений интерфейса обязательны проверка текстов и терминологии,
  браузерные сценарии en-US/ru-RU для затронутых форм и состояний отказа,
  проверка доступных подписей и мобильной читаемости. Автоматическая проверка,
  реализованная в localize-user-hints-in-russian (`npm --prefix frontend run check:ui-language`),
  останавливает штатную сборку/CI при непредусмотренном английском тексте или
  запрещённом термине. Ручная проверка смысла и динамических сообщений остаётся обязательной.
- Приёмка включает смысловую проверку текста: отсутствие латиницы не доказывает
  понятность. Общий запрет латинских символов и широкие исключения на целые каталоги
  не заменяют классификацию именно пользовательских строк.

## Прежняя поставленная модель (история до смены концепции)

Актуальное направление и локальная реализация описаны в начале этого файла и активном
изменении refocus. Следующие требования относятся к поставленной V9 и её истории.

Единое приложение для студии «Ласточка»: публичный лендинг, кабинет клиента
с записью на доступное время и кабинет администратора для управления расписанием
и записями посетителей.

- Визуальная основа — первый макет, «01 Воздух»:
  <https://lastochka-designs.sappyjam9.chatgpt.site/#concept=air>.
- Frontend: React 19 и TypeScript. Лендинг является частью общего продукта.
- Лендинг, запись, кабинет родителя и админка — одно frontend-приложение
  с общей сборкой, маршрутизацией и API-клиентом.
- Backend: Kotlin и Spring Boot 4; перед стартом реализации сверить стабильную
  версию и совместимость зависимостей.
- Java 25 для сборки и запуска backend. База данных — PostgreSQL.
- Сборка выполняется локально; frontend и backend развёртываются отдельно
  для будущего перехода к Kubernetes. Frontend в backend JAR не включается.
  В плане выбраны два независимо версионируемых образа и Docker Compose на первом
  небольшом сервере; Kubernetes и его манифесты остаются следующим этапом.
  PostgreSQL и конфигурация находятся снаружи; на сервере запускаются готовые
  образы без сборки. Java 25 и Node.js runtime входят каждый в свой образ.
- Временный сервер задан пользователем: `139.100.236.101`; публичный URL —
  `https://play-and-say.ru/lastochka/`. Затем предусмотрен перенос на рабочий сервер.
  Тестовая поставка 0.3.0 выполнена; перенос на рабочий сервер остаётся будущим этапом.
  Base path `/lastochka` учитывается маршрутизатором, assets, API, SSR, redirect
  и почтовыми ссылками. Основные маршруты Play&Say остаются у существующего сайта.
- Backend делится на внутренние модули в одном процессе; расписание и платежи
  имеют отдельные модули. Платёжные операции и провайдер остаются будущим этапом.
- Наполнение лендинга отделяется от React-компонентов и предусматривает будущую
  панель редактирования. Сам редактор в текущую версию не входит.
- `openspec/` отслеживается Git. `/info/` и локальные результаты сборок исключаются
  через `.gitignore`; исходные материалы локально сохраняются.
- DTO и эндпойнты фронта должны следовать OpenAPI backend. Не поддерживать
  параллельные вручную написанные версии транспортных DTO на двух сторонах.
- Клиент — родитель: регистрируется по email, добавляет одного или нескольких
  детей и записывает их на индивидуальные занятия или в мини-группы.
- Первая версия поддерживает запись на отдельные занятия. Запись на серию
  занятий не входит в выбранный сценарий первого запуска.
- Администратор задаёт доступное время и управляет переносами.
- Каждая заявка требует одобрения администратора. Первая версия рассчитана
  на одного тренера и один зал.
- Администраторов может быть несколько, у каждого отдельный аккаунт и добровольный WebAuthn.
  Количество администраторов не ограничивается числом тренеров или залов.
- Последнее уточнение пользователя отменяет обязательность WebAuthn для всех
  ролей: подтверждённый email и пароль дают полноценный вход PARENT/ADMIN, включая
  ADMIN+DOCTOR. WebAuthn доброволен, наличие/утрата ключей не блокируют парольный вход.
  Существующие passkey сохраняются; email-ссылка сама по себе не выполняет вход.
- Лендинг, его ресурсы и публичное расписание доступны без общего Basic Auth.
  Кнопка «Войти» открывает модальное окно входа/регистрации, сохраняя фон/прокрутку;
  прямые auth-адреса, подтверждение email и восстановление остаются доступны.
  Подтверждение email и восстановление пароля через email сохраняются.
  Самостоятельные аккаунты детей не нужны.
- Решение 23.10.2026: новый пароль — 6–128 Unicode code points, хотя бы одна
  буква L и цифра Nd. Пробелы/символы разрешены; без trim/normalize. Одинаковая
  проверка frontend/DTO/сервисов register/reset/createAdmin/новых fixtures.
  Старые пароли продолжают работать без нового состава/минимума. VERIFY при
  открытии полной ссылки выполняется автоматически через CSRF POST; повтор
  нейтрален до исходного expiry, ссылка не создаёт новую парольную сессию.
  RESET и «Приду» остаются явными действиями. Публичные ошибки backend хранятся
  в messages.properties и проходят общую фабрику advice/Security. Общая плашка

## Архитектура реализованной локальной MVP

Ниже зафиксировано направление OpenSpec, реализованное и проверенное локально.
Проверки и ограничения описаны в docs/verification.md; серверный production-релиз
не выполнялся. Открытые параметры не становятся подтверждёнными требованиями.

- Один репозиторий с `frontend/`, `backend/` и общими API-артефактами.
- В proposal выбран Gradle multi-project backend: app, identity, customers,
  scheduling, bookings, notifications, content, payments. Только app собирает
  запускаемый bootJar, остальные — внутренние library-модули. Scheduling и
  payments имеют явные границы; модуль payments пока без операций/провайдера.
- В proposal выбраны PostgreSQL 17, Flyway, Spring MVC, Spring Data JPA и Java 25.
  Чистая сборка, миграции и тесты на отдельной PostgreSQL проверены.
- Один origin для браузера и API, Spring Security, серверная сессия с защищённой
  HttpOnly cookie и CSRF-защитой. Аутентификация — подтверждённый email/пароль,
  WebAuthn доброволен. Неподтверждённый email не получает доступ к данным PARENT/ADMIN.
- Для временного preview origin — `https://play-and-say.ru`, WebAuthn RP ID —
  `play-and-say.ru` без пути. Cookie Lastochka имеет отдельное имя и Path `/lastochka`,
  не переиспользует сессию Play&Say. При смене только сервера доменная привязка
  passkey сохраняется; новый несовместимый домен требует отдельного enrollment-плана.
- Для email: отдельный адаптер RuSender при подключении реальной доставки,
  SMTP-адаптер MailHog в тестовом MVP, сохранённая очередь событий/outbox,
  повторные попытки и учёт результата доставки. Изменение записи сохранять
  транзакционно; письмо отправлять после commit. Ошибка доставки не отменяет запись.
  Не обещать SMTP exactly-once: при неоднозначном результате допустим повторный
  захват с тем же Message-ID, без повторного бизнес-действия.
- Для единого frontend выбраны Vite и React Router framework mode с отдельным
  Node.js SSR runtime. Frontend формирует HTML главной и гидратирует React по
  опубликованному LandingContent из backend API; JVM-шаблон frontend не используется.
  HTML не содержит данных семей. Через прокси страницы/assets идут во frontend,
  `/lastochka/api/**` — в backend под одним публичным origin для cookie/CSRF/WebAuthn.
  Backend context path — `/lastochka`, логические контроллеры — `/api/v1`.
  Публичная база/подпуть и внутренние upstream задаются настройками; смена asset base
  может потребовать новую frontend-сборку с конфигурацией, без правки исходного кода.
- Наполнение хранится как версионированный опубликованный документ в PostgreSQL,
  доступный через типизированный API. Начальный seed не перезаписывает его
  при обновлении любого сервиса. Будущий редактор меняет наполнение без пересборки.
- Независимые релизы требуют совместимости API: новый backend поддерживает
  предыдущий frontend на окно rollout; затем выпускается совместимый frontend.
  Версии, health-проверки и откат раздельные. Контейнеры не хранят пользовательское
  состояние; сессии/credentials/outbox находятся в PostgreSQL.

### Связь frontend и backend

Предлагаемая цепочка:

`Kotlin controllers + DTO → OpenAPI → TypeScript types → typed API client → React`

- Сохранять воспроизводимый OpenAPI-артефакт из backend, затем генерировать
  frontend-типы и использовать типизированные операции/пути.
- Кандидат: `openapi-typescript` + `openapi-fetch`:
  <https://openapi-ts.dev/introduction>, <https://openapi-ts.dev/openapi-fetch/>.
- CI должен проверять экспорт актуального контракта, повторную генерацию без
  расхождений и сборку frontend с проверкой типов. Swagger UI сам по себе
  не гарантирует согласованность клиента и сервера.
- Разделять транспортные DTO, внутренние сущности backend и состояние UI.
  Не отдавать JPA-сущности напрямую. Не редактировать генерируемые файлы вручную.
- Определить в контракте обязательность и nullable-поля, статусы, время,
  единый формат ошибок, авторизацию и ответы на конфликт бронирования.

### Модель расписания и записи

Подтверждённая предметная модель: родитель, дети и записи на отдельные занятия.
Предлагаемые названия сущностей: `ParentAccount → Child → Booking → Session`.

- Аккаунт родителя содержит одну или несколько карточек детей. Родитель
  управляет записями своих детей; самостоятельную регистрацию детей не вводить.
- `Session` — конкретное занятие с временем, форматом, тренером и вместимостью.
  `Booking` — запись одного ребёнка на это занятие. Для индивидуального занятия
  вместимость 1, для группы задаётся администратором.
- Если администратору понадобятся шаблоны повторения, отделять их от конкретных
  занятий по датам. Родитель в первой версии записывается на каждое занятие
  отдельно; шаблон расписания не означает автоматическую запись на серию.
- Backend — источник истины для свободных мест. Создание записи проверяет
  вместимость в транзакции и защищает от одновременного занятия последнего места,
  повторной отправки и повторной активной записи ребёнка на то же занятие.
- Различать перенос занятия со всеми участниками и перенос одной записи
  на другое занятие. Проверять пересечения у тренера и ребёнка, вместимость
  и актуальную версию данных. При неудачном переносе сохранять исходную запись.
- Закрытие доступного времени с существующими записями требует явного сценария
  отмены/переноса, а не молчаливого удаления участников.
- Хранить моменты времени в UTC, расписание студии показывать в `Europe/Moscow`.
  Повторения строить по локальной зоне студии, не по зоне браузера.
- Изменения администратора сохранять с историей автора, времени и причины.
- Не собирать диагнозы и медицинские анкеты как часть обычной записи.

## Предлагаемая первая версия

Согласованный пользователем объём включает лендинг, кабинет клиента, запись,
свободное время и управление администратора. Детализация ниже — предложение:

1. Лендинг на основе «Воздуха» с переходом к реальному расписанию.
2. Регистрация с email и паролем, подтверждение email, полноценный парольный вход,
   добровольная привязка/проверка passkey, восстановление пароля.
3. Карточки детей, доступные отдельные занятия, создание записи ребёнка,
   список записей своих детей.
4. Управление администратора: календарь, создание/публикация/закрытие занятий,
   участники, вместимость, запись клиента вручную, переносы и отмены.
5. Email о записи, переносе и отмене; правила напоминаний уточнить.
6. Синхронизация OpenAPI и frontend в CI, проверки прав доступа и конкурентной записи.

Запись на серию отложена за пределы первой версии. Абонементы, онлайн-платежи,
возвраты, лист ожидания, отдельный кабинет тренера,
массовые рассылки и медицинское направление не согласованы для первого запуска.
Платёж и запись в дальнейшем должны иметь отдельные состояния. Не копировать
Play&Say вслепую: сначала сверить его актуальную реализацию и требования студии.

## Открытые решения

- Детализация предложена в `create-lastochka-booking-mvp`: ожидающие заявки
  удерживают место; отмены и переносы выполняет администратор; запись закрывается
  с началом занятия. Это проектные правила proposal, а не отдельные ответы
  пользователя. Напоминания, учёт посещения и серии исключены из этого изменения.
- Сброс пароля отзывает сессии и сохраняет passkey. Поддерживаются несколько
  ключей, отзыв последнего пока запрещён; утрата ключей не блокирует вход
  с паролем. Управление ключами требует недавнего парольного входа (5 минут).
- Конкретные длительности и интервалы между занятиями задаются расписанием.
- Адрес студии, цены, расписание, повторная преддеплойная проверка ресурсов/proxy,
  адрес и окончательный публичный домен будущего рабочего окружения.
  RuSender уже выбран; его API-токен, активный ключ отправки и верифицированный
  домен/адрес понадобятся при отдельном подключении реальной доставки.

Не превращать рекомендации и неизвестные параметры в подтверждённые требования.

Отчёт локального этапа: `docs/backend-refactoring.md`. Последующая разрешённая
поставка backend 0.7.0 описана в `docs/deployment/2026-10-23-backend-refactoring.md`.
OpenSpec архивирован 23.10.2026; tag `backend-refactoring-local` относится к локальным проверкам.

Обязательные правила новых backend-правок:

- Запрос целиком (SQL/JPQL/фрагменты, binding, mapping строк и DB API) — только
  в `repo` владельца. Контроллер обращается к сервису; сервис — к repo/контракту
  другого владельца. Чужие repo/entities и обратные зависимости common запрещены.
  Миграции и test fixtures остаются в своих каталогах.
- Для нового и изменяемого собственного production-доступа к БД использовать
  Spring Data JPA: готовые CRUD-операции и составные методы репозитория по именам,
  для более сложных запросов — JPQL и проекции. Нативный SQL через `@Query` с
  `nativeQuery = true` допустим, когда он нужен для возможностей PostgreSQL или
  сохранения семантики и это обосновано рядом с запросом. Не добавлять новые
  собственные запросы через `JdbcClient`, `JdbcTemplate` или другие низкоуровневые
  JDBC API; существующие вызовы — техдолг для отдельного поэтапного перевода.
  Правило не требует переписывать JDBC внутри Spring Session/Security и не относится
  к миграциям или тестовым fixtures. При переводе сохранять транзакции, порядок
  блокировок, атомарность, совместимость схемы и контракт; проверять поведение и
  запросы на PostgreSQL, включая конкуренцию и отсутствие N+1 там, где это важно.
- Общая часть — `backend/common`, пакет `ru.lastochka.common`. Исключение для
  корня этого пакета — `Metadata.kt`, остальные типы находятся в intentional
  subpackages. Корень приложения `ru.lastochka` содержит только launcher.
- Смысловые литералы и правила — сгруппированные значения Metadata, включая
  однократный новый код/статус/лимит. У чисел указывать единицы. Не объединять
  разные правила из-за одинакового значения. SQL остаётся в repo; пользовательские
  ошибки — messages.properties, результаты/письма — user-messages.properties.
  Рабочие секреты/URL/generation остаются конфигурацией, не константами.
- Один global advice в common/error покрывает все контроллеры; Security использует
  ту же фабрику. Общая обработка не импортирует domain DTO/config/политику пароля.
  Фоновые повторы/lease обслуживаются workers, а не MVC advice.
- Только нейтральные DTO/технические контракты переносить в common. AccountProfile,
  SessionView, BookingView и предметные события остаются у владельцев. Не вводить
  BaseService/универсальный DAO или интерфейс/impl без необходимости.
- Имена отражают действие/предмет, простые if/when и именованные аргументы
  предпочтительнее вложенных цепочек. Удаление/объединение требует проверки usages
  и инвариантов; сокращение LOC само по себе не доказывает улучшение.
- `backend/gradlew -p backend architectureCheck` обязателен в check/bootJar и
  штатной упаковке. Тесты анализатора: `backend/gradlew -p backend/buildSrc test`.
  Не добавлять blanket allowlist/baseline нарушений. Production Java требует
  отдельного расширения контроля; buildSrc — build tooling, а не runtime-код.
- При переносе запросов сохранять транзакционные границы/порядок блокировок/flush,
  idempotency/audit, V9-совместимость, поля/имена OpenAPI и независимость поставок.
