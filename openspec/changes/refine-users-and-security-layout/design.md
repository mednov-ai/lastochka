## Context

См. `proposal.md`. Список в `users.tsx` использует общие карточки, а `security.tsx` выводит общую форму смены пароля перед сеткой ключей. Форма также используется при обязательной смене; общие стили участвуют в других разделах. Существующие правила сессии, недавнего подтверждения и passkey описаны в основных спецификациях.

## Goals / Non-Goals

**Goals:**
- Получить спокойный, согласованный интерфейс в существующей визуальной системе, с проверяемой компактностью и понятной иерархией.
- Ограничить изменения соответствующими страницами и сохранить действующие состояния форм.

**Non-Goals:**
- Новые полномочия, удаление пользователей, изменение политики паролей, ключей, API или БД.
- Гарантия отсутствия прокрутки на любом экране, при увеличении текста и произвольном числе записей.
- Поставка на сервер в рамках этого предложения.

## Decisions

1. **Пользователи — компактные строки с адаптивной компоновкой.** Имя и логин с ролью образуют идентификационный блок, статус и действие расположены в согласованных областях; заголовок имени меньше нынешнего, текст остаётся читаемым. На узком экране области переносятся под идентификацию, длинные значения переносятся без обрезания. Противоположная альтернатива — плотная таблица с обязательными фиксированными колонками — хуже выдерживает узкий экран и длинный текст. Геометрию обычной строки ограничивает спецификация; размер цели действия не менее 44 CSS px.
2. **Безопасность — две равноправные смысловые панели на достаточной ширине.** Смена пароля слева, ключи справа, включая их список и относящееся к ключам подтверждение/проверку. Пояснения и сообщения размещаются рядом с соответствующей операцией, не теряя видимости. На узком экране порядок: пароль, ключи. Альтернатива скрыть ключи в сворачиваемом блоке не выбрана: управление и требования подтверждения должны быть очевидны. Контент и ошибки могут увеличивать высоту; отсутствия вертикальной прокрутки при маленьком окне не обещаем.
3. **Локальные классы, не глобальное уменьшение.** Использовать отдельные классы страниц и при необходимости явные варианты общей формы; не менять размеры всех `form-card`/`list-card` сайта. Удалить ссылку из добровольной формы, сохранив поведение обязательной формы и выход. Общую навигацию кабинета не перестраивать.
4. **Доступность прежде плотности.** Минимум 44 CSS px для интерактивных целей, контраст обычного текста не ниже 4,5:1 и значимых границ/индикаторов 3:1, видимый необрезанный фокус. Не фиксировать высоту форм и не применять обрезание содержимого. Проверить порядок клавиатурного обхода и ошибки, русские подписи, оба браузерных языка ru-RU/en-US.

## Risks / Trade-offs

- [Две колонки становятся тесными при увеличении текста] → переход в одну колонку по доступной ширине и проверка 200%, а не фиксированная ширина содержимого.
- [Общая форма используется ограниченной сессией] → целевой регрессионный сценарий обязательной смены, выхода и показа пароля.
- [Несколько ключей, ошибки и длинные имена увеличивают высоту] → разрешить перенос и рост без скрытия содержимого; проверить реальные состояния и клавиатуру.
- [Глобальные стили повредят другие страницы] → ограничить селекторы и проверить соседние разделы и навигацию.

## Migration Plan

Миграция данных не нужна. Реализация и приёмка локальны; поставка потребует отдельного поручения и штатного плана frontend-only с сохранением совместимого backend и старых ресурсов. Откат при отдельной поставке — на проверенный предыдущий frontend с совместимым backend; данные и сессии не восстанавливаются из старой копии ради изменения оформления.
