## Context

Мотивация — в proposal.md. Сеть `default` в `compose.isolated.yaml` внутренняя, в `edge` входят только прокси и gate. `LASTOCHKA_WORKERS_ENABLED` жёстко равен `false`. На test действует дополнительный `runtime-data/vk-test-20261122/compose.vk-test.yaml`, он не отслеживается Git. Флаг обработчиков включает ВКонтакте и push; обработчик push без VAPID не забирает задания на отправку, но списывает устаревшие.

На test сейчас frontend 0.27.0 с лентой. На момент составления плана её исходники не закоммичены, поэтому сборка из `develop` откатила бы главную.

## Goals / Non-Goals

**Goals:** новая сборка без потери ленты; выход только к `api.vk.com`; воспроизводимая конфигурация; доказанная доставка.

**Non-Goals:** универсальный исходящий прокси, доступ к push-сервисам и банку, изменения production, автоматическая настройка сообщества.

## Decisions

### Ретранслятор TLS по SNI

Отдельный контейнер Nginx со `stream` и `ssl_preread` входит в `default` и `edge`. Во внутренней сети у него alias `api.vk.com`, порт 443 наружу не публикуется. Принимается только SNI `api.vk.com`, остальные соединения закрываются. Адрес назначения разрешает внешний `resolver` из конфигурации: системный DNS Docker вернул бы сам ретранслятор. TLS заканчивается в backend и на серверах ВКонтакте, имя и сертификат проверяет Java.

Подключение backend к `edge` отклонено: оно открывает весь интернет. CONNECT-прокси требует нового образа и параметров JVM. Правила firewall по IP хрупки при смене адресов ВКонтакте. Доступность DNS и наличие модулей `stream` и `ssl_preread` в закреплённом образе проверяются до выпуска. Входящая политика «только TLS 1.2» относится к Nginx сайта и не меняется.

### Отслеживаемое дополнение для test

Настройки ВКонтакте, монтирование ключа, ретранслятор и `LASTOCHKA_WORKERS_ENABLED=true` выносятся в `compose.vk-test.yaml` в корне. Базовый файл остаётся с выключенными обработчиками, production его не наследует. VAPID не задаётся, проверка перед запуском требует пустых значений. До включения фиксируются количество и статусы записей очередей.

### Источник сборки

Сборка идёт из чистого снимка `develop`, в котором есть исправление ВКонтакте и исходники ленты 0.27.0. Если лента не закоммичена её владельцем, выпуск останавливается до решения. Чужие изменения в коммиты этого изменения не включаются. Предлагаемая версия — `0.27.1-vk-delivery-test-<дата>`.

### Порядок включения

Сначала новая сборка с выключенным обработчиком, затем ретранслятор, затем обработчик. Владелец вводит ключ в кабинете; агент ключ не получает. Канал включается после подтверждённого тестового сообщения. Замена контейнеров требует отдельной отмашки владельца и root оператора; обычный `lastochka-agent` только читает.

## Risks / Trade-offs

- Мало памяти: по последнему отчёту доступно около 387 МБ → лимит ретранслятора 32 МБ, проверка памяти до и после.
- DNS или модуль Nginx недоступны → отказ preflight до замены контейнеров.
- Alias перехватывает `api.vk.com` для всех контейнеров внутренней сети test → прокси и gate к этому имени не обращаются, проверяется до выпуска.
- Обработчик push списывает устаревшие записи → снимок очередей до включения; при неожиданных записях остановка.
- Заявка с реальными контактами во время приёмки → используется одна синтетическая заявка; действительные заявки не создаются от имени посетителей.
- Роль чтения агента не видит `vk_enquiry_*` → состояние подтверждает оператор или кабинет, права ради этого не расширяются.

## Migration Plan

1. Сверить источник, выполнить проверки, собрать образы `linux/amd64`.
2. Получить отмашку. Создать резервную копию test и проверить восстановление отдельно. Выполнить preflight.
3. Заменить backend и frontend, сверить версии, данные и неизменность остальных контейнеров.
4. Запустить ретранслятор, проверить разрешённый и запрещённые адреса, включить обработчик.
5. Принять доставку с владельцем, записать отчёт.

Возврат: выключить обработчик и ретранслятор, затем вернуть frontend 0.27.0 и backend 0.26.0; оба совместимы с V34. Восстановление базы не требуется и поверх test не выполняется.
