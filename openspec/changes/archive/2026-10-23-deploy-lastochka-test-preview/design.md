## Context

MVP реализована и проверена локально. Пользователь явно разрешил серверное
развёртывание и создание тестовых аккаунтов. Общий хост Ubuntu 24.04, x86-64,
1 CPU/2 GB; существующие marketing и RepairDevice должны продолжать работу.
Первая поставка 0.2.0 выполнена с общим Basic Auth и обязательным WebAuthn.
Последующее уточнение пользователя меняет целевой доступ: открытый лендинг,
модальный вход/регистрация и полноценный вход по email/паролю. Ниже описано
целевое поведение; действующий код и сервер меняются на следующем этапе apply.

## Goals / Non-Goals

Цель — разделить свободный просмотр сайта и доступ к личным данным через
авторизацию приложения, сохранив тестовые аккаунты и введённые пользователем данные.
Добровольный WebAuthn не должен делать парольный вход зависимым от наличия ключей.
Новый passwordless-сценарий и настройка обязательного MFA в это уточнение не входят.

## Decisions

- Установить Docker/Compose без обновления остальных пакетов; собрать приложения
  локально. В /opt/lastochka хранить версии, отдельные volumes/network и env 600.
- Добавить только Lastochka locations в HTTPS vhost, сохранить TLS 1.2/ACME,
  proxy root и RepairDevice. Перед reload — backup и nginx -t.
- Общий Basic Auth снимается со всех Lastochka browser/API-маршрутов: браузер
  не должен показывать системный запрос пароля. Публичные страницы, assets,
  опубликованный контент и расписание доступны гостю. Личные данные и команды
  проверяют аутентификацию, роль и владельца на backend; снятие proxy-защиты
  не расширяет публичный allowlist API. MailHog остаётся только через loopback/SSH.
  Простой тестовый пароль используется по прямому запросу пользователя; секрет
  не попадает в репозиторий или журналы. Пароль БД остаётся случайным и отдельным.
- Primary role остаётся PARENT/ADMIN. Nullable additional_role=DOCTOR разрешена
  только при ADMIN; AccountView получает дополнительный массив roles. Session
  содержит ROLE_ADMIN+ROLE_DOCTOR. Для всех ролей успешная проверка email/пароля
  подтверждённого аккаунта создаёт полноценную сессию FULL. Security rules
  больше не требуют фактор WEBAUTHN для кабинетов и операций приложения;
  парольный вход не помечается как пройденная WebAuthn-проверка.
- WebAuthn остаётся добровольной возможностью: добавить собственный ключ можно
  после входа в «Безопасности», существующие credentials не удаляются.
  Отказ от привязки, отсутствие/утрата ключа или отмена добровольного WebAuthn
  не блокируют вход по верному паролю. Сброс пароля по email не удаляет ключи.
- Общая оболочка frontend открывает доступный dialog с режимами «Вход» и
  «Регистрация» по кнопке «Войти». Используются общие формы/API-операции с
  существующими auth-маршрутами, без дублирования транспортных DTO.
  Модальное окно сохраняет фон и прокрутку; фокус переходит внутрь, Tab остаётся
  в диалоге, Esc/крестик закрывают его и возвращают фокус инициатору. При открытии
  фон неинтерактивен; на телефоне формы и действия доступны без переполнения.
- Прямые auth-ссылки и страницы подтверждения email/сброса пароля сохраняются
  для почтовых ссылок, обновления страницы и переходов без JavaScript.
  Вход из действия записи сохраняет только локальный безопасный returnTo/ID
  занятия; после входа доступность места проверяется заново. Закрытие модального
  окна не отправляет заявку и не меняет текущую страницу.
- Публичная регистрация создаёт только PARENT и требует подтверждения email
  до полноценного входа. ADMIN создаёт оператор. Защита cookie, CSRF, лимиты
  попыток и серверные проверки роли/владельца сохраняются.
- Одноразовый bootstrap в preview создаёт все семь подтверждённых аккаунтов в одной
  транзакции без passkey. Повтор с теми же параметрами не меняет пароль/ключи;
  конфликт существующих данных приводит к отказу. На малом сервере bootstrap
  запускается до основного backend, не второй JVM одновременно с ним.
- Для приёмки используются отдельные временные аккаунты; семь пользовательских
  аккаунтов не получают виртуальных ключей. Уже созданные пользователем ключи,
  дети и записи при повторной поставке не сбрасываются.

## Risks / Trade-offs

- Публичный доступ увеличивает доступность auth API → сохранить rate limits,
  email-подтверждение, CSRF и проверки доступа; не публиковать MailHog и служебные URL.
- Старая логика frontend может ждать обязательного WebAuthn → обновить frontend
  и backend согласованно, проверить парольный вход с наличием и без наличия ключей.
- Изменение proxy на общем хосте → backup текущего vhost, nginx -t до reload,
  повторная проверка TLS/ACME/root/RepairDevice и только loopback-порты контейнеров.

## Migration Plan

Сначала реализовать и проверить парольный вход, добровольный WebAuthn и модальные
формы локально. Затем собрать версии frontend/backend, сохранить текущие env/БД/
Nginx и обновить только Lastochka. После готовности приложения убрать общий Basic
Auth и проверить сайт в чистом браузере без Authorization, включая открытие
лендинга/форм и недоступность личных API гостю. Bootstrap семи аккаунтов не повторять.
Обновить AGENTS, контекст OpenSpec и документацию, чтобы прежнее обязательное MFA
и общий пароль сайта не выдавались за действующую политику; исторический отчёт
0.2.0 сохранить с указанием последующего изменения.

При сбое вернуть предыдущие образы/Lastochka proxy-конфигурацию из актуального
backup, проверить nginx -t и readiness; не заменять изменения соседних проектов
и не удалять volumes. Возврат старой версии временно возвращает прежние правила
входа, что нужно явно указать в отчёте. Физическая WebAuthn-приёмка остаётся отдельной.
