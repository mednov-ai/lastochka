## Context

Телефон уже хранится в версионированном документе `landing_content` и поступает в общую шапку и блок контактов через `GET /api/v1/public/landing`. Почтового поля в документе и модели ответа пока нет. Причина изменения описана в `proposal.md`.

## Goals / Non-Goals

**Goals**

- Хранить оба контакта в одной опубликованной ревизии и получать их при серверном рендеринге.
- Поддержать чтение документов и ответов API без нового поля.

**Non-Goals**

- Редактор контактов в кабинете и настройка отправки почты.

## Decisions

1. Добавить необязательное поле `email` в документ, модель ответа и OpenAPI. Передавать его из существующего загрузчика в блок контактов. Такой источник позволяет обновлять телефон и почту одной публикацией. Константа почты во frontend потребовала бы отдельной сборки при каждой последующей замене адреса.
2. Новая миграция Flyway меняет только известный прежний телефон `+7 906 602-30-21` и заполняет отсутствующий адрес. При фактическом обновлении синхронно поднять ревизию строки и документа для корректного ETag. Такой подход работает при чистой установке и обновлении существующей базы. Замена исходного seed V3 осталась бы неприменённой на действующих базах.
3. Вывести адрес обычной ссылкой `mailto:` рядом с телефоном, используя имеющиеся стили ссылок и перенос для узкого экрана по необходимости. Обычная ссылка работает в серверном HTML и открывает почтовое приложение пользователя. Отдельная форма потребовала бы серверной доставки.

## Risks / Trade-offs

- В среде могут быть другие опубликованные контакты → сверить значения перед выпуском. Неожиданные значения сохранить и сообщить о расхождении до подтверждения результата.
- При раздельном обновлении сервисов frontend может получить прежний ответ → выводить почту при наличии значения. Совместимость прежнего backend с обновлённым документом проверить до выбора образа для возврата.

## Migration Plan

1. Проверить чистую установку и миграцию на отдельной восстановленной копии перед выпуском. Сравнить документ до и после, включая ревизию и неизменность остальных полей.
2. При согласованном выпуске обновить backend перед frontend. Проверить новый ответ API, ссылки в HTML и доступность главной.
3. При возврате frontend использовать проверенную предыдущую сборку. Для backend использовать только сборку, которая проверена на обновлённом документе и схеме. Если потребуется вернуть прежние контакты, опубликовать их отдельным адресным обновлением с новой ревизией.
