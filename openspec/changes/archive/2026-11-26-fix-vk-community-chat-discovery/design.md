## Context

26 ноября на test два последовательных запроса `messages.getConversations` версии 5.199 с одним ключом и одинаковыми параметрами пагинации вернули `received=0`. Второй запрос отличался только наличием `group_id`. Передача ID соответствует официальному Java SDK VK, однако этого оказалось недостаточно.

## Goals / Non-Goals

Проверить достижимость известной закрытой беседы через адрес со стороны сообщества, восстановить её подключение и сохранить действующую проверку доставки. Изменение касается заявок и тестового сообщества.

## Decisions

- Сначала проверить доставку события `message_new` из «Ласточка-тест». Получить `peer_id` от VK для Test group и вызвать `messages.getConversationsById` с тем же ключом и сохранённым ID сообщества. Зафиксировать наличие события, возвращённый тип беседы и результат проверки. Номер локального чата из пользовательского URL не использовать как адрес сообщества.
- Для эксперимента рассмотреть VK Callback API на выделенном маршруте test. Текущий исходящий ретранслятор допускает только `api.vk.com`, а Bots Long Poll может потребовать дополнительный адрес из ответа VK. До выбора транспорта проверить поддержку сообщества и совместимость с действующим TLS 1.2. Не менять существующие обработчики сообщества без проверки их назначения.
- Для подключения ADMIN получает короткоживущий случайный одноразовый код. Просит участника отправить его в нужную беседу, при необходимости с упоминанием сообщества. Код связан с черновым ключом, ID сообщества и версией настроек. Принять только аутентифицированное событие ожидаемого сообщества с корректным кодом и групповым адресом. Адрес проверять напрямую и показывать название до тестовой отправки.
- Сохранять только необходимые поля настройки. Не записывать тело события, переписку, ключ VK, секрет обратного вызова и код в журналы. Дубликаты события и повторное использование кода не меняют настройку.
- Список и повторная проверка выбора по списку продолжают использовать связанную пару ключа и ID. Для выбора через событие второй запрос списка не требуется. В обоих случаях включение требует успешной тестовой отправки и явного подтверждения ADMIN.

## Risks / Trade-offs

- Если VK не доставляет событие в выбранных условиях или не подтверждает адрес напрямую, сохранить результаты и пересмотреть механизм до внедрения.
- Публичный маршрут события требует проверки секрета, ID сообщества и типа события, ограничения размера запроса и частоты, отдельного теста подтверждения сервера. Маршрут не должен открывать кабинет или API администрирования.
- Смена чернового ключа делает ранее выданный код непригодным. Повторная доставка события не должна менять уже подтверждённую беседу.

## Migration Plan

Сначала провести проверку на test на синтетическом сообщении. После подтверждения выпустить выбранный способ на test, прогнать обе ветки выбора беседы и проверить фактическое получение тестового сообщения. Отключить временную диагностику. Если понадобится хранение нового состояния, проверить совместимость и план возврата перед выпуском.
