## Context

Мотивация и объём — в `proposal.md`. Изучены `frontend/app/ui/auth-form.tsx`,
формы `children`, `admin-session`, общий обработчик ошибок и собственный MailHog UI.
Страница уже имеет `lang="ru"`, большинство явных подсказок русские, но формы
полагаются на браузерные сообщения `required`, `type=email`, чисел и дат.
Наличие английских native-сообщений — проверяемая гипотеза, а не результат
браузерного воспроизведения в этом планировании. `Connected/Disconnected`
непосредственно найдены в `infra/mailhog-public/ui/index.html`.

Локально уже реализован `improve-auth-verification-and-error-feedback`:
`password-policy.ts`, `error-feedback.ts`, полевые ошибки и общий host уведомлений.
Новый план строится поверх этих локальных исходников и сохраняет поведение изменения.
На момент исходного планирования auth-поставка отсутствовала; позднейший отдельный
релиз 0.6.0 отражён в AGENTS.md. Текущий apply остаётся только локальным и не
проверяет/не меняет сервер. Main specs пока отсутствуют.

## Goals / Non-Goals

**Goals:**
- Одна предсказуемая обработка языковых сообщений проверки во всех формах,
  включая появляющиеся динамически в модальных слоях.
- Повторное использование существующей валидации и полевых ошибок без обхода
  ограничений HTML или серверной проверки.
- Проверяемое покрытие всех собственных пользовательских поверхностей,
  с явным перечнем допустимых названий и технических значений.

**Non-Goals:**
- Многоязычный интерфейс, смена библиотек форм, перевод зависимостей целиком.
- Изменение бизнес-правил, аутентификации, автоподтверждения email или «Приду».
- Перевод системных окон выбора passkey/автозаполнения/календаря браузера и ОС.
  Без JS собственные пояснения остаются русскими, язык системной валидации
  остаётся настройкой браузера. Новые серверные формы ради этого не создаются.
- Изменение пользовательских данных, опубликованного контента в БД, текста
  сохранённых писем или закрытого стороннего операторского интерфейса MailHog.

## Decisions

### 1. Инвентаризация по пользовательским поверхностям

Перед правками составить таблицу «страница/элемент → источник сообщения →
исходный текст или тип ограничения → русский текст → проверка». Просмотреть JSX,
`title`, placeholder, доступные имена, CSS-generated content, локальные ошибки,
публичные сообщения backend, состояния загрузки/отказа и публичный почтовый UI.
Проверка исходников дополняется фактическими ошибками в браузере с английской
локалью; простой поиск латиницы пропускает native-сообщения и даёт ложные находки.

Управляемые интерфейсом инструкции получают русские формулировки. `Email` как
самостоятельную подпись/инструкцию заменить на «Электронная почта», а названия
MailHog/WebAuthn/HTTPS, реальные email, URL и идентификаторы сохранять там,
где они нужны пользователю. Английские пользовательские данные не переписывать.
Необходимость технического термина оценивается отдельно: предпочтительнее
«ключ доступа», «вход», «проверка данных»; ссылка или код описываются по назначению.
Правила уже закреплены в AGENTS.md и контексте OpenSpec; автоматическое
применение этих правил остаётся задачей реализации.

### 2. Общая русская проверка поверх существующих ограничений

Предлагается небольшой общий помощник форм и каталог русских сообщений,
без новой зависимости. Использовать `ValidityState` и существующие атрибуты
полей как источник стандартных ограничений. Сообщения покрывают `valueMissing`,
`typeMismatch`, `tooShort/tooLong`, `patternMismatch`, `badInput`,
`rangeUnderflow/rangeOverflow`, `stepMismatch` только там, где такие ограничения есть.
Непредусмотренное невалидное состояние получает безопасное «Проверьте значение поля».

При `invalid` устанавливать русский `setCustomValidity` и связанное полевое
сообщение; на вводе/изменении сбрасывать прежний custom validity перед повторной
проверкой, иначе поле останется навсегда невалидным. Сброс формы, смена auth-режима
и панели также очищают старое состояние. Подключать обработку ко всем формам;
покрытие инвентаризации должно исключить забытые вложенные и динамические поля.
Не отключать валидацию через `noValidate` без равноценной блокировки и не отправлять
запрос программным обходом проверки. Сохранять submit кнопкой и Enter.

Альтернатива — только `lang="ru"` — не управляет текстом браузера надёжно.
Полностью самостоятельный валидатор дублировал бы уже существующие ограничения.
Набор отдельных обработчиков с разными строками усложняет полноту перевода.

### 3. Согласование с полевыми ошибками и политикой пароля

Переиспользовать `aria-invalid`, `aria-describedby` и существующие блоки field errors;
добавить их в формы, где ошибок пока нет. Сохранять другие ID в `aria-describedby`,
не заменяя пояснения. Сообщение доступно до исправления, первая ошибка получает
доступный переход/фокус, native bubble не является единственным источником.
Не создавать отдельную плашку для каждого invalid-поля и не менять общий
механизм дедупликации ошибок запросов.

Unicode-проверка пароля остаётся в `password-policy.ts`; не заменять code points
HTML-ограничением в UTF-16. Сохранять вход существующим паролем без новой проверки
состава. Проверка дат учитывает действующие ограничения и `Europe/Moscow`.
Серверные ошибки сохраняют каталог `messages.properties`, HTTP-статусы и коды;
неизвестные исключения не отображаются через сырой `Error.message`.

### 4. Независимый собственный почтовый UI

Заменить статусы в собственном шаблоне на «Подключено» и
«Нет соединения · переподключение…», проверить остальной текст и форматирование
дат, если оно выводит английские слова. Не редактировать сторонние ресурсы ради
перевода и не расширять allowlist proxy. Обновить локальные/операторские проверки,
которые ожидают старые английские статусы, не выдавая это за серверную приёмку.

### 5. Проверка результата

Инвентаризация завершается таблицей покрытия и небольшим списком допустимых
терминов. В браузерах с `en-US` и `ru-RU` проверить реальные действия submit,
пустые поля, email, границы чисел/дат, доступные ограничения длины/формата,
исправление, повторное открытие и успех. Нельзя ограничиться проверкой `lang`
или отсутствием латинских букв. Если движок не позволяет ввести отдельное неверное
значение, проверять действующее ограничение и описать этот предел сценария.

Покрыть гость/родитель/ADMIN, auth modal и прямые маршруты, ребёнка, создание
занятия, перенос/отмену, «Приду», сеть/API и публичный MailHog; ширины 375/1440,
клавиатуру, отсутствие переполнения и сохранение фокуса. Проверить хотя бы
Chromium и Firefox/WebKit при наличии локального runtime; недоступное не отмечать
выполненным. Прогнать typecheck/build и затронутую регрессию. Backend-проверки
понадобятся только при изменении его сообщений или обработчиков.

### 6. Постоянная проверка текстов и терминологии

Повторяемые тексты frontend собрать в общий русский каталог с группировкой
по пользовательским сценариям; backend сохраняет `messages.properties`,
собственный почтовый UI — свой шаблон/каталог. Новая система выбора языка не нужна.
Все эти источники входят в проверку. Новые литералы за пределами общего каталога
также проверяются: перенос строки в другой файл не должен обходить контроль.

Создать отслеживаемый машиночитаемый словарь: запрещённое слово/устойчивое
выражение, русская замена, примечание о смысле; отдельно — допустимое название,
обоснование и конкретный контекст. Начальные замены заданы в AGENTS.md.
При неоднозначном термине, например «токен», диагностика предлагает описать
назначение ссылки/кода, а проверяющий человек выбирает точную формулировку.
Для кириллических терминов учитывать регистр и явно перечисленные словоформы;
не использовать бесконтрольный поиск подстрок, задевающий другие слова.

Добавить единую команду `npm run check:ui-language` из frontend с анализом
пользовательских поверхностей всего проекта. Для TS/TSX использовать имеющийся
парсер TypeScript: проверять JSX-текст, пользовательские атрибуты и строки
в каталогах/известных местах показа сообщений, включая шаблонные выражения
и строки, передаваемые через переменные. Собственные HTML-шаблоны публичного
MailHog, пользовательский CSS content и backend-каталог включить отдельными
обработчиками. Комментарии, импорты, URL, машинные поля/коды и генерируемый
контракт не являются пользовательскими инструкциями. Не подключать внешнюю
службу перевода или новые зависимости ради этой проверки.

Нарушение завершает команду ненулевым кодом; сообщение содержит файл/строку,
найденное слово, основание и известную замену. Исключения ограничены термином
и областью применения, без глобального разрешения любой строки с MailHog,
отключения целых каталогов или фиксации текущих нарушений как допустимой базы.
Неизвестная английская лексика вне списка допустимых значений считается ошибкой.
Динамическая строка, которую анализ не может определить, остаётся строкой
инвентаризации с браузерным сценарием, а не объявляется проверенной статически.

Ту же команду сделать обязательной перед штатным `npm run build`, включить
в `.github/workflows/verify.yaml` и проверить пути штатной упаковки frontend
и публичного почтового UI, чтобы они не обходили проверку. Для проверки самого
контроля использовать временные минимальные примеры: английская инструкция,
кириллический жаргон, название в разрешённом контексте, запрещённая инструкция
рядом с разрешённым названием, технический идентификатор и динамическая строка.
Отрицательные примеры должны реально давать ненулевой результат, допустимые —
проходить. Не оставлять тестовые нарушения в продуктовых исходниках.

Альтернатива — регулярное выражение по всем исходникам — даёт много ложных
ошибок на код и пропускает связь строк с UI. Только каталог без проверки мест
использования допускает новые тексты в обход него. Статический анализ остаётся
одним слоем защиты: браузерная матрица en-US/ru-RU и смысловая проверка русских
формулировок обязательны для затронутых состояний. В критерии готовности добавить
проверку текста/терминологии, доступных имён и мобильной читаемости.

## Risks / Trade-offs

- Устаревший `customError` блокирует исправленное поле → очищать перед проверкой,
  проверить ввод, change, reset, смену режима и повторное открытие.
- Новый обработчик подавляет текущие серверные ошибки/пояснения → сохранять
  раздельные источники и связи доступности, проверять ответ API и редактирование.
- Русский текст длиннее английского → проверить узкий экран и модальные слои.
- Поиск латиницы ошибочно переводит данные/идентификаторы → ручная классификация
  источника и проверка настоящих сообщений, без преобразования ответов целиком.
- Исходники и сервер имеют разные версии → описать локальную базу и не обещать
  исправления публичного сайта до отдельно выполненной поставки.
- Обход проверки через новую форму записи строки/широкое исключение → проверять
  места показа, отрицательные примеры и точную область каждого исключения;
  динамические источники покрывать браузером и инвентаризацией.
- Формально русский, но непонятный текст проходит анализ → словарь терминов
  дополняется смысловой проверкой при каждой правке интерфейса.

## Migration Plan

1. По новому apply-поручению выполнить локальную реализацию, сохраняя текущие
   несвязанные изменения. Перед React/Kotlin правками прочитать обязательные skills.
2. Миграции БД, изменение API-контракта, обновление зависимостей и seed не нужны;
   при неожиданной необходимости пересмотреть этот план перед расширением объёма.
3. Подключить блокирующую проверку к локальной сборке, CI и штатной упаковке;
   подтвердить её отказ отрицательными примерами и успешный проход чистых исходников.
4. Зафиксировать доказательства в отдельном локальном отчёте, обновить состояние
   AGENTS.md и tasks только по результатам проверок. В этом propose код не меняется.
5. Возможная поставка frontend/почтового UI и, при необходимости, backend — отдельное
   поручение с раздельными версиями. Откат соответствующего образа возвращает прежние
   тексты; восстановление БД для текстового изменения не требуется.
