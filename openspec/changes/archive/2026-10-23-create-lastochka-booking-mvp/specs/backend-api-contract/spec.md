## Purpose

Сохранить согласованность backend и frontend через воспроизводимый OpenAPI-контракт,
генерируемые транспортные типы и проверяемое описание прав, ошибок и времени.

## ADDED Requirements

### Requirement: Полный контракт API
Backend SHALL публиковать OpenAPI для используемых frontend операций, включая
авторизацию, DTO, обязательные/nullable-поля, все статусы записи и занятия,
форматы времени, пагинацию, идемпотентность и возможные ошибки.
Контракт SHALL разделять публичные, родительские и административные операции,
описывать неполный вход, WebAuthn options/assertion/registration и управление ключами.
Передача двоичных полей WebAuthn SHALL быть однозначно описана как base64url.
Контракт SHALL также описывать опубликованный контент лендинга с версией схемы,
ревизией, типами блоков и правилами кеширования.
Для блоков с эффектами SHALL описываться необязательный безопасный пресет
анимации и статическое поведение при его отсутствии/неподдерживаемом значении.

#### Scenario: Представление ожидающей заявки
- **WHEN** frontend получает заявку с PENDING и её версией
- **THEN** контракт однозначно описывает эти поля, доступные статусы и требуемую
  версию для следующей изменяющей команды

### Requirement: Генерация клиента и проверка актуальности
Frontend SHALL использовать типы и типизированные пути операций, полученные
из backend OpenAPI; транспортные DTO SHALL не дублироваться вручную.
CI SHALL повторно экспортировать контракт, генерировать типы, проверять отсутствие
расхождений с сохранёнными артефактами и проверять типы frontend.

#### Scenario: Backend изменил обязательное поле
- **WHEN** backend меняет обязательное поле ответа без обновления frontend и артефактов
- **THEN** проверка контракта или проверка типов завершается ошибкой до выпуска

### Requirement: Единые ошибки и конфликты
API SHALL возвращать машиночитаемый формат ошибки с кодом, понятным описанием,
идентификатором запроса и ошибками полей при валидации. Для неверного ввода SHALL
использоваться 400, отсутствующей сессии 401, недостаточных прав/CSRF 403,
недоступного ресурса 404, конфликта/устаревшей версии 409, ограничения частоты 429.
Сообщения SHALL не раскрывать пароль, токены, чужие данные или внутренний стек.

#### Scenario: Клиент получил конфликт вместимости
- **WHEN** место занято между просмотром и отправкой заявки
- **THEN** API возвращает 409 с устойчивым кодом ошибки,
  а frontend обновляет доступность и показывает понятное сообщение

### Requirement: Форматы времени и ограничения выборок
API SHALL передавать моменты времени в ISO 8601 с UTC offset и зону студии
`Europe/Moscow`; дату рождения SHALL передавать как календарную дату.
Списки SHALL иметь документированные ограниченные выборки и устойчивую сортировку.

#### Scenario: Большая история записей
- **WHEN** родитель запрашивает историю за пределами первой страницы
- **THEN** получает следующую страницу только своих записей в документированном порядке

### Requirement: Независимая поставка frontend и backend
Frontend и backend SHALL иметь отдельные локальные сборки, версии и единицы
развёртывания. Backend JAR для Java 25 SHALL не включать frontend assets/HTML.
Сервер SHALL запускать готовые образы без сборки исходников. Данные и сессии
SHALL сохраняться в PostgreSQL при замене любой из частей. Документация SHALL
описывать отдельные health-проверки, совместимые версии, доставку и откат.

#### Scenario: Обновление только интерфейса
- **WHEN** оператор заменяет frontend на совместимую версию
- **THEN** backend не пересобирается и не перезапускается, данные и доступ
  сохраняются, а новый интерфейс использует существующий API

### Requirement: Маршрутизация и совместимость раздельного деплоя
Страницы/assets и API SHALL обслуживаться разными сервисами через один публичный
origin: API внутри настроенного base path SHALL сохранять маршрутизацию в backend.
Для временного размещения `/lastochka/api/**` SHALL идти в backend, остальные
маршруты приложения под `/lastochka/` — во frontend. Внутренние адреса сервисов
SHALL быть конфигурируемыми и не попадать в browser bundle. Новая backend-версия
SHALL поддерживать предыдущий frontend в пределах rollout; frontend SHALL
выпускаться только на совместимый API. Неизвестные API/assets SHALL возвращать 404.

#### Scenario: Поэтапное обновление
- **WHEN** сначала обновляется backend с аддитивным контрактом, затем frontend
- **THEN** прежний интерфейс продолжает работать до своей замены, а откат frontend
  не требует отката backend и сохраняет публичный origin, cookie и WebAuthn RP ID

### Requirement: Подпуть и перенос окружения
Первое окружение SHALL использовать сервер `139.100.236.101` и публичный URL
`https://play-and-say.ru/lastochka/`. Public URL, base path, API base, внутренние
upstream и RP/origin SHALL задаваться конфигурацией. Корневые маршруты Play&Say
за пределами `/lastochka/` SHALL не переназначаться приложению.
Будущий перенос SHALL сохранять данные PostgreSQL и учитывать совместимость
миграций, настройки публичных ссылок и доменную привязку passkey.

#### Scenario: Совместное размещение
- **WHEN** окружение настроено с base path `/lastochka`
- **THEN** API доступен через `/lastochka/api/v1`, запросы корневого `/api`
  и других разделов Play&Say не перехватываются, неизвестный API Lastochka даёт 404

#### Scenario: Перенос с прежним публичным доменом
- **WHEN** данные восстановлены на рабочем сервере, а прокси переключён на него
  с сохранением публичного URL, RP ID и совместимой конфигурации
- **THEN** записи, контент и credentials сохраняются без изменения исходного
  кода приложения; вход проверяется на новом размещении до завершения переключения

### Requirement: Внешнее состояние и управляемое завершение
Оба сервиса SHALL иметь отдельные проверки жизни/готовности и корректно
завершаться по сигналу остановки. Сессии, credentials и очередь SHALL не зависеть
от локального файлового состояния экземпляра. Подготовка к Kubernetes SHALL
не требовать его установки для первой версии.

#### Scenario: Перезапуск backend
- **WHEN** экземпляр backend заменяется совместимой сборкой
- **THEN** после readiness пользовательские данные, зарегистрированные ключи
  и серверные сессии доступны из общего хранилища
