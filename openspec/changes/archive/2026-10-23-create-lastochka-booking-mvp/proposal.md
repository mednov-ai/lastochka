## Why

Студии «Ласточка» нужен единый путь от знакомства с занятиями до записи ребёнка
и управления расписанием. Сейчас есть только дизайн и материалы: реальных
аккаунтов, свободных мест и обработки заявок нет.

## What Changes

- Создать адаптивный лендинг по концепции «01 Воздух» с материалами из `info/`
  и переходом к реальному расписанию. Лендинг, запись и кабинеты входят в одно
  React-приложение. Наполнение отделено от компонентов и подготовлено к будущему
  редактированию через панель без пересборки frontend.
- Сразу включить выразительные анимации лендинга, синхронные с прокруткой:
  изменение оттенков, прорисовку декоративных линий и раскрытие сцен/карточек.
  Ориентир — презентационная подача Apple в визуальной системе «Воздуха».
  Предусмотреть адаптацию для телефона, уменьшенное движение и статическое содержимое.
- Добавить регистрацию родителя по email и паролю, подтверждение email,
  привязку passkey и обязательный двухэтапный вход email/пароль → WebAuthn
  для родителей и администратора; восстановление пароля не отключает WebAuthn.
  Кабинет родителя поддерживает карточки нескольких детей.
- Показывать отдельные индивидуальные и групповые занятия; принимать заявки
  на свободные места с обязательным одобрением администратора.
- Добавить кабинет администратора для одного тренера и одного зала: занятия,
  свободные места, очередь заявок, одобрение/отклонение, переносы и отмены.
  Администраторов может быть несколько; каждый работает под собственным аккаунтом,
  а конфликтующие решения защищены версиями и аудитом автора.
- Предложенное правило: заявка ожидает решения и удерживает место; отклонение
  или отмена освобождает его. Клиент всегда видит разницу между заявкой
  и подтверждённой записью.
- Использовать MailHog для тестовых email-сценариев: backend отправляет письма
  по SMTP в отдельный сервис, ссылки и уведомления проверяются в его UI/API.
  Предусмотреть установку MailHog локально и в тестовой серверной среде, закрытый
  доступ к ящику и отсутствие внешней доставки. Для будущей реальной доставки
  сохраняется **RuSender** через транзакционный HTTPS Email API.
- Связать React 19 + TypeScript с Kotlin/Spring Boot 4 через генерируемый
  OpenAPI-контракт и проверку его актуальности в CI.
- Использовать Java 25 и PostgreSQL. Собирать frontend и backend локально и
  развёртывать независимо: отдельный frontend с SSR лендинга и отдельный backend
  JAR с модулями scheduling/payments. Frontend в JAR не включается.
- Подготовить два независимо версионируемых образа для небольшого сервера,
  общий публичный origin через reverse proxy, отдельные health-проверки и откат.
  Это основа последующего переноса тех же сервисов в Kubernetes; сборки на сервере нет.
- Первый сервер — `139.100.236.101`, временный публичный адрес —
  `https://play-and-say.ru/lastochka/`. Учесть подпуть во frontend, API, ресурсах,
  email-ссылках и cookie, сохранив существующие маршруты Play&Say. Подготовить
  перенос на рабочий сервер с внешней конфигурацией и сохранением PostgreSQL.
- Хранить `openspec/` в Git, исключить `info/` и локальные результаты сборок;
  нужные приложению производные изображения хранить как обычные исходные ресурсы.
- Поддерживать `AGENTS.md` как актуальный контекст проекта.

### Non-goals

Реальная доставка email, фактический production-запуск с реальными клиентами,
платёжные операции/провайдер, панель редактирования контента, абонементы, запись
на серии, повторяющиеся шаблоны расписания, несколько тренеров/залов, лист
ожидания, самостоятельная отмена/перенос клиентом, учёт посещаемости,
напоминания по таймеру, самостоятельное восстановление при утрате всех passkey,
кабинет тренера, Kubernetes-кластер/манифесты/HA-rollout и медицинские услуги.

## Capabilities

### New Capabilities

- `public-landing`: публичная страница «Воздух», структурированный контент,
  анимации по прогрессу прокрутки, подготовка к будущему редактору и переход
  к записи в общем frontend.
- `parent-auth`: email/password + обязательный WebAuthn, привязка passkey,
  подтверждение email, восстановление пароля, сессии и несколько аккаунтов ADMIN.
- `family-profiles`: карточки детей и изоляция данных семей.
- `studio-scheduling`: конкретные занятия, один тренер/зал, доступность и переносы.
- `appointment-booking`: заявки, удержание мест, административные решения,
  ручная запись, перенос и отмена.
- `mock-email`: outbox, тестовая SMTP-доставка в MailHog и сообщения о жизненном цикле заявки,
  включая закрытый серверный preview без внешней доставки.
- `backend-api-contract`: OpenAPI, генерируемые типы/клиент, совместимость версий
  и независимая поставка frontend/backend, работа в подпути и перенос окружения.

### Modified Capabilities

Нет: проектные спецификации отсутствуют.

## Impact

Новый репозиторий с единым `frontend/`, многомодульным `backend/`, артефактом API
и отслеживаемым `openspec/`. Backend — Kotlin/Java 25, Spring MVC, Spring Security
и Flyway; PostgreSQL хранит данные приложения и опубликованное наполнение лендинга.
Модуль payments имеет отдельную границу сборки, без платёжных операций в MVP.
Добавляются REST API, интеграционные/браузерные проверки, локальные раздельные
сборки и инструкция независимой доставки/отката сервисов. Frontend формирует HTML
лендинга в своём SSR runtime; backend хранит контент и предоставляет API.
`info/` и сборки исключены из Git;
исходные материалы локально сохраняются и не требуются для сборки чистого checkout.
Существующих потребителей API и мигрируемых данных нет; внешние почтовые
и платёжные сервисы изменение не затрагивает.
