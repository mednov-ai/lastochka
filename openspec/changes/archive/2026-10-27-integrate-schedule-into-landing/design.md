## Context

См. `proposal.md` для мотивации. Пользователь подтвердил расписание на главной и затем явно потребовал убрать ненужную отдельную страницу. Production-поставки сайта не было: текущая frontend0.11.2/backend0.11.0/V14 — тестовая площадка. Сохранение публичного `/schedule`, редирект или совместимая оболочка не нужны.

Главная строится из опубликованных `data.blocks`. Публичный маршрут расписания сейчас хранит период/страницу/результат и получает занятия после подключения клиента. `headerLinks` содержит пять ссылок, но компьютерная шапка использует первые четыре через `slice(0, 4)`. Пятый пункт и подвал пока ведут на `/schedule`.

Стили `.public-schedule` рассчитаны на самостоятельные main/page, поэтому перенос требует новой оболочки секции. Нормализация дня в SchedulePeriod устранила SSR/WebKit React418 и сохраняется. Рабочая копия содержит предыдущие изменения, сбрасывать их нельзя. Активные поставленные дельты дополняют основные specs; новый контракт удаляет только отдельную публичную страницу, сохраняя административный редактор и API занятий.

## Goals / Non-Goals

**Goals:**
- Одно место публичного просмотра расписания — раздел главной.
- Доступные до ответа API заголовок/якорь и локальная обработка ошибок.
- Сохранение опубликованных блоков, календарных правил и гостевой заявки.

**Non-Goals:**
- Совместимость `/schedule`, перенаправления и второй вариант интерфейса.
- Новый backend endpoint, общий store или редактор порядка расписания.
- Выделение других разделов в страницы, определение активного пункта по всей прокрутке.

## Decisions

1. **Перенести тело в секцию и удалить публичный маршрут.** Вынести управление/результаты из `routes/schedule.tsx` в компонент раздела главной без вариантов отдельной страницы. На главной — одна секция `id="schedule"` с h2 и корректной иерархией вложенных дней/карточек/помощи, без вложенного main/h1. Сохранить SchedulePeriod, Pager, карточки и защиту от старых ответов. Удалить регистрацию публичного `schedule` из `routes.ts` и освободившийся файл маршрута, не оставлять адаптер/редирект. Прямой GET/reload `/lastochka/schedule` возвращает404 штатной обработкой неизвестного адреса. Альтернатива с двумя оболочками или перенаправлением отклонена пользователем; production-совместимость не требуется.

2. **Детерминированная вставка после форматов.** Разместить секцию после последнего видимого `formats`, в обычной ревизии перед `steps`. Если форматы скрыты — перед первым видимым `steps`, иначе перед `contacts`, иначе в конец main. Вставка только в представлении, без записи published JSON/БД или изменения порядка других блоков. Ключ секции не зависит от hash/недели/результатов, повторный якорь не сбрасывает состояние. Проверить уникальность `#schedule` на используемых ревизиях. Новый сохраняемый блок не нужен, поскольку редактор и миграция контента не входят в задачу.

3. **Все ссылки просмотра ведут к якорю.** Заменить цель расписания в `headerLinks` на `/#schedule`, компьютерной шапке показать полный список. Обновить подвал, первое посещение и другие обнаруженные ссылки публичного просмотра. Проверить все употребления `/schedule`, отличая публичный путь от `/admin/schedule` и API. Для мобильного выбора сначала закрыть меню; повторный якорь обработать также для компьютерной навигации. Использовать измеренный отступ шапки и hash-позиционирование без фиксированного таймера. CTA заявки/кабинета сохраняют назначение. Менять только одну ссылку недостаточно: остальные должны вести к тому же месту.

4. **Сохранить читаемую шапку с пятью пунктами.** До1000px действует прежнее компактное меню, выше1000px видны все пять пунктов. На1001/1100/1280px согласовать интервалы и допустимый перенос desktop-групп; не скрывать расписание и не уменьшать принятые размеры логотипа/текста ради размещения. Мобильные ограничения104/160px и размеры действий сохраняются;200% текста допускает перенос.

5. **Запрос и ошибка локальны.** Сохранить один запрос первого периода после подключения клиента; не добавлять его в обязательный loader всей главной. Пока запрос ожидается или завершился ошибкой, доступны другие блоки, шапка, контакты и заявка. Повтор остаётся внутри раздела, смена периода не меняет маршрут и не прокручивает страницу к началу. Использовать существующие календарные правила, пагинацию и нормализацию русских дней. Не нужны новая библиотека данных, observer или скрытый второй рендер.

6. **Локальные стили и no-JS объяснение.** Перенести оформление0.11.2 в оболочку раздела с согласованной с главной шириной, без минимальной высоты/полей самостоятельной page и без декоративного раскрытия расписания по scroll. SSR содержит якорь/заголовок независимо от API. Без JS скрыть неподключённые команды/сообщение загрузки и показать русское пояснение со ссылкой на действующую серверную форму с подбором занятия; не изображать пустую неделю. Полная недельная навигация без JS не добавляется. Проверить нижние сцены при загрузке/смене высоты и прямые `#coach`/`#contacts`.

## Risks / Trade-offs

- [После удаления остались ссылки на404] → поиск всех ссылок, реальные клики из шапки/подвала/первого посещения, отдельный GET/reload удалённого адреса с HTTP404 без Location.
- [Случайно удалён редактор или API] → разграничить публичный route и `/admin/schedule`, выполнить целевые регрессии управления и заявки.
- [Пятый пункт не помещается] → визуальная матрица1000/1001/1100/1280/1440, гость/ADMIN, текст200%, без скрытия и обрезания.
- [Форматы скрыты/переставлены] → ровно одна вставка с запасным местом, без перезаписи опубликованного контента.
- [Якорь под шапкой или повтор не работает] → прямое открытие/reload, переход с другого маршрута, повтор hash и no-JS; цель существует до API.
- [Высота недели сдвигает сцены/фокус] → пагинация20, долгий ответ, смена недели, back/forward и регрессия нижних сцен; не фиксировать высоту по одному снимку.
- [Расходится первоначальный текст WebKit] → сохранить нормализацию и слушать pageerror с первого открытия.
- [Нет JavaScript] → понятный ограниченный режим с серверной формой, без ложного пустого состояния.

## Migration Plan

Сейчас обновляются только существующие planning-артефакты. При apply прочитать AGENTS/статус/активные дельты, применить React skill и сохранить постороннюю рабочую копию. Миграций БД/API нет. После переноса удалить публичный route, его файл и устаревшие предположения тестов/документации; проверить главную,404 старого адреса, редактор, заявку и лендинг, оформить локальный отчёт.

При отдельно разрешённом обновлении тестовой площадки использовать frontend-only пакет с совместимым backend, свежий backup с проверкой restore и schema14/PASSWORD_LIFECYCLE_V1. Проверить реальные переходы,404 удалённой страницы, ресурсы и сохранность данных. Исходная тестовая версия для отката — frontend0.11.2 с backend0.11.0/V14, перепроверить перед обновлением. Backend/БД/shared Nginx/TLS/соседей не менять, старый dump поверх новых данных не применять. Production-развёртывание отдельно не разрешено этим планом и не считается состоявшимся.

При будущей синхронизации учитывать активные дельты шапки/темы/редактора/композиции расписания. Новые требования переносят публичный просмотр на главную; прежние проверки отдельной страницы заменяются проверками раздела и404, не возвращать сохранение `/schedule` ради совместимости.
