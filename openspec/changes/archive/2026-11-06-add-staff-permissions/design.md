## Context

См. `proposal.md`. Spring Security сейчас допускает административные маршруты по роли ADMIN; клиент построен вокруг пяти разделов. Учётные записи и сессии используют проверку допуска и версии авторизации. Расписание и оплата имеют отдельные модули, а из заявки можно подготовить оплату.

## Goals / Non-Goals

**Goals:** единая серверная политика разрешений, понятное индивидуальное назначение, совместимость существующего ADMIN и проверяемая защита новых сотрудников.

**Non-Goals:** интеграция банка, хранение банковских секретов, выпуск ссылок, возвраты, предустановленные должности, пользовательская регистрация и новая CRM.

## Decisions

1. Роли ADMIN и STAFF плюс фиксированный каталог разрешений. EDIT подразумевает VIEW; интерфейс явно показывает связь и при снятии просмотра снимает изменение. Это проще набора заранее придуманных ролей и исключает недоступный редактор без чтения. Выдача новых прав STAFF по умолчанию запрещена.
2. Проверку построить на актуальных серверных данных допуска/прав, а не только на видимости пунктов и снимке authorities при входе. При изменении прав обеспечить линейную проверку и отзыв на следующих запросах, включая уже выданные сессии; отдельно определить границу начавшихся транзакций. Не разглашать данные через связанные DTO, ссылки на заявки, SSR, кэш, историю и ошибки.
3. Определить исчерпывающую таблицу «маршрут × полномочие», включая GET, POST-предпросмотр, существующие legacy-маршруты, публичное расписание, настройки уведомлений и собственную безопасность. Закрывать неизвестные административные маршруты по умолчанию. Тестировать маршрут и сервисные обходы, CSRF и ограниченную сессию.
4. В хранении иметь явные роль, права и версию для оптимистической конкуренции; миграция не меняет действующих ADMIN или их сведения входа. Последнего допущенного ADMIN проверять атомарно при конкурирующих изменениях. Не доверять клиентскому признаку допуска и не делать неявного повышения существующих аккаунтов.
5. Только ADMIN управляет учётными записями, паролями других пользователей и правами после недавнего подтверждения; личную безопасность каждый ведёт сам. Это исключает обход ограничений через сброс пароля администратора. Аудировать изменения полномочий без персональных платёжных данных и секретов.
6. Версионировать API и поставку по поддержке прав; capability marker и guard должны запрещать старый backend после включения модели. Старый frontend совместим только с прежним ADMIN при подтверждённых проверках; новым сотрудникам нужен понимающий права frontend. Если совместимый откат отсутствует, остановить доступ и исправлять вперёд; не восстанавливать старую БД поверх новых данных.

## Risks / Trade-offs

- [Раскрытие связанной заявки через оплату] → чтение заявки/копирование контакта проверяются отдельно; существующий снимок оплаты не раскрывает исходную заявку.
- [Гонка отзыва и команды] → определить момент авторизации и транзакционную границу; последующие команды отклонять, проверить конкуренцию.
- [Потеря последнего ADMIN] → атомарный инвариант и проверка конкурентного понижения.
- [Неправильный откат] → обязательный capability gate и проверка совместимого пути с сохранением данных и сессий.
- [Выдача будущих полномочий] → фиксированный каталог и отказ по умолчанию, ADMIN получает полный доступ явно.

## Migration Plan

1. На отдельной восстановленной копии выполнить аддитивную миграцию, проверить существующих ADMIN, сессии, ключи и бизнес-данные.
2. Подготовить backend с проверкой прав, новый frontend, контракт и gate; проверить совместимость и сквозные сценарии до отдельно порученной поставки.
3. После подтверждения совместимой пары разрешить ADMIN явно создавать STAFF/назначать права. Режим STAFF не включать на старом backend.
4. Обычный откат — только к версии с эквивалентной серверной проверкой прав и пониманием схемы; иначе изолировать доступ и устранять проблему совместимой сборкой. Данные новой версии не перезаписывать старой резервной копией.
