## Context

Мотивация и решение пользователя — в proposal.md. Пользователь явно выбрал
«Без пароля, доступен всем по ссылке» после уточнения о ссылках восстановления.
Это приоритетное исключение из прежнего запрета публичного MailHog в AGENTS.md,
openspec/config.yaml и исторических changes; исключение ограничено тестовым preview.
Main specs пока отсутствуют, имена capabilities сохранены из исторических changes.

Сейчас Compose держит MailHog в internal-сети `mail`, maildir в отдельном volume,
SMTP backend использует внутри сети, UI/API выходит только на loopback 18026.
`infra/mailhog-access.conf` поддерживает WebSocket Upgrade/Connection и read timeout;
без этих заголовков ранее был воспроизведён Disconnected. Собственный proxy
направляет всё `/lastochka/` во frontend, исключая API. Для нового адреса нужен
более специфичный маршрут. Общий HTTPS Nginx обслуживает соседние сайты.

У установленного MailHog v1.0.1 локальный `-help` подтверждает `-ui-web-path` и
`-api-host`. По исходникам upstream контроллер UI формирует WebSocket URL из host/
текущего пути, а сервер содержит также управляющие API. Это ориентир, не доказательство
совпадения master с установленным образом: apply проверяет именно закреплённый image.
Источники: [MailHog UI](https://github.com/mailhog/MailHog-UI/blob/master/assets/js/controllers.js),
[MailHog API](https://github.com/mailhog/MailHog-Server/blob/master/api/v2.go).

## Goals / Non-Goals

**Goals:** простой URL без настройки клиента; общий публичный просмотр с настоящим
SMTP/live-обновлением; сохранение почтового состояния; отсутствие новых возможностей
публичного управления сервисом и исполнения содержимого писем в origin приложения.

**Non-Goals:** приватность опубликованных писем, per-recipient авторизация, новая
почтовая система или новый кабинет на React, внешняя доставка/RuSender, изменения
схемы БД/политики входа. Реализация не должна автоматически поставлять готовое
`improve-auth-verification-and-error-feedback`. Эта propose-операция не меняет код,
конфигурацию окружений или сервер.

## Decisions

### 1. Один публичный общий ящик без дополнительных секретов

Канонический URL — `https://play-and-say.ru/lastochka/mail_hog_test/`, без пароля,
аккаунтной сессии и gate через SSH/IP/секретный query. Noindex и отсутствие ссылки
в публичном меню не считаются защитой. Предположение: клиенту показывается общий
тестовый ящик preview, включая уже сохранённые письма, а не отдельная выборка семьи.
Ссылку достаточно передать клиенту; добавлять её на лендинг не требуется.

Альтернативы: Basic Auth, вход ADMIN и SSH отклонены выбранным пользователем способом.
Фильтрация по email в браузере не создаёт приватности и не вводится как защита.

Видимые recovery-ссылки позволяют посетителю получить соответствующую тестовую
роль, включая ADMIN. Сохранение ACL backend, режима чтения MailHog и Secure cookie
не устраняет этот эффект. Публичный preview нельзя считать средой для приватных
данных; закрытие маршрута не отзывает ранее скопированные ссылки. Операторская
инструкция должна описывать отзыв ссылок/сессий отдельно, без автоматического
массового сброса аккаунтов, удаления данных или писем.

### 2. Отдельная публичная граница; внутренний MailHog остаётся в корне

Сохранить root API MailHog, SMTP, maildir, существующий mailhog-access/туннель и
`ATTENDANCE_MAILHOG_API_URL` для внутренних задач. Добавить отдельный public proxy
с профилем чтения; собственный preview-proxy направляет узкий `^~` подпуть к нему,
снимая префикс строго один раз при передаче API в MailHog. Общий HTTPS Nginx
пропускает этот подпуть в тот же стек, не открывая host SMTP/UI на внешнем интерфейсе.
Не размещать mail-proxy в backend и не публиковать общий `/api/v1` MailHog.

UI использует относительные ресурсы и явную public API base
`/lastochka/mail_hog_test/`; WebSocket идёт туда же по WSS. Публичная версия
существующего MailHog UI получает небольшую воспроизводимую адаптацию статических
ресурсов для префикса, режима чтения и plaintext. Закрепить происхождение/версию/
checksum/лицензию ресурсов; main React bundle не меняется. Проверить фактические
assets/URL на v1.0.1. Глобально менять WebPath самого daemon не выбранно: это
может сломать закрытый операторский URL и внутреннюю retention-очистку.

Передавать Upgrade/Connection через каждый публичный HTTP proxy, отключить
буферизацию live-потока, задать read timeout и лимит соединений. Не добавлять
авторизационный redirect при WebSocket handshake. Пустой inbox и обрыв подключения
проверять отдельно. CSP connect-src должен разрешать нужный WSS origin явно.

### 3. Серверная allowlist чтения и минимальная адаптация UI

Разрешить UI/assets, GET/HEAD списка v2, поиска v2, конкретного сообщения v1 и
GET WebSocket v2, а также необходимые документированные технические read-запросы
после проверки закреплённого UI. Не применять правило «разрешён любой GET»:
служебные `/outgoing-smtp`/Jim тоже читаются GET. Default deny для всех прочих
путей/методов; POST/PUT/PATCH/DELETE, import, Release, Jim и удаление запрещены.
Raw MIME, HTML и вложения не нужны для текущих текстовых писем и публично закрыты.
UI не предлагает delete/release/import/Jim/HTML-preview/download. Управляющие
операции сохраняются только через прежний закрытый канал; фоновые workers не
перенаправляются на read-only proxy.

Проверить нормализацию URI, percent encoding, двойные slash и method override:
они не должны обходить запрет или попадать в неограниченный MailHog location.
Кнопки сами по себе не являются защитой, все запреты проверяются прямыми запросами.

### 4. Содержимое писем — недоверенный текст

Публичный UI использует plaintext с экранированием и явные http(s)-ссылки,
не компилирует тело письма как шаблон и не вставляет его через HTML binding.
Для текущих SMTP-писем этого достаточно для чтения и перехода verify/reset/«Приду».
HTML/MIME attachments не отдавать как активные документы того же origin.
Добавить no-store, no-referrer, X-Robots-Tag и nosniff; CSP для UI ограничить
фактически нужными локальными ресурсами и live endpoint, запретить внешние
images/connect, frames/объекты и встраивание страницы. Raw API отдавать JSON с
правильным Content-Type. Одного CSP или удаления Cookie в proxy недостаточно:
проверить инъекции и Angular template expressions в теме/получателе/теле.

Public proxy не передаёт Cookie/Authorization в MailHog и не пропускает Set-Cookie
назад; аккаунтные cookie Lastochka не меняются. UI не вызывает личные API и не
запрашивает auth/me. Переход по ссылке письма — отдельное осознанное действие.
Предпочтительна адаптация существующего UI; проксирование полного административного
MailHog без ограничений или серверная подстановка HTML писем отклонены.

### 5. Явный переключатель и сохранность

Отдельная настройка `MAILHOG_PUBLIC_PREVIEW_ENABLED` по умолчанию false управляет
генерацией публичной конфигурации. При true допускается только test-preview;
конфигурационный preflight отклоняет включение в рабочей среде. При false весь
подпуть, включая API/assets/live, возвращает 404 без frontend SSR fallback.
Не менять обычный compose.local или существующие изолированные acceptance-стенды
глобальным публичным доступом.

Планируемая поставка меняет только нужные proxy/UI-компоненты. Нельзя делать down -v,
пересоздавать accounts/seed или заменять существующий maildir. Исходный SMTP остаётся
internal и без внешней пересылки. Публичный режим не требует изменения backend,
OpenAPI, auth-сборок или ключей attendance.

## Risks / Trade-offs

- Письма/ссылки доступны всему интернету → это выбранное поведение тестового preview;
  рабочая среда выключена, ограничения не маскируются заявлениями о приватности.
- HTML/шаблоны в same-origin UI могут обойти границу приложения → plaintext,
  закрытые raw/MIME endpoints, CSP и adversarial browser-проверки до включения.
- Потеря префикса или Upgrade возвращает Disconnected → HTTP/WSS тест сквозь
  всю цепочку, пустой inbox, приход SMTP без reload и повторное подключение.
- Новая граница мешает оператору/retention → отдельный proxy, прежний внутренний
  адрес и полные права закрытого канала остаются.
- Публичное чтение перегружает небольшой сервер → ограниченные размеры страниц,
  частота read-запросов, число WS на IP и bounded logs без body/token/cookie.
  Конкретные численные лимиты подобрать локально без CAPTCHA/авторизации.
- Обычный reload Nginx не закрывает старые WS → отключать отдельный public proxy
  с завершением соединений и проверять уже открытый браузер. Не рестартовать
  общий Nginx или SMTP ради этого.

## Migration Plan

1. Apply: прочитать исходный change, сохранить snapshot конфигурации и состояния;
   реализовать отдельный публичный профиль и UI только в локальном стенде.
2. Пройти анонимный путь, SMTP/live, чтение/поиск, отказ управляющим endpoint,
   инъекции/личные API, отключение и сохранность. Обновить AGENTS/config/runbooks
   на актуальное исключение для public preview; старые отчёты оставить историей.
3. Серверная поставка — по отдельному поручению: сохранить рабочий конфиг, maildir
   и отпечатки данных; сверить актуальный config-release исправления WebSocket,
   проверить nginx -t, включить только новый узкий маршрут и нужные компоненты.
4. Публичная приёмка в чистом браузере: без SSH/Authorization, UI + SMTP/WSS и
   живое обновление; запрет управления и внешнего SMTP; прежние сайты/сессии/данные.
5. Откат: выключить public флаг/location и остановить только public proxy, завершив
   старые WS. Проверить 404/закрытие активного соединения, SMTP и операторский
   loopback/туннель. Не откатывать БД, приложение, maildir, TLS или соседние сайты.
   Откат не делает уже опубликованные письма/скопированные ссылки приватными.


### Уточнение реализации после проверки закреплённого image

MailHog v1.0.1/maildir игнорирует start/limit списка; поиск возвращает неполный total.
Проверено реальными SMTP-письмами на закреплённом image. Public UI использует тот же
read API списка, сортирует по Created и выполняет поиск по декодированным полям/тексту
и страницы локально. Внутренний MailHog/retention/хранилище не меняются. Последовательность
ответов защищена номером запроса. JSON списка растёт с inbox: это профиль небольшого
синтетического тестового ящика; масштабирование архива отдельной задачей.
