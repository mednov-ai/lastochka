## Context

См. proposal.md — Why. Исследована локальная V11/0.8.0; сервер в этом этапе не проверялся и не менялся. Архив предыдущего изменения подтверждает закрытие функций, но не отсутствие кода. Новое поручение заменяет прежнее требование держать MailHog работающим закрытым архивом.

Подтверждённые места для разбора:

| Место | Остаток / решение |
| --- | --- |
| backend/settings.gradle.kts, app/build.gradle.kts | customers/bookings по-прежнему включены; удалить модули и зависимости после снятия активных импортов |
| notifications | SMTP starter, OutboxStore/NotificationService, cipher/retention/delivery и email workers рядом с действующей TelegramQueue; сохранить Telegram, удалить email-граф |
| identity | Зависимость notifications, RegistrationService, EmailTokenService/AuthTokenRepository, RegistrationLockRepository, email-поля и ветви DTO; PasskeyService зависит от EmailTokenService — сначала сохранить актуальные проверки ключа, затем удалить почтовую связь |
| scheduling | ObjectProvider<SessionReservations>, свободные места/служебные методы прежних участников; доказать вызовы и убрать осиротевшую модель |
| app/config | PreviewAccountsBootstrap, старые initializer/confirmation settings/headers; отдельно сохранить ConceptGuard, ADMIN bootstrap, security/CSRF и минимальный LegacyEndpointFilter |
| frontend | routes.ts содержит account/* и booking/confirm нейтральные маршруты: это действующая совместимость, не целые старые кабинеты; проверить imports/exports, компоненты, styles, тексты, зависимости и тесты по графу достижимости |
| infra/Compose/scripts/CI | MailHog local/preview profiles, public/operator overlays, vendor UI, образы, mail/attendance/env и старый auth-feedback CI-стенд; убрать исполняемые пути, оставить исторические отчёты |
| test-fixtures | Старые suites и подготовка V9; заменить штатные стенды, но сохранить минимальные данные миграционного теста и старые Flyway SQL |

Это список кандидатов, не доказательство мёртвости каждого символа. Реализация составляет журнал «удалить / оставить / развязать» с потребителями, ресурсами, задачами сборки и причинами. Новые расходы памяти/размеров измеряются относительно одного и того же V11-кандидата, без придуманного процента улучшения.

## Goals / Non-Goals

**Goals:** физически сократить runtime и зависимости при неизменных действующих сценариях. Получить проверяемый upgrade с V11 и чистый install со всей историей Flyway, два независимых образа и воспроизводимый запуск без MailHog.

**Non-Goals:** смена ORM/framework, объединение предметных модулей ради числа папок, дизайн-переработка, отказ от ключей/сессий, подключение бота/платёжного провайдера. Переименование всех внутренних email-principal и перепривязка сохранённых ключей не входят в объём.

## Decisions

1. **Удалять по достижимости, а не по названию или аннотации Profile.** Учитывать DI, reflection/JPA mapping, configuration binding, frontend routes/CSS, ресурсы, генератор API и CLI. Оставление всего под legacy-archive отвергнуто: байткод и зависимости останутся. Автоматическое удаление всего найденного поиском отвергнуто: PasskeyService и рабочая инфраструктура имеют скрытые связи. Специальный новый анализатор всего проекта не нужен: доступны компиляторы, поиск ссылок и фактическая сборка/тесты.
2. **Семь удаляемых таблиц:** children, bookings, auth_tokens, notification_outbox, attendance_grants, attendance_contexts, move_previews. Прочие таблицы не удалять: accounts, auth_limits, user_entities, user_credentials, webauthn_challenges, spring_session/attributes, studio_settings/sessions, landing_content, audit_events, idempotency_records, concept_state, enrollment_requests, enquiry_replays, telegram_outbox, payment_requests и flyway_schema_history обслуживают действующую модель. Даже пустые replay/queue/ключевые таблицы нужны. В новых артефактах перечень из семи имён является исчерпывающим; расширение потребует доказательства использования и пересмотра плана.
3. **Новая миграция V12 (если номер свободен на apply).** V1–V11 неизменны. Использовать явный порядок FK и DROP TABLE без CASCADE, проверять отсутствие непредусмотренных ссылок. Непустые удаляемые таблицы сначала инвентаризируются/архивируются закрытым backup; автоматическое удаление неожиданных новых данных не допускается. Не выполнять VACUUM FULL/пересоздание рабочей БД ради уменьшения размера.
4. **Не путать email-идентичность с email-доставкой.** Сохранить внутренний principal/accounts.email и FK user_entities на этом этапе, а также stable credential/user handles. Удалить email-auth/recovery/notification поведение и зависимости, сохранив назначение логина и операторский сброс, auth_version/generation, rate limits и WebAuthn. Это безопаснее массовой смены идентификаторов без продуктовой необходимости.
5. **Минимальная совместимость адресов.** Старые API продолжают отвечать410 через независимый фильтр, старые страницы остаются коротким объяснением без доменных модулей, почтовый подпуть404. Сохранить форму без JS, подпуть /lastochka, SSR/route data и старые статические ресурсы по действующей политике поставки. Generated types меняются только через backend export/generate.
6. **MailHog удаляется полностью из текущей эксплуатации.** Сначала проверить приватную копию трёх писем/manifest и конфигураций, затем адресно убрать только контейнеры/volume/network/образы Lastochka, если они не используются другими потребителями. Нельзя использовать down -v или системный prune. Старые backup и архивные отчёты сохраняются, работающий inbox/operator/tunnel больше не обещается; собственные инструкции туннеля выводятся из эксплуатации без закрытия чужих SSH-процессов. Отдельный архивный сервис вместо MailHog отвергнут: поддержка почты больше не нужна.
7. **Граница отката по схеме.** Marker ADMIN_ENQUIRIES_V1 сам по себе недостаточен: 0.8.0 может инициализировать JPA/repo удалённых таблиц. Gate/manifest должны проверять поддержку диапазона схемы обеими сборками; откат на 0.8.0 после DROP не считается совместимым без отдельного доказательства. Новые заявки/очередь/DRAFT не затирать старым dump. Disaster restore — изоляция и новая внешняя generation. Репетиция без второй JVM на малом сервере, тяжёлые проверки локально.

## Risks / Trade-offs

- [Скрытая зависимость ключа от email-службы] → миграционный fixture с сохранённым ключом, проверка старого credential после нового входа и подписи виртуального устройства; не менять principal.
- [Таблица выглядит старой, но нужна новой команде] → журнал владельцев/SQL/ограничений, FK-проверка, запрет CASCADE и сохранность активных replay/audit.
- [Очистка тестов скрывает регрессию] → перенос проверок актуальной концепции в штатный CI, а не уменьшение набора до пустого зелёного запуска.
- [Удалён maildir до проверки backup] → адресные manifest/restore и явный checkpoint до удаления; серверные действия отдельным поручением.
- [Заявленное облегчение не измерено] → сравнить модули/dependencies, JAR, client chunks, SSR/image sizes, containers/ports и idle RSS в одинаковой среде; не обещать обязательное падение каждого показателя.

## Migration Plan

1. На apply обновить инвентаризацию V11 и граф зависимостей; зафиксировать исходные размеры и действующие проверки. Рабочие данные не трогать.
2. Удалить/развязать код, добавить миграцию и адаптировать интеграционные fixtures, генерацию и текущий CI/упаковку; выполнить чистую сборку без MailHog и info/.
3. На изолированной копии V11 с ADMIN/ключом/сессией/занятием/заявкой/очередью/DRAFT/аудитом/replay проверить upgrade и восстановление backup, fresh install и границу rollback.
4. Подготовить согласованные образы, schema manifest/gate, адресный inventory/runbook ресурсов и план короткого обслуживания. Это завершает локальное изменение; сервер остаётся0.8.0/V11 до отдельного поручения.
5. При отдельно порученной поставке: свежий backup/restore БД и maildir, остановка старых команд/worker, миграция, согласованная пара, вход/ключи/заявка/DRAFT/health/соседи. Только после принятия проверить отсутствие потребителей и адресно удалить собственный MailHog volume/resources. Новые обращения сохранять на всех шагах восстановления.
