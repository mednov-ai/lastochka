## Context

Общий `AuthProvider` получает `/auth/me` на клиенте, обновляет данные при фокусе и событиях других вкладок, но `null` пока объединяет ожидание и ошибку. Подвал всегда рендерит `AuthLink`, который открывает модальную форму. В `Workspace` общей кнопки выхода нет; существующий выход с CSRF реализован в `security.tsx`, отдельный — в `change-password.tsx`. В безопасности тот же `AuthLink` намеренно используется для повторного подтверждения. Актуальная дельта компактного редактора требует сохранить его предупреждение и обработку незавершённых команд.

## Goals / Non-Goals

**Goals:**

- Достоверное состояние для выбора действия и безопасное поведение в гонках и при сбое.
- Общий доступный выход с существующей серверной семантикой, без потери редакторского ввода.

**Non-Goals:**

- Новые роли, изменение учётных данных, API или схемы БД; автоматический выход других администраторов.
- Добавление поддержки работы кабинета без JavaScript: требуется корректный переход из подвала и сохранение действующей публичной формы заявки.

## Decisions

1. Подвал получает собственное действие, а не меняет смысл всех `AuthLink`: подтверждённый FULL ведёт к расписанию, ограниченная сессия — к смене пароля, а подтверждённый гость — к прежней форме. Перед выполнением действия проверять актуальное состояние; явно различать загрузку, гостя и ошибку. Это сохраняет отдельный сценарий повторного подтверждения. Скрытие ссылки после входа рассматривалось, но лишает администратора полезного пути в кабинет.
2. При SSR и без JavaScript использовать прямую ссылку `/auth/login`; серверный обработчик этого адреса проверяет именно сессию запроса через существующий `/auth/me`, передавая только необходимую cookie, и перенаправляет FULL или ограниченную сессию. Гость получает прежнюю страницу входа. Ошибка проверки не означает анонимность. Персонализированный ответ нельзя помещать в общий публичный кеш; таймаут и ошибки не должны мешать публичной заявке. Для гидратации обеспечить совпадающую начальную разметку и не показывать доступное, но ещё не работающее действие. Прямой вход после проверки не мешает модальному повторному подтверждению.
3. Вынести общий процесс выхода в оболочку кабинета и убрать дублирующую кнопку со страницы безопасности; ограниченная сессия сохраняет свой доступный выход через тот же процесс. Запрос отправлять только после решения о несохранённом вводе; использовать существующие механизмы редактора, не создавать ложного успеха при ошибке. При успешном серверном ответе обновить сессию и уведомить другие вкладки. Если последующая проверка недоступна, не выдавать устаревшую сессию за активную и предоставить повтор проверки.
4. Проверить работу при пропущенных сообщениях вкладок, смене состояния во время запроса и запоздалых ответах: устаревшая проверка не должна перезаписывать более свежую. Доступ к данным всегда определяется сервером, состояние интерфейса не является авторизацией.

## Risks / Trade-offs

- [Сетевой сбой до нажатия] → понятное состояние ошибки и повтор, без открытия формы по предположению.
- [Персонализированный SSR и cookie] → минимальная передача cookie только внутреннему backend, запрет общего кеша, отсутствие секретов в логах; проверка двух независимых сессий.
- [Выход при открытом редакторе или ожидающей команде] → согласовать с активной дельтой редактора: отмена не отправляет logout, задержанный ответ не открывает окна. При успешном выходе сохраняется действующее правило очистки контекста повтора; исход команды при необходимости сверяется после повторного входа.
- [Изменение прямого входа] → проверить гостевую закладку, обязательную смену и отдельное повторное подтверждение.

## Migration Plan

При отдельном поручении реализовать и проверить локально. При отдельно разрешённой поставке готовить frontend-only выпуск и откат на совместимый frontend с действующим backend/V15; изменение не требует миграции данных. Доказательства локальной и серверной приёмки разделять, общую инфраструктуру и существующие данные сохранять.
