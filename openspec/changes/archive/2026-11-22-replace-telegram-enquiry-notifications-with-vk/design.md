## Context

`EnquiryService` сохраняет заявку, снимок каналов и задания в одной транзакции. Worker Telegram использует отдельную очередь и секрет из окружения. Браузерный push использует свой worker, VAPID и подписки аккаунтов и устройств. В кабинете уже есть общие настройки уведомлений и раскрываемые статусы в карточке.

`AlfaEnvironmentSecretBox` хранит версию формата, ID ключа, случайный nonce и шифротекст AES-256-GCM с аутентифицированным контекстом среды и назначения. Ключи шифрования загружаются из каталога вне БД.

## Goals / Non-Goals

- Цели. Управление одним рабочим назначением ВКонтакте из кабинета, доставка через существующую схему очередей, проверяемое переключение и восстановление.
- За рамками. MAX, входящие сценарии бота, рассылки, платежи и публичная форма заявки. Развёртывание и фактическая отправка согласуются отдельно.

## Decisions

### Подключение в существующем разделе уведомлений

В раскрытии «Уведомления о заявках» разместить два самостоятельных блока. ВКонтакте и браузерный push запрашивают свои данные параллельно, у каждого блока свои состояния загрузки, ошибки и подтверждения. При ошибке загрузки рядом с сообщением об ошибке появляется «Повторить загрузку». Кнопка повторяет только запросы своего блока. Доступные действия соседнего блока остаются на месте.

В блоке браузерного push общий переключатель для ADMIN подписан «Отправлять браузерные уведомления о новых заявках». Пояснение относит его к студии. Рядом с состоянием текущего браузера отдельно доступны «Подключить это устройство» или «Отключить это устройство». У STAFF с доступом к заявкам отображается управление своим устройством.

В блоке ВКонтакте действия идут в порядке «Ввести ключ» → «Выбрать беседу» → «Отправить тестовое сообщение» → «Включить уведомления». Название выбранной беседы видно рядом с подтверждением включения. При замене ключа название текущей рабочей беседы остаётся отдельно от новой до подтверждения замены.

ADMIN вводит токен сообщества в поле пароля. Backend сохраняет зашифрованный черновик настройки, проверяет токен сообщества и запрашивает его доступные беседы через `messages.getConversations`. Сервер фильтрует только групповые беседы и возвращает названия и идентификаторы без тел сообщений. Учитывается пагинация. Выбор `peer_id` проверяется на сервере, тест подтверждает возможность отправки. Загрузка списка с реальным ключом и наличие закрытой беседы проверяются на test. [Официальная схема VK API](https://github.com/VKCOM/vk-api-schema/blob/master/messages/methods.json)

ADMIN выбирает беседу, отправляет нейтральный тест и подтверждает включение или замену рабочего назначения. Внешний вызов выполняется вне длинной транзакции. Результат фиксируется только для исходной версии черновика, ключа и беседы. Неудача оставляет рабочую настройку доступной. Действия настройки защищены полной сессией ADMIN, CSRF, версиями и аудитом. STAFF с доступом к заявкам читает статусы и использует штатный повтор. Настройки своего устройства push доступны по прежним правам.

Выбор по названию упрощает привязку. Ручной ввод ID добавляет риск ошибки, а callback и Long Poll требуют обработки входящих событий. Рабочий сценарий использует исходящие запросы. Сотрудник подтверждает получение проверки в нужном чате.

### Шифрование по образцу Альфа-Банка

Использовать AES-256-GCM, случайный nonce, версионированный формат, ID ключа и контекст вида `lastochka:vk:<окружение>:community-token:<id-ключа>`. Переиспользовать низкоуровневую криптографию, если её можно выделить без изменения банковского формата. ВКонтакте получает отдельный каталог ключей вне БД и собственный контекст. Файлы подаются backend с минимальными правами, отдельно для test и production. Банковский ключ для ВКонтакте не используется.

Открытый токен поступает только в защищённом запросе сохранения и используется backend. Исходящие запросы идут POST на фиксированный HTTPS-хост VK с ключом вне URL. Клиент очищает поле после сохранения, отмены или выхода и обходится без browser storage. Ответ чтения содержит признак наличия ключа, назначение и безопасные коды ошибок. Журналы, аудит и OpenAPI-примеры обходятся без секрета и сырых ответов VK. Ротация ключа сохраняет чтение записей по ID до адресного перешифрования. При восстановлении БД ключевой материал своей среды восстанавливается отдельно. Конфигурация в env потребовала бы участия оператора при каждой замене, а зашифрованная запись позволяет владельцу работать через кабинет.

### Очередь и адресат

Добавить конфигурацию и очередь ВКонтакте аддитивной миграцией. При сохранении заявки зафиксировать, включён ли канал и какая пара «сообщество и беседа» проверена. Для неё сохраняется одно задание с устойчивым `random_id`, уникальность которого обеспечивает приложение. Если test и production используют одно сообщество, выделить окружениям разные диапазоны допустимых значений. Переиспользовать принципы захвата, аренды, задержек и аудита существующей очереди. Сетевой вызов выполняется вне транзакции сохранения заявки. Worker проверяет содержимое результата, включая объект ошибки внутри HTTP 200. Временные ошибки повторяются с ограниченными задержками. Ошибки ключа и доступа видны в кабинете. Принятие API с идентификатором сообщения фиксируется отдельно от прочтения. [Официальный клиент VK](https://github.com/VKCOM/vk-php-sdk/blob/master/src/VK/Actions/Messages.php)

Переключатель управляет выбором канала для новых заявок. Для ранее созданных заданий допустима отправка и ручной повтор только в исходное проверенное назначение. Замена токена с сохранением сообщества и беседы позволяет продолжить очередь с прежним `random_id`. Смена назначения останавливает ожидающие задания исходной беседы, в том числе после перезапуска. Worker перепроверяет получателя перед вызовом. Вызов, начатый до смены, может завершиться только к исходному адресату, а результат относится к исходному заданию. Перенос накопленной очереди в новое назначение мог бы отправить прежние заявки в другой чат.

Короткое сообщение формируется из номера и ссылки на карточку от канонического origin окружения. Переход загружает заявку по защищённому API независимо от текущей страницы списка. При необходимости входа возврат ограничен внутренним путём.

### Совместимость и история Telegram

VK получает отдельные административные операции. Прежнее чтение доставки Telegram продолжает показывать историю. Ранее ожидавшие задания отображаются остановленными при сохранении исходных записей. Старый POST повтора получает безопасный отказ, устаревшая команда включения Telegram предлагает обновить страницу. Маршруты и контракт push сохраняются. Новый frontend загружает историю, статус ВКонтакте и push независимо.

На миграции ВКонтакте выключен. Сохраняются заявки, Telegram outbox, VAPID, переключатель push и подписки. При приёмке следует согласовать замену оставшихся проверок Telegram из `simplify-enquiry-form-with-age-directions` проверкой действующего канала с учётом фактических исторических результатов.

## Risks / Trade-offs

- [VK ограничивает видимость закрытой беседы] → проверить список со штатным ключом и приглашённым сообществом. Показать подсказку по приглашению и обновлению списка. Успешный тест обязателен перед включением.
- [Потерян ответ VK после принятия] → повторять с исходным `random_id`. Поведение дедупликации зависит от VK. Единственность заявки и логического задания обеспечивается приложением.
- [Ошибка расшифровки при старте или восстановлении] → показать статус канала, продолжить приём и push, восстановить ключевой материал своей среды отдельно от PostgreSQL.
- [Старый backend может возобновить Telegram] → завершить обработку прежним процессом до переключения и использовать для отката только сборку с отключённой отправкой Telegram.

## Migration Plan

1. При отдельно порученной поставке определить исходную сборку, окружение и состояние очередей без чтения секретов. Сделать копию test и проверить восстановление в отдельной БД.
2. Прогнать аддитивную миграцию на восстановленной копии. Сверить заявки, записи Telegram, настройки и подписки push. Проверить новый backend со старой вкладкой и новым frontend.
3. Прекратить запуск исходящих отправок Telegram и дождаться завершения старого обработчика до переключения test. Проверить доставку с отдельной тестовой беседой и ключом, введённым владельцем в кабинете. Синтетическая заявка проверяет ВКонтакте и push раздельно. Проверить TLS 1.2.
4. При инциденте выключить ВКонтакте для новых заявок и при необходимости отдельно остановить его обработчик. Использовать проверенную сборку, которая сохраняет новые данные и держит Telegram отключённым. Production выпускается по отдельной отмашке.
