Мотивация и область изменения — в `proposal.md`. Пользователь дополнительно подтвердил: «Выход только внутри админки»; на публичных страницах для вошедшего администратора остаётся переход в кабинет.

Исходное состояние проверено 29.10.2026 по локальным исходникам. Актуальная поставка по началу `AGENTS.md`: frontend 0.15.1, backend 0.15.0, PostgreSQL V18; более старые записи в `openspec/config.yaml` описывают историю. Два существующих активных изменения — компактный календарь и уведомления — не завершаются и не архивируются этой работой.

### Проверка устройства и времени жизни сессии

1. `backend/app/src/main/kotlin/ru/lastochka/config/SecurityConfiguration.kt` и `backend/identity/src/main/kotlin/ru/lastochka/identity/service/LoginSessionService.kt` сохраняют вход в `HttpSessionSecurityContextRepository`. `application.yaml` задаёт cookie `LASTOCHKA_SESSION`, HttpOnly, Path `/lastochka`, SameSite=Lax; Secure включается настройкой HTTPS-среды. Миграция `V1__spring_sessions.sql` хранит сессии и время обращения в PostgreSQL. Авторизационных JWT, отдельного access token, refresh token, refresh-endpoint или механизма remember-me в просмотренном приложении нет. CSRF-код служит защите команд, а не продлению входа.
2. `backend/app/src/main/resources/application.yaml:32` задаёт `server.servlet.session.timeout: 30m`. Это интервал без запросов, обращающихся к сессии, а не 30 минут с момента входа. В штатном `compose.preview.yaml` переопределение этого интервала не задано; фактические настройки работающего сервера в рамках планирования не читались.
3. `frontend/app/ui/auth-context.tsx` вызывает `/api/v1/auth/me` при загрузке, фокусе, возвращении видимости и каждую минуту. Метод `refresh()` здесь повторно читает состояние, не обменивает refresh token. Успешные запросы с cookie обновляют последнее обращение к серверной сессии. Пока браузер реально выполняет эти запросы чаще тайм-аута, вход может оставаться действующим несколько дней без действий человека. ОС или браузер могут приостанавливать фоновые вкладки; один факт открытой вкладки не гарантирует продление.
4. `SessionVersionFilter` проверяет допуск ADMIN, `auth_version` и внешнюю generation. Для обычной полной сессии отдельный абсолютный предел от момента входа не обнаружен. Выход отзывает текущую сессию; смена/сброс пароля и изменение допуска отзывают доступ по действующим правилам. Независимые сессии в других браузерах одним обычным выходом не завершаются.
5. Временный пароль имеет срок 24 часа; ограниченная сессия смены — максимум 15 минут от её начала, даже при обращениях. Повторное подтверждение постоянного пароля для чувствительных действий действует 5 минут. Эти три ограничения не являются сроком полной ADMIN-сессии.
6. Постоянный Max-Age для cookie в коде не задан. Закрытие браузера не следует обещать как надёжный выход: восстановление браузерных сеансов может сохранить cookie, а сервер самостоятельно проверяет срок и отзыв. Возраст и конкретная причина сохранения сессии пользователя без её диагностики не установлены; найденный механизм объясняет такое поведение, но не доказывает историю его браузера.

Семантика проверена по [официальной документации Spring Session](https://github.com/spring-projects/spring-session/blob/main/spring-session-docs/modules/ROOT/pages/api.adoc): срок бездействия связан с последним обращением, значение cookieMaxAge по умолчанию — −1. Авторитет для параметров именно этого приложения — перечисленные исходники и последующая адресная проверка среды.

## Goals / Non-Goals

**Goals:**

- Изолировать геометрию административного ряда от публичных меню, календаря и общих кнопок.
- Выбирать основное действие шапки из подтверждённого состояния входа и контекста маршрута, сохранив единственный механизм выхода.
- Сделать причину долгого входа проверяемой и документированной без выдачи результатов анализа кода за измерение сессии пользователя.

**Non-Goals:**

- Изменение тайм-аута, фоновых проверок, абсолютного срока входа, хранения сессий или ввод JWT/refresh token. Пользователь спросил об устройстве; новую политику длительности он не задавал.
- Переделка всего кабинета, публичной шапки или формы остальных кнопок, изменение серверных контрактов, данных и паролей.
- Реализация или поставка в рамках `openspec-propose`.

## Decisions

### 1. Локальная геометрия пяти ссылок

Добавить собственный класс административной навигации вместо расширения общего `.page nav`. Ссылки остаются навигационными ссылками, не получают семантику вкладок с другим клавиатурным поведением. Использовать flex с переносом, явным выравниванием и постоянным промежутком 8 px; ряд выровнять по левому краю содержимого. У ссылки — `border-radius: 0`, симметричные отступы, центрирование по обеим осям, минимум 44 px по высоте и читаемая подпись. При обычном тексте в строке высоты одинаковы; при 200% тексту разрешены перенос и рост. Ширины соответствуют длине подписей. Активное состояние не меняет толщину рамки или размеры. Выход из этого ряда удаляется.

Альтернатива — заменить только радиус общего селектора. Она сохраняет нежелательную связь с прочими `nav` внутри `.page` и не исправляет смешанную геометрию; одинаковая ширина всех пяти ссылок неоправданно увеличивает число переносов.

### 2. Контекстное действие общей шапки

Контекст кабинета определяется маршрутом приложения после учёта basename: `/admin/*` и `/account/security`. Не использовать проверку произвольного вхождения слова `admin` в URL, query или hash. Если в маршрутизации есть пригодный общий признак оболочки кабинета, предпочесть его единичному дублированному списку; выбор не меняет внешнее поведение.

| Подтверждённое состояние | Страница | Основное действие шапки |
| --- | --- | --- |
| FULL ADMIN | Кабинет или безопасность | «Выйти» |
| FULL ADMIN | Публичная | «Кабинет администратора» / «Кабинет» |
| Гость | Любая публичная | «Записаться» |
| PASSWORD_CHANGE_REQUIRED | Обязательная смена | Сохранить прежнюю шапку и отдельный выход формы |
| Загрузка, сбой проверки, без JS | Любая | Сохранить прежнее безопасное поведение; не показывать неподтверждённый рабочий выход |

Подвал остаётся прежним: переносится главное действие шапки. Его ссылка не является второй кнопкой выхода. Публичные пункты шапки продолжают вести к разделам главной и не превращаются в административное меню.

Альтернатива — показывать выход при любой полной сессии — противоречит подтверждённому пользователем размещению только внутри кабинета. Глобальная замена текста ссылки оставила бы неверный адрес и не выполнила серверный выход.

### 3. Один механизм выхода, два оформления

Расширить существующий `LogoutButton` вариантом оформления для шапки, оставив прежнее оформление для обязательной смены пароля. Вариант управляет только представлением; цепочка CSRF → POST → завершение клиентского контекста редактора → главная → обновление состояния остаётся общей. Сохраняются `requestEditorExit`, отмена намерения, предупреждение о неопределённом исходе уже отправленной команды и штатное оповещение других вкладок. Повторная отправка блокируется на время запроса; ошибка остаётся рядом с инициатором и объявляется доступно, без сдвига логотипа или меню. Не вызывать выход автоматически при смене маршрута.

В шапке резервируется достаточное место для «Выйти»/«Выходим…»; для ширин 375–1000 px сохраняется существующая одна строка закрытой шапки, а на 320–374 px и при 200% допускается прежний перенос. Контраст, высота целей и коррекция якорного отступа остаются действующими. Новая кнопка не должна наследовать декоративную стрелку перехода в кабинет или распределять единственную подпись через `space-between`.

Альтернатива — реализовать отдельный выход прямо в `Header` — создаёт второй набор ошибок и правил защиты ввода. Только скрывать старую кнопку стилями также не подходит: она осталась бы частью семантики и потенциального порядка фокуса.

### 4. Документирование сессии без новой политики

При реализации перенести результаты исследования в документ навигации/сессии и проверить выбранные параметры среды без чтения содержимого cookie, идентификаторов сессий или секретов. Продление запросами и отсутствие абсолютного срока описать как текущие свойства, не вводить новое нормативное требование о бесконечном входе. Изменение политики времени входа оформляется отдельным решением. Периодические проверки нужны и для синхронизации выхода между вкладками; убирать их попутно нельзя.

## Risks / Trade-offs

- Общие стили могут затронуть чужую навигацию → локальный класс и проверка главной, заявки, календаря и безопасности.
- Смена маршрута может оставить неверное действие в шапке → проверить реальные переходы в обе стороны, прямой адрес и reload для всех пяти разделов.
- Перенос выхода может обойти защиту редактора → использовать прежний компонент и проверить отмену с вводом, подтверждение и неизвестный исход команды.
- Ошибка либо длинная подпись может расширить мобильную шапку → резерв места для ожидания, доступное сообщение без изменения основной строки и замеры на границах 374/375 и 1000/1001 px.
- Старая вкладка имеет прежний frontend → новая версия не меняет протокол, срок и серверное хранение сессии; проверить старую вкладку в штатном окне совместимости. Обновление само по себе не должно завершать вход.
- Фактический серверный тайм-аут может отличаться от исходного → обозначить предел доказательств и адресно проверить только разрешённые несекретные параметры перед утверждением результата реализации.

## Migration Plan

1. После отдельного запроса на реализацию изменить только frontend и связанные проверки/описания. Выполнить языковую проверку, проверку типов, сборку, форматирование затронутых файлов и целевые браузерные сценарии. Прежние посторонние ошибки общего форматирования/нестабильную регрессию календаря учитывать отдельно, не объявлять исправленными этой работой.
2. При отдельно порученной поставке выпускать только совместимый frontend с backend 0.15.0/V18. Не менять БД, допуск ADMIN, generation, пароли, ключи или серверные сроки входа. До поставки следовать действующему runbook и сохранить прежние ресурсы для старых вкладок.
3. Откат — прежний принятый frontend 0.15.1 либо актуальная совместимая предыдущая версия на момент поставки с тем же backend 0.15.0/V18. Миграция и откат backend не требуются. Авторизованную проверку площадки и физические устройства учитывать отдельно от локальной приёмки.
