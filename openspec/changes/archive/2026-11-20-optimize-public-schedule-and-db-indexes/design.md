## Context

14.11.2026 на публичном test с локального компьютера в новых Chromium-контекстах при открытии `/#schedule` результат выбранной недели появлялся в DOM через 2,836–3,158 с на 1440×900 и 2,841–3,229 с на 390×844 (по три открытия). Это замер до появления DOM, а не отдельный замер физически видимого пикселя; экран телефона эмулировался. Первый байт HTML приходил через 0,754–0,797 с; клиентские вызовы направлений и двух недель стартовали через 2,56–2,96 с, а наблюдённые ответы каждого занимали около 0,25–0,34 с. В одном прогоне ответ следующей недели ещё не завершился на момент фиксации. Состояние других устройств, production, CPU сервера и планы БД не проверялись. Однократная проверка HTML test показала индикатор загрузки, но не таблицу расписания.

В текущем коде `ScheduleSection` начинает три вызова внутри `useEffect`, после загрузки и подключения клиентского кода; первая неделя и справочник обязательны для результата, следующая неделя загружается параллельно и влияет на текст пустых строк. `home.loader` уже отдельно получает направления для блока на главной. `loadScheduleProjection` проверяет полноту всех страниц и их снимок. Сохранить отсутствие блокирования главной из `studio-scheduling` и текущее поведение [афиши](../../../specs/public-landing/spec.md). V29 и связанные изменения формы в рабочем дереве незакоммичены: не перезаписывать и проверить согласованность с тем, что уже развёрнуто.

## Goals / Non-Goals

**Goals:** уменьшить реальное время до результата выбранной недели, проверить стадии загрузки и сохранить корректность; ввести два согласованных индекса и измерить их с учётом обновлений.

**Non-Goals:** изменение визуальной концепции, правил заявок/оплат и протокола публичного расписания; замена индексов очередей уведомлений; индекс `studio_sessions(ends_at)` без дополнительных доказательств; production-выпуск без отдельного разрешения.

## Decisions

1. **Начинать независимое получение расписания раньше.** Исследовать на production-сборке передачу данных начальной недели через неблокирующую серверную загрузку/потоковую выдачу, либо ранний безопасный запрос с последующим использованием его результата клиентом; выбрать по измерению и совместимости конкретного runtime. Не добавлять синхронное ожидание расписания в общий loader: медленный backend не должен задерживать HTML остальных разделов. Если выбран streaming/SSR, предусмотреть таймаут и корректное восстановление при ошибке, одинаковую неделю МСК между сервером и браузером, начальное и последующее согласование данных без hydration mismatch. Если инфраструктура не позволяет потоковую выдачу, реализовать другое измеренно эффективное раннее получение без блокировки и без дублирующего запроса. Первичные данные и даты предоставлять только из публичных контрактов; никакие данные пользователя не встраивать в общедоступный ответ.
2. **Не заставлять следующую неделю задерживать первую.** Независимо от реализации основной результат включает всю выбранную неделю и направления; дополнительная следующая неделя может завершаться позже, сохраняя существующий нейтральный текст до успешного ответа. По возможности повторно использовать уже полученный справочник направлений, если он содержит все нужные поля и соответствует версии/обработке ошибок; в противном случае сохранить независимую загрузку. Полнота, snapshot, сортировка и проверка поздних ответов сохраняются. Не вводить продолжительный публичный кэш: при любой переиспользуемой выдаче определить конкретную актуализацию при публикации/закрытии/отмене, начале занятия, смене недели и возврате вкладки, проверить границу недели МСК и серверную проверку при заявке.
3. **Приоритет доказательствам.** В инструментированной изолированной production-сборке зафиксировать цепочку HTML → JS → запросы → полный DOM/отрисовка результата; измерить также переключение недели, размер/распределение запросов и TTFB остальных разделов. Сравнивать до/после на идентичном seed, одной машине, одном браузере и профилях 1440×900/390×844, стабильной искусственно заданной задержке и без переиспользования контекста/кеша. Провести минимум семь независимых прогонов каждого варианта с чередованием, указать браузер, CPU, сеть, сервер, версии и разброс. Для заполненной недели медиана времени до видимого полного результата должна снизиться минимум на 30% и 300 мс на каждом размере; не переносить ожидание в TTFB главной. Дополнительно проверить быстрый, задержанный и ошибочный backend, а также многостраничную неделю. Прямой test-замер здесь служит диагностикой, а не универсальным SLA.
4. **Два индекса из принятого аудита.** Следующая свободная версионная миграция после проверки фактической ветки/схемы (V29 уже занята незакоммиченной миграцией):

   ```sql
   CREATE INDEX payment_requests_created_id_idx ON payment_requests(created_at DESC, id DESC);
   CREATE INDEX alfa_attempts_due_environment_idx
     ON alfa_test_attempts(environment, next_check_at, payment_id)
     WHERE (archived = false AND operation_state NOT IN ('PAID', 'CANCELLED'))
        OR callback_pending = true;
   ```

   Это дополнительные B-tree индексы без удаления исходных и изменения строк. Сверить с текущими версиями запросов и наличием индексов; протестировать `due` и `dueProduction`, включая callback для терминального состояния, аренду и равные сроки, custom/generic-планы с реальной формой параметров. На отдельной PostgreSQL 17 с малым и большим наборами и реалистичными долями снять `EXPLAIN (ANALYZE, BUFFERS)` до/после для списков, счётчиков и очереди, размер и накладные расходы insert/update; результаты не экстраполировать на production. Старые индексы не удалять по косвенным данным.
5. **Доставка без риска данных.** Проверять сервер и окружение, использовать только отдельную локальную синтетическую базу или разрешённую изолированную проверенную копию. Перед применением на test — согласовать текущий исходник, состав и режим миграции, проверенный backup/restore и совместимость старого backend с новой схемой; индексы потенциально блокируют запись при создании, поэтому измерить время и запланировать безопасное окно/способ выполнения с учётом Flyway и PostgreSQL. Проверить откат приложения при сохранении индексов; не восстанавливать базу и не удалять индексы на работающем сервере ради проверки. Для production отдельная ветка release и новая отмашка пользователя. TLS 1.2 сохраняется.

## Risks / Trade-offs

- [Предзагрузка перенесёт задержку в HTML или удвоит нагрузку] → не блокировать лендинг, проверить TTFB, число запросов и отказы; отменять неактуальные результаты.
- [Данные устареют после изменений расписания или пересечения начала занятия] → строгая политика актуальности и проверка действий на backend, тесты смены недели и отмены; не показывать ошибку как пустоту.
- [Платёжные индексы замедлят записи или заблокируют таблицы при построении] → замерить объём/вставку/обновление, отдельная миграция и план с backup, а не удаление текущих индексов.
- [Локальный бенчмарк не воспроизводит WAN и сервер] → одинаковые воспроизводимые условия до/после, затем безопасная внешняя проверка test только при разрешённой поставке, явно указать ограничения.
