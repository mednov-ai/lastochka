## Context

Мотивация и границы продукта — в proposal.md. До этого изменения реализация использовала
`StudioCalendar`, одну страницу sessions за 30 дней и отдельную очередь bookings.
Данные кабинетов закрыты password/verified-email проверкой; письма содержат ссылку
в общий кабинет. Команды scheduling/bookings сериализуются через существующую
блокировку студии, проверяют версии, пишут аудит и outbox в одной транзакции.

Локальная проверка 23.10.2026 с подменой только ответов браузеру показала:
35 занятий → 25 видимых и ложные пустые выходные; 34 цели переноса → 24 варианта;
при 25 заявках форма на телефоне находилась примерно на 7280 px ниже верха viewport.
Это исходные исследовательские примеры. Результаты локальной приёмки новой
реализации описаны в `docs/calendar-attendance.md`, эксплуатация —
в `docs/calendar-attendance-operations.md`. По отдельному последующему поручению
выполнена серверная поставка 0.5.0; отчёт — `docs/deployment/2026-10-23-calendar-confirmation.md`.

Main specs ещё не опубликованы. Базовая линия — AGENTS.md и соответствующие specs
неархивированного `create-lastochka-booking-mvp`, с учётом последующих изменений
парольного входа в `deploy-lastochka-test-preview`. Этот change не архивирует их.
Design обязателен: затронуты несколько модулей, модель данных и безопасность.

## Goals / Non-Goals

**Goals:**
- Полнота повестки и безопасное явное управление двумя видами переноса.
- Минимальные полномочия получателя ссылки, отсутствие зависимости от аккаунтной сессии.
- Единые серверные инварианты для новых и прежних административных команд.
- Аддитивные миграции и проверяемый порядок независимого выпуска сервисов.

**Non-Goals:**
- Ответ «Приду» не является отметкой фактического посещения или проверкой личности.
- Публичный лендинг и родительский выбор времени не переводятся целиком на новый календарь.
- Серверная поставка, реальная доставка, OTP, самоперенос, самоотмена и напоминания
  не добавляются; перечень остальных исключений находится в proposal.md.

## Decisions

### 1. Собственная полная повестка и независимые выборки

Добавить административную calendar-выборку точного диапазона `[from,to)` максимум
семь суток. День/неделя/список используют один выбранный диапазон, сортировку
`startsAt,id` и МСК; неделя начинается в понедельник. Выборка включает пересекающие
диапазон интервалы (`startsAt < to && endsAt > from`), в том числе начавшиеся
до полуночи; сетка обрезает только визуальную проекцию, не длительность. Ответ содержит все занятия
диапазона, без page/size общего списка. Для защиты установить предел 1000 занятий:
превышение возвращает 409 `CALENDAR_RANGE_TOO_DENSE` без частичного items;
интерфейс предлагает режим дня или другую дату, не рисует пустоту. Список
в календаре также показывает полный выбранный период, а не скрыто усечённую страницу.
Проверка количества и чтение выполняются в согласованном snapshot чтения.
Предел технический, не ограничение числа занятий в бизнесе.

Состав выбранного занятия загружается отдельно для всех активных bookings,
с данными ребёнка в пределах ADMIN-прав, статусом и ответом клиента. У состава
есть отдельная пагинация, полный total и явно доступные следующие страницы;
он не зависит от общей очереди. Для обычной группы всё помещается на первой странице.
Поиск transfer-targets — отдельный диапазон до 93 дней, page/size, формат,
проверка будущего OPEN со свободным местом, исключение исходного занятия.
Сервер проверяет дубли/пересечения также при окончательном переносе.

Календарь имеет собственные состояния loading/error/empty и generation запроса;
поздний ответ другого периода игнорируется. Переход в другой режим не сбрасывает
дату. Во временной сетке видны начало и окончание, статус и занятость;
цвет дублируется текстом. Телефон показывает выбранный день и повестку.

Альтернатива: использовать первую страницу или увеличить size до 100.
Отклонена: скрытое усечение остаётся. Тяжёлую календарную библиотеку сейчас
не выбирать; базовые режимы реализуются в существующем React UI, новую зависимость
можно обосновать отдельно без изменения поведенческого контракта.

### 2. Панели, предпросмотр и два вида переноса

Панель занятия/записи открывается поверх текущей повестки (side panel на широком
экране, полноэкранный dialog на телефоне), удерживает фокус, закрывается Escape
и возвращает фокус инициатору. Навигация или повтор загрузки не должны молча
переносить редактирование на другой объект. Причина обязательна для отказа/отмены
по прежним правилам; для переноса можно указать комментарий без нового бизнес-барьера.

Общие стадии обоих сценариев: выбор → серверный предпросмотр → явное подтверждение
→ серверная транзакция → обновление повестки/состава. Перенос всего занятия меняет
только начало/окончание с сохранением ID, состава и по умолчанию длительности;
изменение названия/формата остаётся отдельным редактированием с теми же инвариантами
отзыва подтверждений. Перенос ребёнка выбирает существующую целевую Session,
сохраняет ID Booking и PENDING/CONFIRMED. Смена формата/длительности видна в preview.

Preview хранится на сервере пять минут и привязан к ADMIN accountId и виду операции.
Он содержит исходные/целевые условия, версии, отсортированный отпечаток затрагиваемых
активных записей, число логических писем и сбросов ответов, каноническую команду.
Он не удерживает места и не является разрешением обойти проверки.
Подтверждение принимает previewId и Idempotency-Key; сервер под блокировкой студии
сверяет фактические условия и состав, повторяет проверки и выполняет сохранённую
команду. Любое существенное изменение требует нового preview, истечение даёт 409.
Число уведомлений равно числу затронутых активных записей, не числу уникальных
семей: два ребёнка одной семьи остаются двумя логическими событиями.

Повтор с тем же ключом и телом возвращает исходный результат без новых писем,
проверка уже сохранённого результата идёт до отказа из-за использованного preview.
Новый ключ не делает уже применённый preview повторно применимым.

Перетаскивание целой Session на desktop только заполняет время и открывает preview.
Предлагаемая сетка — 15 минут; точное время остаётся доступно через форму.
Растягивание длительности жестом и drag отдельного ребёнка не требуются.
Исходная позиция до успеха остаётся сохранённой; pending-проекция имеет явную метку.
На touch обычная прокрутка не захватывается; кнопочная альтернатива полная.

Альтернатива: сохранять сразу после drop. Отклонена из-за риска переноса всей
группы и отправки писем случайным жестом. Альтернатива одному серверному preview —
локальный расчёт последствий; отклонена из-за параллельной работы ADMIN.

### 3. Независимая ревизия условий и ответ клиента

В Booking добавить `attendanceRevision` (начально 1), nullable `clientConfirmedAt`,
`clientConfirmedRevision`, `invitationIssuedAt`; наружу дать `clientResponse`
(`AWAITING_RESPONSE`/`WILL_ATTEND` для CONFIRMED, null для прочих), время и признак
отправленного приглашения. Для старой CONFIRMED без приглашения показывать
«Ответ не получен · ссылка ещё не отправлена», без ложного заявления о рассылке.

Ответ действителен только если revision совпадает с текущей. Административный
статус и occupied подсчитываются по прежним PENDING/CONFIRMED, независимо от ответа.
Ни истечение разрешения, ни очистка письма не меняют occupied.

В таблице разрешений хранить hash SHA-256 от CSPRNG 32-byte base64url-секрета,
bookingId, parentId, назначение `ATTENDANCE_CONFIRM`, attendanceRevision,
отпечаток email получателя, receiverAuthVersion, generation окружения,
issuedAt/expiresAt/consumedAt/revokedAt и eventId. TTL — min(72 часа, startsAt).
Открытый секрет нужен только при выдаче, шифровании письма и отправке.

При переносе Booking в другую Session либо изменении начала/окончания, названия
или формата Session увеличить attendanceRevision у затронутых активных записей,
сбросить текущий ответ, отозвать все разрешения/контексты старой ревизии.
Для будущих CONFIRMED выпустить новые приглашения в той же транзакции;
PENDING получает только своё письмо о переносе. При отмене, отклонении и EXPIRED
отозвать разрешения, очистить текущий ответ, историю сохранить в аудите.
Вместимость и OPEN/CLOSED без других изменений ревизию ответа не меняют.

Проверка текущего verified email и authVersion при каждом доступе автоматически
отзывает доступ после восстановления аккаунта/смены получателя. Изменение email
не реализуется заново: если/когда такая операция доступна, она должна менять
привязку и требовать нового подтверждённого адреса. Восстановление аккаунта
инвалидирует ссылку, но само по себе не отменяет уже принятое намерение на те же условия.
Событие identity об отзыве доступа обрабатывается до commit и записывает revoked_at
разрешений; при запуске нового поколения также фиксируется отзыв несовпадающих grants.

Отзыв и сброс выполняются внутри общих доменных путей, включая старые PUT/action
эндпойнты. Новые preview-команды используют те же сервисы. Иначе старый frontend
мог бы оставить действующую ссылку на старое время.

Альтернатива: один дополнительный Booking.status либо обычный optimistic version
в роли ревизии согласия. Отклонены: смешиваются решения ADMIN/клиента или сброс
вызывают несущественные изменения. JWT отклонён: отзыв и одноразовость всё равно
потребуют БД, которая уже существует.

### 4. Ограниченный browser-контекст без входа

Публичная оболочка — `/lastochka/booking/confirm#token=...`; она не использует
Workspace-guard, не требует auth и не содержит приватных данных в SSR HTML.
До загрузки приложения/аналитики bootstrap читает fragment в память, удаляет
его через history.replaceState и не переносит секрет в router state/storage.
Для этого маршрута не подключаются сторонние ресурсы, общие telemetry hooks
с URL/body и service-worker cache. JS-ошибка после удаления не выводит секрет;
повторный переход возможен из письма. Без JS показывается читаемая инструкция
включить JS или связаться с администратором, без автоматического действия.

Последовательность отдельного пространства API:

1. GET `bootstrap` создаёт короткий непривязанный контекст и CSRF.
2. POST `exchange` с секретом в body, CSRF и допустимым Origin проверяет разрешение
   без consume, вращает идентификатор контекста и связывает его с одним grant.
3. GET `view` возвращает только разрешённые поля и непрозрачный `viewNonce`,
   связанный с grant/revision/контекстом, после повторной проверки актуальности.
4. POST `confirm` принимает только viewNonce и CSRF; bookingId выбирается сервером.

Контекст хранится в БД с SHA-256-хешем cookie-секрета и имеет абсолютный TTL
15 минут, ограниченный сроком grant. Cookie отдельная, host-only, HttpOnly,
Secure, SameSite=Strict, Path=`/lastochka/api/v1/public/booking-confirmation`.
Локальный HTTP допускает Secure=false только в явно локальном loopback-профиле;
HTTPS-приёмка проверяет production-атрибуты. Обычная cookie входа не меняется.
CSRF хранится/проверяется отдельно от аккаунтного Spring Session; для этих POST
задаётся точечный механизм, а не глобальное отключение CSRF. Допустимый origin
берётся из доверенной конфигурации, не из Host. Никакой SecurityContext/FULL
не устанавливается, даже если получатель уже вошёл другим пользователем.

Ссылка — ограниченное bearer-разрешение; пересылка даёт получателю те же права.
IP/User-Agent не используются как обязательная привязка: почтовый webview
и переход на мобильную сеть не должны ломать сценарий.

Повтор exchange действующего неиспользованного grant допустим и не расходует его.
После confirm grant consumed. Старый активный контекст может получить текущий
минимальный результат/идемпотентный ответ до своего TTL, но новый exchange по
consumed grant запрещён. При любой инвалидации отказывают и старые контексты.
viewNonce не позволяет вкладке A подтвердить запись B после замены общей cookie
переходом по другой ссылке; несовпадение даёт 409 `CONFIRMATION_CONTEXT_CHANGED`.

Минимальное имя берётся только из отдельного проверенного поля givenName,
если оно существует; иначе «Ваш ребёнок». Не добавлять сбор нового обязательного
имени/медицинских данных и не извлекать фамилию эвристикой из текущего name.

Альтернативы: magic login или открытый `/bookings/{id}` без сессии. Отклонены:
полномочия шире требуемых. Одношаговый GET-confirm отклонён из-за сканеров писем.

### 5. Транзакции, ошибки и ограничение частоты

Confirm и все административные изменения используют одну последовательность
блокировок: блокировка студии → аккаунт получателя при необходимости → booking
→ grant/ограниченный контекст. Действующие identity-транзакции не должны брать
эти блокировки в обратном порядке; authVersion/email перепроверяются перед записью.
Одноразовость обеспечивается условным обновлением grant и уникальным аудитом
на `(bookingId, attendanceRevision, ATTENDANCE_CONFIRMED)`, не таймером в браузере.
Подтверждение сохраняет ответ и аудит одной транзакцией, отдельного письма
«вы подтвердили» в этом объёме нет. Повтор из двух допущенных контекстов той же
ревизии получает WILL_ATTEND без второго события. Ошибка не потребляет grant.

Если сначала прошёл confirm, перенос очищает его; если сначала перенос — confirm
отклоняется. Аналогично отмена. Существующая coarse-grained блокировка приемлема
для одного зала, общий рефакторинг конкуренции не нужен.

Публичные ошибки invalid/expired/revoked/consumed/new-context унифицированы в
400 `CONFIRMATION_UNAVAILABLE`, без ID и деталей. CSRF/origin: 403; смена показанного
контекста: 409; rate limit: 429 с Retry-After. При неизменённом действующем контексте
повтор confirm возвращает 200 с текущим результатом. Аккаунтные API сохраняют 401/403.

Предлагаемые настраиваемые лимиты: bootstrap 30/IP/минуту, exchange 10/IP/минуту,
confirm 10/контекст/минуту; повторная отправка 1/запись/минуту и 5/запись/час
с дополнительным пределом 20/ADMIN/час. Счётчики не хранят сырой секрет;
лимиты действуют согласованно между backend-процессами и не блокируют аккаунт.
С доверенных proxy принимается IP только при явно настроенной цепочке.

На странице и персональных API: Cache-Control: no-store, Referrer-Policy: no-referrer,
запрет framing через CSP frame-ancestors 'none', ограниченная CSP для собственных
ресурсов. Токен, Cookie, CSRF и чувствительные body исключаются из request/error logs,
трасс и отчётов; noindex добавляется как вспомогательное поведение, не авторизация.

### 6. Письма, секретный outbox и восстановление

Выдача grant и enqueue одного письма — часть одобрения/переноса. ADMIN resend
использует обычный вход, CSRF, expectedVersion/идемпотентность и лимиты; он отзывает
прошлые grant/контексты, но не сбрасывает уже принятый ответ неизменённой ревизии.
Клиенту с недействительной ссылкой предлагается связаться с администратором;
публичная форма ввода email для рассылки не добавляется.

Существующий plaintext body outbox не подходит для хранения новых секретов.
Добавить nullable encrypted-payload/key-id/nonce/version для новых attendance-писем;
в body таких событий оставлять только несекретную заглушку. Использовать AES-256-GCM
со случайным уникальным nonce на payload и eventId как authenticated associated data.
Ключ берётся из внешнего секрета конфигурации, отдельно от БД/backup; не включается
в Git, image, командную строку и вывод. Поддерживать key-id для расшифровки событий
на период ротации. Включение функции без активного ключа запрещается с безопасной
ошибкой конфигурации. Старые письма продолжают использовать прежний формат.

Worker расшифровывает только в память при отправке, сохраняет eventId/Message-ID
и тот же secret при retry. Перед отправкой проверяет grant/revision; заведомо
устаревшее событие получает SKIPPED и не блокирует последующие события aggregate.
Отзыв уже переданного SMTP письма невозможен; безопасность даёт отказ grant.
CAPTURED payload очищается в пределах 24 часов от acceptedAt; прочий payload —
в пределах 24 часов после expiry/revocation, с минутным запасом для периодического cleanup. Для старых ошибок после очистки
оператор делает новый resend, а не восстанавливает payload и TTL.
Cleanup идемпотентен, работает после перезапуска с backlog, сохраняет метаданные.
MailHog хранит расшифрованные письма только в закрытой среде; для новых писем
реализовать документированную очистку не позже семи суток, без удаления чужих писем.

Для запрета оживления ссылок из старого backup ввести внешний непустой
`confirmation-generation` (случайный UUID конфигурации). Grant/context/preview
привязаны к generation; после любого восстановления БД или отката на старый backend
оператор обязан сменить generation до включения функции. Старые grant не принимаются,
новые выдаются только явным действием. Шифровальные ключи и generation имеют
разные назначения; generation не является секретным криптографическим ключом.

Альтернатива: хранить только hash и восстанавливать секрет из него для SMTP retry.
Невозможна; хранить неизменный payload требуется, поэтому он шифруется и очищается.

### 7. Контракт и границы модулей

Scheduling отвечает за календарь и ресурсы, bookings — за состав, перенос ребёнка,
attendanceRevision/grant/контекст и смысл ответа, notifications — за доставку
зашифрованного payload и очистку. Контроллеры, DTO и persistence остаются раздельными
по Kotlin-правилам проекта. UI не держит ручную копию транспортных DTO.

Предлагаемые новые логические пути (все под `/lastochka/api/v1`):

| Метод и путь | Доступ и назначение |
| --- | --- |
| GET `/admin/calendar?from&to` | ADMIN, полный диапазон ≤7 суток, максимум 1000 |
| GET `/admin/sessions/{id}/participants?page&size` | ADMIN, собственный полный постраничный состав |
| GET `/admin/bookings/{id}/transfer-targets?from&to&format&page&size` | ADMIN, диапазон ≤93 суток, size ≤100 |
| POST `/admin/sessions/{id}/move-preview` | ADMIN+CSRF, предлагаемое новое время |
| POST `/admin/bookings/{id}/transfer-preview` | ADMIN+CSRF, выбранное targetSessionId |
| POST `/admin/move-previews/{id}/confirm` | Тот же ADMIN+CSRF, Idempotency-Key |
| POST `/admin/bookings/{id}/attendance-invitations` | ADMIN+CSRF, expectedVersion, Idempotency-Key |
| GET `/public/booking-confirmation/bootstrap` | Без входа, только контекст/CSRF |
| POST `/public/booking-confirmation/exchange` | Контекст+CSRF+Origin, secret в body |
| GET `/public/booking-confirmation/view` | Ограниченный контекст, минимум сведений |
| POST `/public/booking-confirmation/confirm` | Ограниченный контекст+CSRF+Origin, viewNonce |

Пути и DTO экспортируются из backend, затем генерируются в frontend. Security
явно проверяет каждую публичную операцию; широкое permitAll не является проверкой
grant. Существующие пути/запросы не меняют обязательность и семантику.
Счётчики, feature flags и пределы не раскрываются в пользовательском UI как
внутренняя архитектура: клиент получает понятную причину и следующее действие.

## Risks / Trade-offs

- Пересылка письма передаёт право ответа → минимальные данные/права, ограниченный
  срок и честный аудит «по ссылке», без гарантии проверенной личности.
- XSS в общем origin может украсть секрет до удаления → ранняя обработка fragment,
  CSP, отсутствие сторонних скриптов; отдельный origin не вводится в этом изменении.
- Технический предел календаря → явная ошибка и сужение периода до дня вместо усечения.
- Coarse-grained блокировка → короткие транзакции, без SMTP внутри; нагрузка одного зала.
- Утечка DB backup → payload зашифрован, ключ отдельно, ограниченные сроки/внешняя
  generation; backup и MailHog всё равно требуют закрытого доступа.
- Потеря ключа → queued-письма не расшифровываются; безопасная ошибка, смена ключа
  и новые приглашения, без восстановления секрета или автоматического входа.
- Сканер способен выполнять JS и отправлять формы → GET/preview безопасны и нет
  авто-submit, но активного сканера с имитацией нажатия невозможно отличить от
  владельца bearer-ссылки без дополнительной проверки; это ограничение модели.
- Небезопасный rollback → обязательное отключение функции и смена generation,
  сохранение данных/аудита и запрет destructive down-migration.

## Migration Plan

1. До реализации прочитать применимые Kotlin/React skills, сохранить чужие изменения.
   Добавить аддитивные миграции: nullable поля ответа, grants/contexts/previews,
   уникальность аудита, encrypted outbox, индексы/метаданные очистки и лимиты.
   Seed не запускать. Старые CONFIRMED не получают ответ «Приду» или письма автоматически.
2. Ввести `attendance-confirmation.enabled=false` по умолчанию. Подготовить внешний
   keyring и generation. При выключении все публичные grant-операции безопасно
   недоступны; обычные кабинеты продолжают работу, новые секреты не выдаются.
3. Локально проверить backend с предыдущим frontend, затем новый frontend с новым
   контрактом. Старые команды переноса должны сбрасывать новые ответы/разрешения.
   Проверить реальный PostgreSQL и настоящий SMTP в отдельный закрытый MailHog.
4. После локальной готовности отдельно запросить серверную поставку. Её порядок:
   backup/проверки → backend с выключенной выдачей → frontend с новым маршрутом
   → настройка ключей/generation → включение → синтетическая HTTPS-приёмка.
   Существующие записи приглашаются только явным ADMIN resend, без массовой рассылки.
5. При откате frontend на версию без публичного маршрута сначала выключить
   confirmation и отозвать текущую generation; клиенты получают временную
   недоступность и контакт администратора. При откате backend также отключить
   функцию и сменить generation перед последующим включением. Миграции не удалять,
   ответы и аудит не стирать. Календарь можно откатить независимо при совместимом API.
6. После восстановления backup обязательно новая generation; сверить расписание,
   аудит и outbox до повторной выдачи. Автоматически пересылать старые секреты нельзя.

## Open Questions

Нет блокирующих продуктовых вопросов. Точные размеры панелей, подписи пустых
состояний и визуальные акценты уточняются при реализации в рамках спецификаций.
72 часа/15 минут/5 минут, пределы и лимиты выше — явные плановые значения;
изменение их внешнего поведения требует согласованного обновления specs/design/tasks.

Пользователь разрешил поставку на существующий play-and-say.ru/lastochka с
сохранением данных. Порядок Migration Plan применяется к двум образам 0.5.0.

generation создаются в закрытой server env, не в пакете. Перед миграцией — backup
и отпечатки исходных колонок каждой бизнес-таблицы, поскольку V8 добавляет колонки.

generation; V8 и бизнес-данные сохраняются, destructive down-migration не нужна.
