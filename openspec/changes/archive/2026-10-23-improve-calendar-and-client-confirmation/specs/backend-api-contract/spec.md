## Purpose

Описывать типизированные операции полного календаря, управляемых переносов
и ограниченного подтверждения клиента с явными правами и совместимостью поставок.

## ADDED Requirements

### Requirement: Поставка на существующий тестовый сервер с сохранением данных
По отдельному поручению пользователя серверная поставка SHALL использовать готовые
Linux/amd64 backend/frontend образы, свежую проверенную резервную копию и сравнение
существующих бизнес-строк. Порядок SHALL быть backend с выключенной функцией,
совместимый frontend и затем включение с внешними keyring/generation. Seed и
массовые приглашения существующим семьям SHALL не запускаться. MailHog SHALL
оставаться закрытым без внешней доставки; проверочные данные SHALL удаляться
точечно с защитой чужих записей. Откат SHALL сохранять V8/данные и предварительно
отключать функцию с отзывом generation.

#### Scenario: Публичная приёмка календаря и анонимной ссылки
- **WHEN** оба образа поставлены на существующий HTTPS preview
- **THEN** оператор проверяет полный календарь, оба переноса и SMTP-письмо → просмотр без входа → «Приду», затем удаляет только свои fixtures и сверяет исходные аккаунты/пароли/роли/ключи/контент и соседние сайты

#### Scenario: Откат после включения
- **WHEN** требуется вернуть предыдущие совместимые образы
- **THEN** оператор сначала отключает confirmation и отзывает generation, сохраняет бизнес-данные/аудит и не выполняет destructive down-migration или down -v

### Requirement: Контракт административной повестки и переносов
OpenAPI SHALL описывать отдельную полную выборку календарного периода, полный
состав выбранного занятия, независимый поиск целей переноса и два вида переноса.
Контракт SHALL документировать границы диапазонов, защитные пределы, сортировку,
неполучение частичного результата как успешного полного, версии, срок предпросмотра,
изменяемые условия, последствия и ключ идемпотентности финальной команды.
Превышение предела SHALL иметь отдельный машиночитаемый код ошибки.
Все эти операции SHALL требовать действующего ADMIN и CSRF для POST.

#### Scenario: Устаревший предпросмотр
- **WHEN** ADMIN подтверждает перенос с истёкшим или изменившимся предпросмотром
- **THEN** API возвращает 409 с устойчивым кодом и не выполняет часть операции

### Requirement: Отдельный контракт ограниченного подтверждения
OpenAPI SHALL явно разделять bootstrap без данных записи, обмен секрета,
минимальное представление одной записи и POST «Приду». Ограниченная сессия SHALL
не считаться обычной сессией PARENT/ADMIN. Контракт SHALL описывать CSRF,
cookie, срок, привязку к показанному контексту, безопасные повторы и отсутствие
возможности выбирать произвольный bookingId в подтверждающей команде.
Неверные, истёкшие, отозванные и использованные разрешения SHALL возвращать
одинаковую ошибку 400 `CONFIRMATION_UNAVAILABLE` без сведений о записи;
ошибки CSRF SHALL давать 403, устаревший контекст страницы 409, ограничение частоты 429.

#### Scenario: Обычный API с ограниченной cookie
- **WHEN** клиент передаёт только cookie подтверждения в запрос кабинета
- **THEN** API не считает его вошедшим родителем или администратором

### Requirement: Аддитивность и генерируемые типы
Новые операции и поля ответа клиента SHALL экспортироваться из backend OpenAPI
и генерироваться в TypeScript без ручных транспортных DTO. Старые операции,
статусы и обязательность полей запросов SHALL сохранять совместимость с прежним
frontend на окно rollout. Существующие команды изменения времени/переноса SHALL
также выполнять отзыв разрешений и сброс ответа, чтобы старый frontend не обходил
новые инварианты. Старый интерфейс SHALL не блокироваться отсутствием нового поля в своём клиенте.

#### Scenario: Старый frontend переносит запись
- **WHEN** после обновления backend предыдущий frontend выполняет прежнюю команду переноса
- **THEN** операция соблюдает прежний контракт и новые правила отзыва/сброса ответа, не оставляя действующую старую ссылку

#### Scenario: Повторная генерация
- **WHEN** контракт экспортирован и клиент сгенерирован повторно без изменений backend
- **THEN** артефакты воспроизводимы, typecheck проходит и отдельные ручные версии DTO отсутствуют
