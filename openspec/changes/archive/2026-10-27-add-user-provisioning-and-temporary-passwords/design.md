## Context

Мотивация и состав изменения — в proposal.md. Уточнение пользователя: механизм пароля общий для любых будущих пользователей, но сейчас допускается создание только ADMIN. Нынешние admin-access и openspec/config.yaml фиксируют создание/сброс только оператором; дельта этого изменения явно расширяет границу и не включает будущие роли.

В identity уже есть Account, PasswordPolicy, auth_version, SessionVersionFilter, отзыв challenge и закрытый AdminAccessBootstrap. AuthView различает только ANONYMOUS/FULL; LoginSessionService выдаёт парольному входу административные полномочия. SecurityConfiguration разрешает группу auth-маршрутов широко, а WebAuthn требует аутентификации. Поэтому одной проверки в React недостаточно. В accounts сохраняется обязательный технический email principal для совместимости старых ключей; пользовательский email и почта не нужны. Исходная локально документированная схема — V13; перед реализацией проверить актуальные миграции. Сервер этим предложением не исследован и не менялся.

План артефактов: proposal → три delta-spec → design → tasks → строгая проверка. Ни одна задача реализации в этом этапе не считается выполненной.

## Goals / Non-Goals

**Goals:**

- Отделить состояние пароля аккаунта от модели ролей и политики административного допуска.
- Использовать существующие хеширование, проверку версии сессии, CSRF и аудит; закрыть все пути обхода через auth/WebAuthn и старые вкладки.
- Сохранить текущие аккаунты и сессии без массового сброса, обеспечить проверяемые конкурирующие смены и адресные операции.

**Non-Goals:**

- Добавление ролей, универсальный конструктор прав, обычные кабинеты, публичная регистрация, переименование логинов, удаление/отключение аккаунтов.
- Почта, автоматическая доставка паролей, генератор паролей, история старых паролей и изменение действующей политики сложности.
- Серверная поставка в рамках подготовки предложения.

## Decisions

### 1. Состояние пароля принадлежит Account

Добавить аддитивной миграцией must_change_password=false и temporary_password_expires_at=null, с согласованностью: временный пароль требует дату истечения, постоянный её не имеет. Использовать auth_version как ревизию изменения секретов и существующий механизм отзыва; в безопасном административном представлении отдавать revision для конкурентного сброса. Не менять значения существующих строк, роли, admin_enabled, хеши, ключи или auth_version. Выбрать следующий свободный номер миграции после проверки дерева, не переписывать V13.

Общие операции назначения/смены работают с ID аккаунта и не содержат привязки к ADMIN. Проверка полномочий вызывающей стороны и разрешённых целевых ролей находится на границе административного сервиса: в текущей версии только ADMIN. При дальнейшем добавлении роли потребуется отдельно разрешить её создание, вход и полномочия; неизвестная роль никогда не получает ADMIN по умолчанию. Альтернатива с отдельной таблицей/сервисом временных ADMIN-паролей дублирует жизненный цикл и мешает расширению.

Для нового ADMIN создать уникальный непрозрачный технический principal вида UUID@accounts.lastochka.invalid; не принимать его от клиента и не выводить в UI. Это сохраняет существующий способ идентификации сессий без возврата email-функций и без миграции прежних principal/ключей. Адаптивный хешер и PasswordPolicy остаются общими для временного и постоянного пароля.

### 2. Назначение пароля и срок действия

Администратор вручную вводит временный пароль и передаёт владельцу вне приложения. Сервер не возвращает секрет даже при создании. Срок 24 часа и ограниченная сессия 15 минут — принятые плановые значения, поскольку пользователь не задавал сроки. Время вычислять через серверный Clock, проверять на входе и при обязательной смене; в момент expires_at пароль уже недействителен. Срок ограниченной сессии абсолютный: min(время входа+15 минут, expires_at); обращения его не продлевают. До смены владелец может повторно войти с ещё действующим временным паролем; после смены он больше не принимается. Потребление пароля при первом вводе вместо успешной смены отвергнуто: оно блокировало бы владельца при обрыве соединения.

Назначение временного пароля себе через административную операцию запретить; самостоятельная смена выполняется на странице безопасности. Операторская адресная процедура сброса также должна применять временный режим, а обычное повторное provision не должно менять существующие пароли. Это сохраняет путь восстановления при потере доступа всеми администраторами.

### 3. Ограниченное состояние входа проверяет сервер

Расширить AuthView состоянием PASSWORD_CHANGE_REQUIRED. Ограниченная сессия содержит идентификатор аккаунта, версию, generation и время начала, но не полномочия полного административного доступа и не признак недавнего подтверждения постоянного пароля. Выдать её с ротацией session ID. Добавить единый серверный барьер обязательной смены перед защищёнными маршрутами, включая WebAuthn и выдачу/использование challenge. Сохранить публичные endpoints и явно разрешить ограниченной сессии только me/csrf/change-password/logout. Широкое правило permitAll для auth/** не должно открывать новую операцию без её собственной проверки.

Повторно проверять must_change_password, auth_version, действующий допуск и ADMIN_ACCESS_GENERATION по текущим данным, а не по сохранённому клиентскому признаку. Прежняя отозванная сессия получает 401; действующая ограниченная при обращении к защищённому ресурсу — 403 PASSWORD_CHANGE_REQUIRED. Истёкшая ограниченная сессия инвалидируется. Ключи сохраняются, но любые операции с ними до смены запрещены. Простое скрытие меню или добавление клиентского флага отвергнуто как обходящееся прямым API/старой вкладкой.

### 4. Транзакции, конкурентность и аудит

Создание аккаунта/допуска/аудита — одна транзакция с уникальностью нормализованного логина на уровне БД. Повтор с тем же логином всегда даёт 409 и не выполняет upsert хеша. Не сохранять исходный пароль для идемпотентного ответа.

Смена и сброс используют ожидаемую auth_version: для собственной смены она берётся из сессии, для адресного сброса — из revision выбранной строки списка. Проверка текущего хеша, допустимости, версии/срока, замена хеша, сброс/установка временного режима, увеличение версии, отзыв challenge и аудит выполняются атомарно с блокировкой строки или условным UPDATE. Только один конкурентный запрос фиксирует результат, другой получает 409. В аудите создавать distinct-события создания, временного сброса, обязательной/добровольной смены с actorId и targetId. Пароли, хеши и тела запросов не записывать.

Повышенная версия сразу делает старые сессии недействительными через существующую проверку; физическую очистку серверных сессий выполнить штатным SessionRevocationRepository, не отзывать сессии других аккаунтов. Для чувствительных конкурирующих команд повторно проверить версию в транзакции перед фиксацией; согласовать порядок блокировок, чтобы сброс не позволял зафиксировать команду на уже отозванных полномочиях. Фактические проверки и предел для запросов, начавшихся до сброса, зафиксировать в отчёте реализации.

После собственной смены завершить транзакцию и создать свежую FULL-сессию в текущем браузере с новым session ID/CSRF, версия и парольное подтверждение соответствуют новому паролю; прежние сессии отозваны. Если ответ потерян или новая сессия не сохранилась, новый пароль уже действует и пользователь входит заново; откатывать пароль из-за ошибки HTTP нельзя. Неудачная проверка текущего пароля и лимиты не меняют состояние. Секрет проверяется сервером и для FULL-сессии — недавнего входа самого по себе для добровольной смены недостаточно.

### 5. Контракт и интерфейс

Предлагаемые пути под /lastochka/api/v1:

| Операция | Доступ и результат |
| --- | --- |
| GET /admin/users | FULL ADMIN; page/size, ограничение size≤100, сортировка createdAt/id; безопасные id/login/name/role/mustChangePassword/expiresAt/revision |
| POST /admin/users | FULL ADMIN + постоянный пароль ≤5 минут + CSRF; name/login/role=ADMIN/temporaryPassword; 201 без секрета |
| POST /admin/users/{id}/temporary-password | те же проверки + ожидаемая revision; подтверждённая цель, 200 без секрета |
| POST /auth/change-password | FULL либо действующая ограниченная сессия + CSRF; currentPassword/newPassword/confirmPassword; новый AuthView |

Пути внутреннего frontend — /admin/users и /account/change-password, с учётом basename. На странице «Безопасность аккаунта» — отдельная форма добровольной смены. В административной навигации — «Пользователи». В списке безопасные статусы «Пароль нужно сменить»/«Временный пароль истёк»; создание и адресный сброс в доступной форме с подтверждением цели. Клиент не делает секреты частью route loader/data, URL, toast, localStorage или sessionStorage. Назначенный пароль после успешного ответа очищается; при потере ответа предложить проверить список и при необходимости явно назначить новый, не повторять автоматически.

Русские тексты — через текущие каталоги и RussianForm; backend messages.properties остаётся источником ошибок. Уточнить fieldErrors для currentPassword/newPassword/confirmPassword/temporaryPassword. Для подтверждения недавнего постоянного пароля использовать существующий вход с сохранением безопасного пути возврата. После временного входа общий auth-контекст и AuthDialog направляют на обязательную форму; любые returnTo разрешать только локальные и выполнять после смены. Все формы очищают секреты при уходе/отмене; при ошибках поля паролей не эхоить сервером. На страницах с секретами/состоянием поставить no-store, исключить захват значений из диагностик/трассировок.

Полноценная административная работа без JS сейчас не является отдельной целью. При его отсутствии показать русское сообщение о необходимости JavaScript, не выдавая защищённого содержимого; публичная серверная форма заявки остаётся рабочей. Отдельная реализация будущих кабинетов не требуется.

### 6. Совместимость и границы отката

Новые поля и endpoints аддитивны для прежних постоянных аккаунтов. Расширение enum AuthView требует проверки старого клиента: ограниченное состояние не должно давать доступ даже если UI не умеет его отображать. Для старых вкладок предусмотреть безопасное предложение обновиться; не возвращать FULL ради совместимости.

Старый backend способен прочитать аддитивную схему, но может принять временный пароль как постоянный. Поэтому одного schema range недостаточно: добавить проверяемую возможность PASSWORD_LIFECYCLE_V1 в metadata образа/manifest и в штатную проверку релиза. После начала создания/сбросов допустима только сборка с этой защитой. Альтернатива автоматического обратного преобразования временных паролей отвергнута как ослабляющая доступ.

## Risks / Trade-offs

- Общий ADMIN может создавать других ADMIN → явно показывать роль «Администратор», требовать недавний постоянный пароль и подтверждение цели, вести раздельный аудит.
- Ручная передача пароля может потеряться → повторное адресное назначение с новым сроком; секреты не восстанавливаются из БД и не отправляются ботом.
- Сохранённый WebAuthn или широкое auth-правило может обойти ограничение → отрицательные интеграционные проверки каждого защищённого пути и challenge, а не только интерфейса.
- Ошибка ротации сессии после commit → пароль остаётся изменённым, восстановление через новый вход, без автоматического повторения команд.
- Параллельные операции и повторный запрос → версия аккаунта, единая транзакция и уникальность логина; проверить межзапросные гонки и отказ audit/БД.
- Старый образ не соблюдает временный режим → блокирующая проверка совместимости отката; не применять старый dump поверх новых данных.

## Migration Plan

1. При Apply установить актуальное дерево/схему и снимок исходных аккаунтов, прочитать применимые Kotlin/React skills. Добавить миграцию, проверить V13→новая схема и restore в изолированной БД с сохранностью исходных хешей/ключей/сессий.
2. Реализовать серверные проверки, UI, экспорт OpenAPI, генерируемые типы; выполнить сценарии из tasks.md. Не использовать пользовательские пароли для тестов, создать только отдельные fixtures и удалить их.
3. Обновить AGENTS.md, docs/project-status.md и openspec/config.yaml: новая возможность помечается локальной до подтверждённой поставки. Подготовить совместимые Linux/amd64 образы, manifest PASSWORD_LIFECYCLE_V1 и runbook с ограничением отката.
4. Серверная поставка требует отдельного поручения. При ней повторить read-only preflight, проверенный restore backup, контроль аккаунтов/данных, затем совместимый backend и frontend. Не назначать временные пароли исходным ADMIN в ходе приёмки; сохранить их прежний вход/ключи/сессии.
5. Публичную авторизованную приёмку проводить на отдельных тестовых ADMIN, проверить создание → временный вход → смена → повторный вход → сброс → отзыв, удалить только свои данные и сессии, повторно сверить исходные отпечатки. Заявки/очередь/публикации/DRAFT не терять.
6. Откат UI допускается только с сохранением серверного запрета обхода. Откат backend — на совместимую сборку с поддержкой временного режима; в остальных случаях исправление вперёд. Проверить это до включения новых операций.
