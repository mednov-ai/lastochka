## Context

Мотивация — в proposal.md. Реализация 0.3.0 уже работает на общем сервере;
требуется исправить frontend и сохранить аккаунты/контент/данные записи.

Проверено при подготовке плана:

- В пользовательском Chrome клик «Записаться на занятие» из #contacts и
  «Выбрать занятие» в мини-группе меняет URL на /lastochka/schedule, после чего
  показывается «Страница не найдена». Network фиксирует schedule.data → 404,
  при этом JS chunks получают 200. Reload исходного лендинга возвращает страницу.
- В frontend/server.mjs перед request handler стоит общий запрет путей,
  заканчивающихся расширением. Он отсекает и служебный .data-транспорт маршрутизатора.
  Успешный page.goto расписания в прежних тестах не доказывал работу Link-перехода.
- Нынешняя hero-сцена меняет масштаб всего с 0.98 до 1, карточки смещаются на 24 px;
  линия подхода очень тонкая. Это объясняет слабую заметность, но точную причину
  каждого рывка ещё нужно измерить trace: она не объявляется доказанной по скриншоту.
- У изображений нет отдельной hover-реакции. Портрет имеет 1122×1402 px, но в CSS
  получает width:100%, height:540px и общий object-fit:cover — пропорции несовместимы.
- Все CTA лендинга сейчас являются Link на /schedule и не используют существующий
  AuthDialogProvider. Он уже умеет открывать режим register с безопасным next.

## Goals / Non-Goals

**Goals:**

Связать движение с содержанием, сделать начало/середину/конец каждой сцены
различимыми, дать быстрый отклик медиа и действиям. Устранить подтверждённую ошибку
SSR-навигации, направлять гостя с CTA в регистрацию и сохранять намерение записи
после письма/входа. Проверять результат в собранном runtime, а не только Vite dev.

**Non-Goals:**

Замена концепции «Воздух», полная перестройка кабинетов, новая библиотека анимаций
как обязательная зависимость, видеофон/3D, новые фото или медицинские функции.
Фильтрация расписания по формату и новые параметры backend API не вводятся:
все форматные CTA ведут после входа к общему расписанию; ранее выбранный session ID
сохраняется. Редактор контента и production-почта не входят в изменение.

## Decisions

### 1. Сначала исправить транспорт навигации

Разделить обработку реальных статических файлов, API и служебных route-data
запросов. Распознанный .data-транспорт внутри base path должен доходить до React
Router request handler; неизвестные assets/routes по-прежнему получают 404.
Сохраняются проверка API на backend, запрет случайной HTML-подстановки для JS,
существующий /lastochka prefix и root Play&Say. Не выключать целиком защиту
статических путей и не заменять исправление window.location/reload на каждом CTA.

Регрессионный тест выполняет реальные клики от главной/#contacts, переключение
страниц после login, Back/Forward, прямой URL и reload. Проверяется production
frontend за proxy, включая .data-ответы. Vite используется для разработки,
но не подменяет проверку standalone server.mjs.

### 2. Три сцены вместо незаметного изменения декоративных деталей

Предлагаемый storyboard; диапазоны — отправная точка для визуальной настройки
при apply, а не отдельные пользовательские требования к числу пикселей.

| Сцена | Начало | Середина | Завершение |
| --- | --- | --- | --- |
| Главная | Изображение уже читается, мягкая рамка чуть уже финальной; тёплый фон | Рамка раскрывается примерно с 90% до 100% ширины, фоновый свет заметно смещается/усиливается | Спокойная завершённая композиция с постоянным CTA, без бесконечного движения |
| Подход | Три тезиса видны, начало единого пути выделено | Путь дорисовывается через три точки, последовательно усиливает номер/акцент каждого тезиса | Полный непрерывный путь и три читаемых тезиса; переход не зависит только от почти незаметной смены оттенка |
| Форматы | Все карточки доступны, есть небольшой ступенчатый сдвиг и менее раскрытая рамка изображения | Карточки последовательно раскрываются по локальному прогрессу | Ровный ряд/мобильный список с активными CTA и готовностью к hover/focus |

Изменение фона через opacity подготовленного слоя, движение через transform;
маски/скругления — только если укладываются в измеренный бюджет. Важный текст
не исчезает в ожидании скролла. Для линии проверить viewBox/границы пути, запас
под stroke и clip: дорисовка не должна выглядеть как разорванная волна.
Не добавлять длинные pinned-сцены и «пустые экраны ради анимации».

### 3. Один контроллер движения с предсказуемой геометрией

Сохранить небольшое решение на CSS и requestAnimationFrame без React setState
на каждом scroll. Геометрия измеряется отдельно от записи стилей; читаются
неподвижные layout-рамки, а не собственные уже трансформированные элементы.
Пересчёт объединяется после resize, загрузки медиа/шрифтов, изменения ревизии
контента и смены reduced-motion. В одном кадре обновляются только затронутые
активные сцены; observers/listeners/rAF освобождаются при уходе со страницы.

Scroll-прогресс непосредственно задаёт состояние: не накладывать на каждое
его обновление CSS transition, создающий запаздывание и рывки при смене направления.
Состояние при init/reload вычисляется сразу, без проигрывания заново от нуля.
Никакого самопроизвольного дрейфа после остановки. CSS scroll-driven API или
сторонний motion engine не обязательны: проблема здесь требует управляемой
композиции и измерений, а не смены библиотеки.

### 4. Hover/focus как отдельный слой

Scroll меняет внешнюю рамку/обёртку, hover — вложенное изображение/акцент: два
эффекта не перезаписывают один transform. Для hero и форматов — ориентир 1.03–1.05
для масштаба внутри безопасной маски, до 4 px смещения и 4–6 px движения стрелки,
180–260 ms ease-out. При уходе указателя состояние возвращается без скачка.
Для ссылки/карточки focus-within даёт такой же акцент и видимый focus ring.

Портрет тренера реагирует рамкой/подложкой, а не приближением с новой обрезкой.
Декоративные фигуры не получают tabindex/роль button. При coarse pointer действия
не ждут второго касания; reduced-motion отключает движение, оставляет цвет/контраст.

### 5. Портрет по исходным пропорциям

Убрать конфликт фиксированной высоты и object-fit:cover для тренера. Использовать
рамку с пропорциями около исходных 4:5, ограничением ширины и резервированием
размеров; изображение сохраняет исходное соотношение и безопасный запас сверху.
Если нужен иной размер рамки — contain с подходящей подложкой вместо обрезания
лица. Скругление/hover не должны пересекать верхнюю границу головы.

Проверять реальный исходник и портрет целиком, а не только отсутствие overflow:
375/390 и 1280/1440/1728/1920 px, разные высоты окна, hover. Текущий ресурс остаётся
иллюстрацией из концепции с подписью. Не выдавать её за новое фото студии.

### 6. Единый сценарий CTA без новой аутентификации

Использовать существующий AuthDialogProvider/AuthForm и общий компонент действия:

| Действие | Гость | Полноценная сессия |
| --- | --- | --- |
| Кнопки записи, включая три карточки и контакты | Register dialog, next=/schedule; доступно переключение на login | /schedule |
| «Войти» | Login dialog | Кабинет |
| «Посмотреть расписание» и footer «Расписание» | /schedule без регистрации | /schedule |

После регистрации показывается понятное ожидание подтверждения email. Безопасный
next/выбранный session ID хранится ограниченное время текущим механизмом возврата
и доступен после открытия письма в том же браузере/новой вкладке. Если намерение
недоступно/истекло, CTA-сценарий возвращает к расписанию, а не теряется в кабинете.
Проверить недоступный storage и невалидный внешний next: только внутренний fallback.
Пароль даёт FULL, WebAuthn доброволен. Подача заявки — отдельное явное действие
после выбора своего ребёнка и повторной проверки места; admin approval сохраняется.

Без JS у CTA действующий href на /auth/register?next=... внутри /lastochka.
В модальном варианте фон/scroll/focus сохраняются. Не вводить отдельную копию
формы, CTA-специфические пароли или обязательный WebAuthn.

### 7. Приёмка визуального результата и производительности

Проверять production SSR/client с прогретыми локальными изображениями и шрифтами,
Chromium, 60 Hz, 1440×900 и 375×900, CPU slowdown ×4; сохранить версию браузера
и стенд. Целевой бюджет: p95 межкадрового интервала ≤32 ms, доля интервалов >50 ms
≤1%, отсутствие задач обработчика scroll >100 ms и forced layout на каждом кадре.
Измерять реальную непрерывную wheel/touch-подобную прокрутку в обе стороны,
а не только отдельные scrollTo с ожиданием завершения. Значения бюджета относятся
к описанному стенду, не объявляются гарантией для любого устройства.

Сохранить видео и снимки 0/25/50/75/100% каждой сцены, hover до/после и портрет
на контрольных ширинах. Численно правильный --progress сам по себе не является
приёмкой: на записи должны быть различимы сцены и отсутствовать рывки. При
превышении бюджета упростить маску/эффект до transform/opacity, сохранив заметность.
Нужны также reduced-motion, без JS, touch, keyboard, якоря/reload и тест изменённой
ревизии контента. Ресурсы runtime берутся из Git, не из info.

## Risks / Trade-offs

- Насыщенные эффекты могут вернуть ощущение тяжёлой презентации → ограничить
  движение тремя смысловыми сценами и коротким hover, сохранить обычную прокрутку.
- Маски, цвет и большие перерисовки могут ухудшить плавность → подготовленные слои,
  transform/opacity, trace и упрощение эффекта при выходе за бюджет.
- Регрессия route data незаметна при прямом GET → обязательные клики на собранном
  frontend за proxy и просмотр сетевых ответов, включая открытые вкладки после rollout.
- Регистрация может потерять контекст после письма → единый безопасный next,
  bounded storage, проверка той же/новой вкладки и явный fallback к расписанию.
- Изменение контента может сломать кадрирование/границы сцен → резервирование размеров,
  локальная геометрия по стабильным id, statically allowed presets и fallback.

## Migration Plan

При apply сначала воспроизвести regression на текущем production runtime локально,
исправить .data-транспорт, затем CTA и визуальные сцены. Обновить storyboard,
AGENTS и сведения о приёмке. Собрать новый отдельный frontend image локально;
backend 0.3.0 и OpenAPI остаются прежними, если проверка не выявит необходимости.

На 139.100.236.101 сохранить текущую env/proxy и данные по runbook, развернуть
только Lastochka frontend и при необходимости собственный proxy. Сохранить прежние
hashed assets на окно совместимости. Не перезапускать чужие сервисы, не менять
TLS/ACME/root/RepairDevice и не запускать seed. Не сбрасывать семь аккаунтов,
добавленные тестировщиком ключи, семьи, записи или опубликованное наполнение.

На публичном URL без Basic Auth пройти CTA из hero, всех форматов и контактов,
регистрацию через отдельный временный аккаунт/MailHog, возврат к расписанию,
password-only login, просмотр расписания без входа, сохранность private API.
Временные данные удалять адресно, чужие записи не затрагивать. При сбое вернуть
предыдущий frontend image/proxy без отката БД; отметить, что старый image содержит
известную ошибку .data. Записать версии, проверки, визуальные материалы и ограничения.
