## Context

Форма постоянного расписания использует общий компонент для создания и изменения правила. API требует положительную вместимость, которая сохраняется в правиле, занятиях и снимках; старые правила могут иметь размер, отличный от 8.

На desktop-скриншоте выпуска `0.21.1` форма занимает только часть широкого окна, а кнопки `−30` и `+30` смещены относительно поля длительности и соседних полей. Общий селектор кнопок блока занятия также затрагивает кнопки внутри составного поля длительности; дополнительные общие правила подписей и полей влияют на вертикальные отступы. Существующее окно используется и другими редакторами, поэтому исправление его общих правил требует проверки затронутых сценариев.

## Goals / Non-Goals

**Goals:** исключить ввод размера из формы, сохранить корректность создания и изменения правила и придать форме расписания продуманную, ровную композицию на desktop и mobile.

**Non-Goals:** удаление данных, миграции, изменение других форм или переопределение сохранённых значений.

## Decisions

Для нового расписания frontend передаёт прежнее внутреннее значение 8, чтобы не менять контракт и поведение существующего backend. При редактировании он передаёт точную сохранённую вместимость правила, а не значение по умолчанию. Поле и связанная с ним доступная ошибка удаляются из формы. В остальных сценариях хранения и отображения значения сохраняются прежние правила.

Для desktop спроектировать окно с соразмерной шириной и высотой и понятной иерархией; не оставлять большой пустой области рядом с короткой формой. В строке занятия выстроить день недели, начало и длительность по общей линии. Поле длительности и обе кнопки изменения должны восприниматься как единое управление с одинаковой высотой и выравниванием; действие удаления отдельного занятия не должно ломать эту сетку. При уменьшении доступной ширины поля должны предсказуемо перестраиваться без обрезания и наложения. Сохранять читаемые подписи, видимый фокус и удобную область нажатия, включая увеличение текста.

Перед изменением CSS применить `frontend-design` к самой форме, затем проверить получившуюся композицию по `web-design-guidelines` и через `playwright-cli`. По возможности ограничить новые стили формой постоянного расписания и составным полем длительности, чтобы не нарушить прочие редакторы. Проверять форму с одним и несколькими занятиями, а также предпросмотр и состояние конфликта, не подменяя реальные данные примерами в продукте.

## Risks / Trade-offs

Внутреннее значение остаётся техническим параметром совместимости; оно не означает доступные места. Ошибочное применение 8 при редактировании изменило бы ранее сохранённые данные, поэтому проверка обязана использовать правило с другим значением. На test и production изменения не выпускаются без отдельного запроса.

Сужение окна без проверки длинного предпросмотра, нескольких строк и ошибок может ухудшить управление. Ширина, высота и прокрутка должны проверяться вместе с сохранением фокуса и доступности всех действий; изменения общих селекторов — сопровождаться регрессионной проверкой других форм. Реальные устройства и технологии доступа нужно отмечать отдельно от браузерной эмуляции.
