## Context

`security.tsx` размещает карточки пароля и ключей в общей сетке, а `AlfaSettings` — отдельно под ней. У банка карточка растянута, ввод ограничен `34rem`, а действия находятся вне формы и на скриншоте имеют другую ширину; состояние и действия не образуют ясной группы. Текущий `candidate` допускает nullable `merchantLogin`; в сохранённых версиях он зашифрован вместе с API-реквизитами. Подтверждение доступности отмены для данного мерчанта отсутствует: тестовый шлюз вернул код 8. Предыдущее изменение `integrate-alfa-test-payments` не завершено и содержит собственные требования.

## Goals / Non-Goals

**Goals:** согласовать банковскую настройку со страницей, убрать лишний ввод, сохранить защитные и версионные границы и дать конкретные критерии вёрстки.

**Non-Goals:** выпуск, подключение production, включение тестового шлюза или банковской отмены, возврат средств, изменение паролей, ролей и разрешений в банке.

## Decisions

1. **Композиция.** Сохранить текущую сетку пароля и ключей. Ниже расположить отдельную общую область «Тестовое подключение Альфа-Банка» в той же внешней сетке и с теми же отступами. На достаточной ширине слева — компактная сводка состояния и последнего изменения, справа — форма и её действия; границу двух зон задаёт пространство, а не вложенная декоративная карточка. На мобильном — один столбец в порядке состояние → поля → подтверждение → сохранение → проверка/отключение. Не ставить три несвязанные крупные кнопки друг над другом на широком экране.

   ```text
   desktop: [ Сменить пароль          ] [ Ключи доступа            ]
            [ Тестовое подключение Альфа-Банка                    ]
            [ Состояние подключения    | Тестовый логин            ]
            [ последнее изменение      | Тестовый пароль           ]
            [                          | [ ] Тестовая среда        ]
            [                          | Сохранить  Проверить       ]
            [                          | Отключить подключение     ]

   mobile:  [ Сменить пароль ] [ Ключи доступа ]
            [ Тестовое подключение / состояние ]
            [ Логин / пароль / подтверждение   ]
            [ Сохранить / проверить / отключить]
   ```

   Все надписи, поля и действия выровнены по левому краю; ширина формы и ряда действий определяется одной колонкой. Сохранение — основное действие, проверка — второстепенное, отключение — спокойное отдельное действие с сохранением подтверждения. Неактивное действие не должно выглядеть как идущее выполнение; причину недоступности показывать кратко, когда она известна. Альтернатива — три равные карточки в одной сетке: она смешивает личную безопасность и банковскую интеграцию и непредсказуемо растягивает высоту; отдельная страница добавила бы навигацию без необходимости.

2. **Визуальные опоры.** Использовать действующую типографику кабинета Arial/Helvetica и существующие токены `#203637` (текст), `#526b6b` (вторичный текст), `#ffffff` (карточка), `#cde4e0` (граница), `#167f82` (основное действие), `#f7fbfa` (фон). Заголовок банка и внутренние отступы согласовать с `security-layout`; метку тестовой среды и состояние выразить словами, не полагаться только на цвет. Сохранить заметный фокус, тексты до 80 символов в строке, поддержать переносы, 200% текста и 320 px. Декоративные бейджи, банковский логотип и новые стили страницы не нужны. Альтернатива — яркий отдельный брендинг банка: он перетягивает внимание с настройки и визуально отделяет её от интерфейса «Ласточки».

3. **Скрытое поле и данные.** Удалить поле и текст подсказки из формы; не показывать и не отправлять `merchantLogin` новым интерфейсом. Текущий сервер уже принимает отсутствие/null для новой версии, поэтому первое предпочтение — совместимый frontend без миграции и без изменения API. Новая версия с отсутствующим значением не наследует его из другой версии и не выводит из имени API-пользователя. Ранее созданные зашифрованные активные/исторические версии и связанные попытки сохраняются без переписывания, включая имеющееся значение; при замене создаётся новый неактивный кандидат по прежним правилам. Старый frontend может продолжить посылать параметр в рамках действующего контракта. Не удалять параметр API или структуру зашифрованных данных без отдельного совместимого плана. Альтернатива — автоматически обрезать `-api`: выдаёт предположение за проверенный параметр и не решает отказ в праве.

4. **Отмена и параллельные изменения.** Текущие backend-проверки и выключенный флаг отмены сохранить: без подтверждённого параметра, права банка и необходимых существующих условий отправка не допускается. Наличие исторического значения не является подтверждением и не меняет флаг. Согласовать `integrate-alfa-test-payments` при реализации до завершения/архивации: там отмена предусмотрена условно; текущий документ лишь убирает ввод и оставляет вопрос разрешения банковской отмены открытым. Не выдавать отсутствие кнопки или пустое поле за отмену заказа.

5. **Поведение формы.** Сохранить статус кандидата, активной настройки и выключенного режима; повторное подтверждение пароля в момент чувствительной операции, CSRF, блокировку двойной отправки, русские сообщения, очистку секрета после успешного сохранения и доступность только ADMIN. При исправимой ошибке и возврате из подтверждения не терять незавершённый ввод. Не маскировать сетевую ошибку под успешное подключение и не показывать сохранённые реквизиты.

## Risks / Trade-offs

- [Пользователь может ожидать, что отмена теперь работает] → показывать доступность операции достоверно; настройки банка и флаги не менять.
- [Новый кандидат без идентификатора отличается от старого] → не перезаписывать старые версии, тестировать открытые попытки и замену при включённой/отключённой настройке; не наследовать значение молча.
- [Длинные статусы, mobile и увеличение текста нарушат сетку] → проверить 320, 375, 430, 768 и 1440 CSS px, 200% текста, фокус и чтение ошибок в Chromium/WebKit.
- [Два активных OpenSpec-изменения описывают интеграцию] → при реализации согласовать затронутые требования и задачи `integrate-alfa-test-payments` без архивирования незавершённого изменения.

## Migration Plan

1. Проверить фактические контракты и данные без чтения секретов; сохранить совместимость старого и нового интерфейсов с сервером. При выборе frontend-only не требуется миграция БД.
2. Реализовать и проверить интерфейс на изолированных фиктивных данных, в том числе версии с историческим идентификатором и новую версию без него; проверить, что старый клиент и backend совместимы по предусмотренному контракту.
3. При отдельном запросе на выпуск — следовать проектной процедуре только для разрешённой среды с сохранением ADMIN и данных, проверкой совместимости открытой старой вкладки и явным откатом frontend. Этот документ не разрешает выпуск.
4. При необходимости отката вернуть прежний совместимый frontend; не восстанавливать БД и не менять сохранённые версии ради отката формы.
