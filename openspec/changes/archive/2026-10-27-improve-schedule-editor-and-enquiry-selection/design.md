## Context

25.10.2026 после начала Apply пользователь отдельно поручил поставку и публичные скриншоты. Итог — backend0.10.0/frontend0.10.1/V13; фактическая приёмка и откат описаны в docs/deployment/2026-10-25-schedule-editor.md.

Мотивация и границы продукта — в proposal.md. Осмотр 25.10.2026 выполнен на локальной сборке frontend0.9.10 с синтетическим backend; это не новая серверная приёмка. Скриншоты находятся в локальном, исключённом из Git каталоге artifacts/schedule-review-2026-10-25/ и не являются обязательной зависимостью реализации.

Сейчас AdminSession использует defaultValue; при открытии review форма размонтируется, возврат создаёт её из session и теряет ввод. Создание сразу закрывает панель, не выбирая период созданного занятия. Публикация — отдельная команда после повторного открытия. PUT опубликованного занятия немедленно меняет публичные параметры. Версия единственная. Enquiry.loader получает session из URL, но внутри формы нет подбора/замены; выбранные ID/version передаются скрытыми полями. EnquiryService уже фиксирует снимок и блокирует изменение расписания на время проверки/сохранения обращения. Эти свойства сохраняются.

Календарь администратора имеет полную ограниченную выборку, а публичный список — пагинацию, ограничение периода 93 дня и фильтрацию OPEN/CLOSED будущих занятий. LandingContent уже структурирован, однако отдельный редактор контента не реализуется этим изменением. Восемь ранее поставленных активных дельт (телефон, шапка, тема, фокус, анимация, удаление legacy) остаются действующими ограничениями.

## Goals / Non-Goals

**Goals:** единый сохраняемый редактор с отдельным публичным результатом; переиспользование представлений и оболочки; связь формы заявки с конкретным расписанием; проверяемая совместимость старых вкладок и данных.

**Non-Goals:** общий движок хранения любых страниц, универсальная схема всех будущих редакторов, произвольные HTML/CSS, возврат семейной модели, повторяющиеся занятия, массовое редактирование, автоматические решения по возрасту, реальная доставка/платежи. В этой работе доступен только редактор расписания; список возможных разделов в обсуждении не становится набором пустых рабочих экранов.

## Decisions

### 1. Общая оболочка, конкретные предметные редакторы

В Workspace появляется вход «Сайт» и выбранное подразделение «Расписание»; /admin/schedule остаётся действующим каноническим адресом редактора, общий вход может переводить на него. Заявки/оплата/безопасность остаются доступны. Реестр подключённых разделов задаёт заголовок, адрес и доступность; общие части отвечают за панель действий, состояние сохранения, защиту выхода и переключатель предпросмотра. В реестре сейчас только расписание.

Публичная карточка и метаданные занятия выделяются в общие компоненты для schedule, выбранного пожелания, подбора и предпросмотра. Компоненты принимают данные и режим действий, а не вызывают административные API. У будущих редакторов будут свои формы и серверные правила. Альтернатива — сразу универсальный конструктор блоков — существенно расширяет область риска без подтверждённой потребности.

### 2. Раздельные публичное состояние и черновик параметров

Существующие studio_sessions и её version остаются источником опубликованных условий и жизненного цикла DRAFT/OPEN/CLOSED/CANCELLED. Для нового занятия DRAFT продолжает быть штатным черновиком в studio_sessions. Для правок OPEN/CLOSED вводится отдельная запись session_edit_drafts на занятие: полный снимок редактируемых параметров, собственная version, baseSessionVersion, автор и время. Две версии нужны, чтобы сохранение черновика не делало уже выбранное публичное занятие устаревшим.

Один общий сохранённый черновик на занятие доступен ADMIN; оптимистическая версия предотвращает незаметное перетирание. Несохранённый ввод хранится только в памяти текущей формы. Автоматическое сохранение и хранение чувствительных форм в localStorage не вводятся. Сохранённый черновик не резервирует ресурсы: конфликты окончательно проверяются при публикации.

Новые операции проекта контракта: GET/PUT/DELETE /api/v1/admin/sessions/{id}/draft, POST .../{id}/draft/publish, GET .../{id}/history, POST .../{id}/history/{revisionId}/restore-draft. Сохранение проверяет expectedDraftVersion и expectedSessionVersion; отсутствие черновика для создания выражается явно через nullable expectedDraftVersion. Публикация проверяет обе актуальные версии под существующей блокировкой студии; проверяет дату/ресурсы/формат/возраст, обновляет studio_sessions и убирает применённый черновик в одной транзакции. Повтор команды возвращает исходный результат. DELETE удаляет только неопубликованные правки с проверкой версии и аудитом; публичное занятие не удаляется.

Изменение статуса приёма — отдельная команда. После закрытия/повторного открытия основание черновика считается устаревшим; UI показывает новую публичную версию и предлагает явно сохранить переоснованный черновик. После отмены или начала занятия публикация запрещена. Для CLOSED публикация параметров не открывает приём. Существующий PUT остаётся немедленным совместимым обновлением для старых вкладок, но новый редактор им не пользуется для OPEN/CLOSED. Такой PUT также делает прежнюю основу черновика устаревшей.

Альтернатива — только локальное состояние до публикации — проще, но не даёт настоящего «Сохранить черновик» и восстановления после повторного входа. Замена старого PUT на сохранение черновика сломала бы старые вкладки, поэтому не выбирается.

### 3. История использует существующий аудит

Действующие audit_events уже содержат aggregate_id, автора, время, before_state/after_state. Добавляются события операций черновика/публикации/восстановления, административная постраничная проекция разрешённых параметров; отдельная дублирующая история не создаётся. Объект истории явно различает сохранённый черновик и опубликованный результат. Старые события отображаются с отсутствующими новыми полями, пустая старая история не выдумывается.

Восстановление берёт снимок параметров только события этого занятия, проверяет принадлежность/версию схемы, создаёт обычный новый черновик на актуальной основе. Статус/ID/version/автор из старого снимка не восстанавливаются. Восстановление никогда не откатывает БД/заявки и не обходит запрет исторического или отменённого занятия.

### 4. Ввод управляется сохраняемой моделью формы

Одна модель формы живёт выше form/review/preview и хранит значения, ошибки, server baseline и dirty. Все переходы сохраняют модель. Сохранение не закрывает редактор; после ответа выбираются период/день занятия и его карточка. На компьютере форма и предпросмотр соседние, на узком экране — вкладки с доступными именами; действия видимы при прокрутке и не перекрывают поля/экранную клавиатуру. Закрытие формы с dirty предлагает сохранить/отбросить/остаться; закрытие вкладки использует beforeunload с обычными ограничениями браузера.

Дата нового занятия берётся из выбранного дня, исходная длительность — 50 минут как проектное значение, а не ограничение бизнеса. При редактировании вычисляется точная текущая длительность. Начало и длительность формируют endsAt в Europe/Moscow; переход суток подписывается. INDIVIDUAL даёт capacity=1, GROUP восстанавливает ранее введённую вместимость. Отмена вынесена в отдельное раскрываемое действие. Подтверждение публикации показывает отличия всех параметров, включая формат и возраст, а не только название/время.

### 5. Возраст — необязательные данные с аддитивной совместимостью

Добавляются nullable ageFrom/ageTo в занятие и снимок черновика: оба отсутствуют либо 0 ≤ ageFrom ≤ ageTo ≤ 17. Старые записи получают NULL/NULL; названия автоматически не переписываются. Возраст в заявке остаётся 0–17 независимо от рекламного диапазона; рекомендация не запрещает отправку и не фильтрует автоматически.

Старый PUT без возрастных полей сохраняет существующий диапазон. Для этого при реализации DTO обновления должен различать отсутствие поля и явное обнуление; новый контракт явно описывает очистку обоих полей. Создание старым клиентом без возраста даёт NULL/NULL. Полный снимок новой команды черновика всегда однозначен. Возраст добавляется в новые снимки пожелания, старые строки/сообщения не пересчитываются.

### 6. Один публичный источник для списка, подбора и предвыбора

schedule и форма используют публичные опубликованные данные, общую навигацию периода/пагинации и общие карточки. Публичная страница показывает OPEN/CLOSED, подбор только будущие OPEN. Используется серверная выборка с опциональным фильтром selectable=true; фильтр добавляется в существующий публичный список совместимо, по умолчанию сохраняется прежняя семантика OPEN/CLOSED. Лимиты/сортировка/page/total остаются явными; после загрузки страницы поздний ответ старого периода не заменяет новый. Нельзя отфильтровать только первую страницу и объявить остальную неделю пустой.

По умолчанию показана текущая неделя МСК без начавшихся занятий; дата задаёт неделю с понедельника по воскресенье. «Эта неделя» и «Следующая неделя» считаются от текущей даты МСК, соседние периоды выбираются стрелками; дальние даты — полем даты. Список группируется по датам, интервал компактен, у перехода суток подписана следующая дата. Общая заявка доступна из пустого/ошибочного состояния. Нет вычисления свободных мест.

Общий вход в enquiry показывает необязательное поле «Желаемое занятие» с вариантом «Помогите подобрать время». /enquiry?session=<id> сохраняется и сразу показывает выбранную карточку с «Изменить». Переход в подбор не сбрасывает контактную модель. Предвыбор недоступного занятия не заменяется молча общей заявкой: показывается причина и явный выбор продолжения.

### 7. Серверные действия подбора без JavaScript и идемпотентность

Форма остаётся progressively enhanced: выбранное пожелание, фильтр периода, пагинация и введённые поля передаются POST-действиями намерения выбрать/сменить период/подтвердить условия/отправить. Только намерение отправить вызывает EnquiryService.submit. Остальные ветви не требуют полной обязательной проверки контактных полей, используют formnovalidate, CSRF и no-store, возвращают серверно отрисованную форму; персональные данные не попадают в query string, журналы или localStorage. Поля телефона проходят через существующий phoneNational/phoneFromForm без потери раннего ввода и маски.

При однозначном конфликте server action сохраняет все введённые поля; актуальные параметры подтягиваются безопасно и применяются только отдельной командой пользователя. Новый payload после смены пожелания/принятия условий получает новый ключ. После неизвестного сетевого результата содержимое и прежний ключ сохраняются для повтора; интерфейс не обещает отсутствие уже созданной заявки и не заменяет ключ автоматически. Гарантия идемпотентности относится к одному логическому отправлению, не к разным осознанным заявкам.

Проверка OPEN/будущего времени/version и сохранение заявки/Telegram остаются под общей блокировкой студии, исключающей гонку с публикацией/закрытием/отменой. Для выбранного ранее занятия, ставшего недоступным, наружу отдаётся безопасный 409; отсутствующее/скрытое занятие не раскрывает закрытые данные. Новые HTTP-статусы точечно документируются для подачи заявки, обычный публичный GET отсутствующего занятия остаётся 404.

## Risks / Trade-offs

- [Две версии и старый клиент] → независимые draft/public версии, интеграционные гонки, прямой старый PUT не обходит новые проверки.
- [Сохранённые пересекающиеся черновики] → явно не считаются резервированием ресурсов; окончательная проверка на публикации, введённые данные сохраняются при отказе.
- [POST-подбор разрастается] → конечный набор намерений и один серверный renderer; проверки отсутствия преждевременной заявки и утечки контактов.
- [Различие предпросмотра и сайта] → общие компоненты, один набор форматирования и снимки desktop/mobile после реальной публикации.
- [Новые поля стираются старым PUT] → различать отсутствие/очистку, отдельные проверки старого payload с сохранённым возрастом.
- [Старая история содержит иные поля] → наружу отдаётся ограниченная предметная проекция, восстановление только разрешённых параметров.
- [Локальные результаты принимаются за серверную приёмку] → отдельный отчёт, синтетические fixtures и раздельные этапы реализации/поставки.

## Migration Plan

1. До Apply повторно прочитать AGENTS.md, статус, все действующие активные дельты и фактическую схему; сохранить существующую грязную рабочую копию. Проверить разрешённый набор изменяемых файлов.
2. Добавить следующую свободную аддитивную Flyway-миграцию: nullable возраст с CHECK, отдельные черновики с FK/версиями/индексами, необходимые индексы чтения истории. Не менять V1–V12 и не удалять данные. Проверить migration/restore от V12 на отдельной БД.
3. Реализовать backend и экспортировать OpenAPI/клиент. Сначала проверить старый frontend с новым backend, гонки и сохранность; новый frontend включать после backend с новыми API. Текущие публичные данные не меняются при одной миграции.
4. Выполнить локальную матрицу браузеров/языков/экранов, SSR/no-JS, auth/CSRF/версии, старые вкладки, снимки предпросмотра и сайта. Проверить исходные данные, удалить только собственные fixtures.
5. При отдельной разрешённой поставке — свежие backup/restore, проверка concept marker и schema range обеих сборок, immutable images, сначала совместимый backend, затем frontend; публичная приёмка и проверка ADMIN/контента/очереди/платёжных черновиков/старых assets. Shared Nginx/TLS/ACME/соседи не затрагиваются.
6. Откат frontend допустим на прежнюю принятую сборку при успешной проверке старого UI с новым backend; новые сохранённые черновики останутся в БД. Возврат старого backend допустим только при доказанной работе на новой аддитивной схеме и корректном schema range; иначе оставить новый backend и откатить frontend. Обратные миграции и старый dump поверх новых данных не применяются. V12 и новый предел схемы явно отражаются в упаковщике/отчёте.
