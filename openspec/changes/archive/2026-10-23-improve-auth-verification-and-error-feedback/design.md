## Goals / Non-Goals

**Goals:**
- Предсказуемое завершение email verification, в том числе при повторе запроса.
- Одинаковое правило нового пароля на обеих сторонах и отсутствие обхода через API.
- Один backend-источник текстов ошибок и единый безопасный контракт для клиента.
- Заметная доступная ошибка без дублей, потери фокуса или перекрытия модальным слоем.

**Non-Goals:**
- Email verification не создаёт парольную сессию. Проверенный ранее пароль
  и добровольный WebAuthn сохраняют свои существующие правила.
- RESET и «Приду» не получают автоматического подтверждения при открытии ссылки.
- Новая авторизация, обязательная смена паролей, новые языки, blacklist паролей,
  внешние библиотеки уведомлений, реальная почта и серверная поставка не добавляются.

## Decisions

### 1. Автоматический защищённый POST и явная машина состояний

Для `/auth/verify#token=...` извлечь секрет в память, убрать fragment и автоматически
получить CSRF/отправить существующий POST `/api/v1/auth/verify-email`. Серверный GET
страницы остаётся без бизнес-эффектов. В React состояние `checking → success|error`;
проверка запускается один раз на токен за mount, включая StrictMode. Секрет не
сохраняется в localStorage/sessionStorage, SSR, toast или логах.

После успеха убрать verify-форму и submit, удалить секрет из UI-состояния,
показать постоянный результат и ссылку «Войти» с прежним безопасным next.
Не перенаправлять автоматически в кабинет. Обновить auth-состояние/соседние вкладки
существующим механизмом, не подменяя уже открытый аккаунт другого пользователя.
Если пароль был проверен ранее в этом же аккаунте, сохраняется обычная семантика
FULL после подтверждения email; новая сессия не создаётся.

При сетевой ошибке оставить возможность явного «Повторить проверку» в текущем
mount, используя тот же секрет из памяти; автоматического бесконечного retry нет.
Недействительная/истёкшая/заменённая ссылка даёт постоянный нейтральный экран и
путь к новому письму. Без секрета/JS — читаемая инструкция, без ложного успеха.

Альтернатива — подтверждающий GET с токеном в query. Отклонена: GET становится
изменяющим, секрет попадает в URL запросов. Сохранение нынешнего ручного submit
не выполняет требование пользователя.

### 2. Ограниченная идемпотентность только VERIFY

Добавочная миграция identity добавляет nullable `consumed_at` к `auth_tokens`
и индекс/очистку по expiry при необходимости. Для VERIFY сохраняется hash-запись
до исходного expires_at (24 часа от выдачи); plaintext не добавляется.
Под блокировкой аккаунта повторно проверить kind/hash/expiry и отметить consumed
в той же транзакции, что verifiedAt. Первый запрос меняет аккаунт, повтор тем же
действующим токеном возвращает такой же нейтральный успех без повторного события,
письма, сессии или изменения verifiedAt. Два параллельных запроса сериализуются.

Истечение, удаление аккаунта, повторная выдача и отзыв прекращают такой повтор;
TTL не продлевается. Повторная отправка удаляет прежние VERIFY receipts тем же
существующим правилом. Уборщик удаляет expired VERIFY в пределах минуты работы
worker после expiry, включая backlog после restart. RESET сохраняет одноразовое
атомарное потребление и прежний отзыв сессий/attendance grants.

Альтернатива — лишь клиентский useRef. Недостаточна при потере HTTP-ответа и в
двух вкладках. Не хранить бессрочную историю использованных секретов и не считать
любой INVALID_TOKEN успешным только потому, что неизвестный адрес уже verified.

### 3. Общая политика нового пароля и проверяемое совпадение сторон

Решение пользователя: 6–128 символов, минимум одна буква и одна цифра.
Регистрация, новый пароль при reset и создание новых ADMIN/fixtures используют
один backend-валидатор identity; сервисные входы защищены независимо от `@Valid`
контроллера. DTO validation вызывает тот же валидатор, без независимого regexp.
Reset проверяет пароль до потребления токена/изменения хеша, в одной транзакции.

Технические уточнения: длина — Unicode code points, буква — категория L, цифра — Nd;
латиница/кириллица допустимы, спецсимволы/пробелы разрешены и не обязательны.
Значение не trim/normalize/case-fold. JS/Kotlin применяют одинаковые правила и
общую таблицу тестовых векторов, включая supplementary Unicode. Ограничения
нативного input по UTF-16 не должны отвергать корректные 128 code points.
OpenAPI отражает 6/128 и правило состава; frontend-типы генерируются из backend.
Новый endpoint политики для фиксированного правила не нужен.

Frontend helper проверяет обе формы register/reset, показывает правило до ввода,
проверяет при blur/submit и отмечает конкретное поле. Невалидный новый пароль не
отправляется. Для ошибок, возвращённых backend, применяются его fieldErrors.
Порядок причины одинаковый: длина, затем недостающая буква/цифра.

При входе не применять новый состав или минимум 6 к сохранённому паролю:
непустое значение в безопасной верхней границе проверяется против имеющегося
Argon2-хеша. Хеши, аккаунты и passkey не перезаписываются миграцией/seed.

Альтернатива — поменять только HTML minLength. Отклонена: API и service bypass
оставляют разные правила. Не вводить обязательные регистры/спецсимволы сверх решения.

### 4. Каталог сообщений, advice и ошибки Security

`backend/app/src/main/resources/messages.properties` — UTF-8 каталог публичных
ошибок всех текущих API и полевых сообщений, а не файл журналирования исключений.
Spring MessageSource/MessageProvider разрешает известные ключи и безопасные args.
Доменные сервисы передают code/аргументы без готового пользовательского текста;
существующие ResponseStatusException с известным reason-code адаптируются advice.
Типизированные нарушения политики пароля содержат только ключи/причины, не пароль.

Общая фабрика ApiError использует каталог для title/detail/fieldErrors и вызывается
`@RestControllerAdvice`, authenticationEntryPoint и accessDeniedHandler. Фильтровые
401/403/CSRF не «перебрасываются» искусственно в MVC: это отдельные точки входа
в ту же фабрику. Результат остаётся `application/problem+json` со старыми
`type,title,status,code,detail,requestId,fieldErrors`; статусы и Retry-After сохраняются.

Полевой парольный отказ: HTTP 400, `code=VALIDATION_ERROR`, локализованная
`fieldErrors.password` с точной причиной. Общий detail объясняет исправление формы.
Покрыть binding/constraint/malformed/domain/conflict/not-found/429/500 и Security.
Для неизвестного ключа/исключения — безопасный фиксированный fallback и технический
код; ни сырой reason, exception.message, SQL, rejectedValue, email, пароль, токен,
ни чувствительные параметры не возвращаются и не добавляются в диагностические логи.
Внутренний лог сохраняет безопасные code/requestId и класс/место ошибки.

Frontend предпочитает корректный detail/fieldErrors собственного API как текст.
Для старого backend временно остаётся ограниченный legacy code fallback, для
сетевого сбоя/HTML от proxy/невалидного ответа — локальный безопасный текст.
Не передавать произвольный Error.message в toast. Локальные ошибки формы/WebAuthn
получают отдельные известные пользовательские сообщения.

Альтернатива — каталог только для новых auth-ошибок. Отклонена: сохраняется
непредсказуемый UX разных разделов и обход обработчика ошибками Security.
Слепое копирование fallback «вернуть сам код» из референсов не используется.

### 5. Один поток уведомлений, включая native dialog и публичную ссылку

Общий клиентский host уведомлений не зависит от FULL/AuthProvider; он доступен
в кабинетах, auth и ограниченной странице «Приду». SSR не содержит чужих ошибок,
серверное module-level состояние не используется. Новая библиотека не требуется.

По умолчанию показывать одну плашку на неуспешное foreground-действие/загрузку
пользователя. Ответ проходит один нормализатор и диспетчер; catch формы добавляет
fieldErrors/состояние, не второй toast. Dedup — идентичность запроса/ошибки, а не
постоянное подавление одинакового code; новая попытка снова может показать ошибку.
Ожидаемый ANONYMOUS `/auth/me`, фоновые опросы и отменённые/устаревшие запросы
не создают поток плашек. Не обходить generation guards календаря/расписания.

Справа внизу на desktop; на узком экране ширина ограничена viewport/safe-area,
без горизонтального overflow. Предлагаемый timeout — 6 секунд видимого времени,
ручное закрытие, максимум 3 видимых уведомления. Таймер приостанавливается при
hover, keyboard focus и скрытом документе; исчезновение не крадёт фокус.
Есть текстовое объявление screen reader и подписанная кнопка закрытия;
reduced-motion отключает лишнее движение.

Native dialog находится в top layer: один лишь большой z-index body portal не
решает задачу. Host направляет отображение в верхний открытый dialog/его выделенный
контейнер, а без dialog — в body; при смене слоя не дублирует live announcement.
Визуальное и клавиатурное поведение проверить на auth dialog и admin side panel.
Никакой новой focus trap у toast, Tab/Escape/возврат фокуса dialog сохраняются.

Полевые ошибки остаются рядом с input до исправления. Невозможность загрузить
календарь и недействительная ссылка сохраняют понятное состояние страницы и
доступное следующее действие после исчезновения toast. Успех verification —
постоянный результат, а не исчезающее сообщение вместо результата.

## Risks / Trade-offs

- JS-сканер письма может автоматически подтвердить email → согласованное изменение;
  не выдавать аккаунтную сессию или доступ по самой ссылке, не менять RESET/«Приду».
- Новый смысл повтора VERIFY расходится с исторической «одноразовой ссылкой» →
  повторяет только результат в исходном TTL, не создаёт нового действия; явная дельта.
- Несовпадение Unicode/DTO/HTML правил → общие векторы границ и сгенерированная схема.
- Toast в невидимом слое/под экранной клавиатурой → проверки dialog, safe-area,
  размеров и фокуса; постоянная полевая подсказка не зависит от плашки.
- Дубли из middleware/catch или фоновый шум → единый владелец показа и request scope.
- Утечка через exception args/detail → allowlist кодов/аргументов, текстовый render
  и негативные проверки SQL/HTML/rejectedValue/секретов на всех точках обработки.

## Migration Plan

1. Реализация по новому поручению: применить Kotlin/React skills, зафиксировать
   чужие изменения и исходные аккаунты/данные. Этот этап только планирует.
2. Добавочная миграция VERIFY receipt без изменения хешей/паролей/ролей/ключей;
   старые действующие токены обрабатываются, RESET не меняет срок/одноразовость.
3. Новый backend поддерживает предыдущий frontend: ручной POST verify работает,
   старые поля/коды API сохраняются. Экспорт OpenAPI → генерация → новый frontend.
4. Локально проверить старый frontend с новым backend, целевые auth/toast сценарии,
   регрессию календаря/переносов/ограниченной ссылки и backup/миграцию.
5. Возможная будущая серверная поставка — отдельное поручение, backup и backend
   перед frontend. Никакой смены семи существующих паролей или повторного seed.
   Откат frontend возвращает старую ручную кнопку; откат backend не требует удаления
   nullable колонки, но возвращает старые правила новых паролей и повтора verification.
   Не восстанавливать backup поверх принятых пользовательских изменений.


## Implementation Notes — 23.10.2026

Локальная реализация и доказательства описаны в
`docs/auth-verification-and-error-feedback.md`. Состояние не означает серверную поставку.
Использована V9 с `auth_tokens.consumed_at` и индексом expired VERIFY; повтор
сохраняет исходные timestamps. Frontend обрабатывает также hashchange той же
страницы, чтобы открытие другого письма не показывало прежний результат.
Один постоянный DOM-контейнер переносится в dialog/body без пересоздания плашек
и таймеров. Показ принадлежит актуальному UI catch, без автоматического показа
в transport middleware. Стандартная генерация OpenAPI/TypeScript сохранена.
Фактический backend rollback на V9 не заявляется проверенным; перед возможной
поставкой нужен отдельный gate. Локальные тестовые процессы/сервисы остановлены,
пользовательский сервер и туннель не изменялись.
