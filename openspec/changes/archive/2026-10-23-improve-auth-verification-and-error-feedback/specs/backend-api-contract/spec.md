## Purpose

Предоставлять всем клиентам стабильные безопасные ошибки API с единым каталогом
пользовательских сообщений, точной валидацией полей и совместимостью независимых поставок.

## ADDED Requirements

### Requirement: Единый каталог публичных ошибок backend
Публичные тексты ошибок и валидации всех текущих API SHALL централизованно храниться
в UTF-8 `messages.properties` и разрешаться по известному коду и безопасным аргументам.
Обработка исключений SHALL возвращать согласованный текст каталога; ошибки доступа,
аутентификации и CSRF SHALL следовать тому же контракту до входа в контроллер.
Файл properties SHALL быть каталогом сообщений, а не хранилищем произошедших ошибок.

#### Scenario: Бизнес-ошибка с аргументом
- **WHEN** операция возвращает известный доменный код и разрешённые параметры сообщения
- **THEN** API сохраняет код/HTTP-статус и отдаёт понятный русский текст из каталога, который frontend показывает без собственного перевода этого кода

#### Scenario: Отказ до контроллера
- **WHEN** запрос не имеет нужного входа, прав или CSRF
- **THEN** 401/403 возвращаются в том же формате с сообщением из того же каталога, а защита операции не ослабляется

### Requirement: Совместимый формат и точные ошибки полей
Ответ SHALL сохранять `application/problem+json` и поля
`type,title,status,code,detail,requestId,fieldErrors`. HTTP-статусы и семантика
существующих стабильных кодов SHALL сохраняться, включая 429 и Retry-After.
Полевой отказ SHALL содержать понятную конкретную причину в fieldErrors;
новый невалидный пароль SHALL давать 400/VALIDATION_ERROR и fieldErrors.password.
OpenAPI SHALL отражать новые правила входных данных, frontend SHALL использовать
сгенерированные transport types без ручного параллельного DTO.

#### Scenario: Неверный состав пароля
- **WHEN** новый пароль достаточной длины содержит только буквы
- **THEN** fieldErrors.password объясняет необходимость цифры, а общий detail не подменяет точную ошибку поля универсальной фразой

#### Scenario: Неправильный JSON или параметр
- **WHEN** запрос не проходит binding/constraint либо содержит неправильный JSON
- **THEN** API возвращает безопасный каталогизированный 400 вместо стека/HTML и сохраняет requestId

#### Scenario: Прежний frontend и ограничение частоты
- **WHEN** прежний frontend вызывает совместимую операцию либо запрос превышает лимит
- **THEN** прежние поля/коды остаются понятны клиенту, 429 и период ожидания сохраняются без потребления токена или блокировки аккаунта

### Requirement: Безопасное неизвестное исключение и неполный каталог
Неизвестное исключение/код/отсутствующий ключ SHALL давать фиксированный безопасный
fallback. Ответы и штатные журналы SHALL не содержать произвольных exception.message,
SQL, stack trace в HTTP, rejectedValue пароля, секретов ссылок, cookies или тел запросов.
Все известные публичные коды SHALL иметь проверяемое покрытие каталогом.

#### Scenario: Ошибка содержит чувствительное значение
- **WHEN** внутреннее исключение содержит пароль, токен, SQL или HTML
- **THEN** клиент получает безопасное сообщение и requestId без исходного значения, а чувствительный текст не попадает в журнал

#### Scenario: Ключ отсутствует
- **WHEN** разрешить переданный код через каталог невозможно
- **THEN** пользователь получает читаемый fallback вместо самого неизвестного кода или текста исключения
