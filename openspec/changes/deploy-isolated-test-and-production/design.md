## Context

Сервер Ubuntu 24.04 имеет 1 vCPU и 2 ГиБ RAM после увеличения тарифа; ресурсы двух копий frontend, JVM backend и PostgreSQL необходимо проверить. Существующий preview использует `/lastochka` и отдельный origin WebAuthn; его нельзя считать автоматически совместимым с новыми доменами. Старый тестовый стенд и активный OpenSpec по Альфа-Банку сохраняются.

## Goals / Non-Goals

**Goals:** Два независимых окружения, проверяемый доступ, выпуск по отмашке, восстановление и контролируемое переключение.

**Non-Goals:** Включение боевого эквайринга, импорт старых данных в production, отключение SSH root, удаление старого стенда или обещание отказоустойчивости одного VPS.

## Decisions

- Отдельные Compose projects, volumes, сети, конфигурации и БД; общий Nginx с отдельными HTTPS virtual hosts. Внутренние порты не публикуются наружу. Отдельные поддомены и cookie scopes, настройки origin/RP WebAuthn для каждой зоны; ранее зарегистрированные ключи не переносятся.
- Чистая инициализация production и test без переноса старых данных. Штатный bootstrap `kines`; секрет из указанного локального файла передаётся защищённым каналом без аргументов, журнала и Git. Проверить политику пароля до работы; не сохранять сам пароль в артефактах и не сбрасывать учётку при повторе. Пароль SSH и приложения совпадает по явному запросу пользователя; предусмотреть отдельную последующую замену без самовольного изменения.
- Защита production: обычная роль агента только читает БД, runtime приложения имеет необходимые DML-права, а миграции используют отдельную контролируемую роль без доступа из обычного агентского процесса. Скрипты проверяют независимые идентификаторы хоста и БД, явно выбирают окружение и отказывают по умолчанию; destructive SQL, операции с volume и restore поверх production требуют отдельного плана, проверенного восстановления и согласия пользователя. Секреты привилегированных ролей не доступны обычной роли агента. Хранить версионированные копии на сервере под отдельными правами без удаления агентом; проверять восстановление на отдельной базе. Root и доступ к контейнерному движку позволяют обойти защиту, поэтому выделить ограниченную учётную запись и не выдавать ей root/docker; существующий root остаётся отдельным аварийным доступом.
- Текущий backend автоматически запускает Flyway при старте через основной datasource; перед production-поставкой разделить этот путь: runtime и bootstrap с ограниченной ролью без автоматических миграций, отдельный миграционный запуск с привилегированной ролью и проверкой цели. Проверить отсутствие DDL и запуска миграций при перезапуске или случайном test bootstrap, а также способность штатных операций работать с DML-ролью.
- Ежедневно ночью создавать сжатые копии в отдельном каталоге сервера; учётный лимит 5 ГиБ распространяется на копии БД. Сначала создать и проверить новую копию, затем удалять старые по возрасту; при нехватке места или ошибке не удалять последнюю пригодную копию и сообщить об ошибке. Ключи — в отдельном защищённом каталоге, без разрушения копий ключей, нужных для сохранённых backup.
- Две независимые случайные 32-байтные Alfa key files в закрытых каталогах вне образов и БД; отдельная защищённая копия ключей на этом же сервере и привязка к соответствующему backup. Интеграции и уведомления по умолчанию выключены, production не подключать к тестовому банку автоматически.
- Заглушка — публичная минимальная страница и логотип; последовательность из трёх нажатий открывает отдельный серверный password gate. Nginx или выделенный проверяющий компонент принудительно защищает все application routes, API и SSR, включая прямые ссылки, до доступа к upstream; доступны только явно перечисленные ресурсы заглушки и endpoint входа. Вход защищён CSRF, rate limit, безопасными HttpOnly/Secure/SameSite cookie с ограниченным сроком и выходом; пароль отдельно от `kines`, хранится хешированным. Keyboard/touch и доступность сохраняются. Тройной клик не является секретом. Определить безопасный доступ к test отдельным credential, не добавляя API-обходы.
- Использовать неизменяемые версии/дижесты образов и выпускать на prod те же артефакты после отмашки. Перед миграцией — совместимость и проверенный restore; откат образа не откатывает схему и бизнес-данные автоматически. Сборка вне VPS.
- Пользователь увеличил память до 2 ГиБ при 1 vCPU: провести бюджет памяти, диска и CPU, максимально ограничить test и рассмотреть запуск test по требованию при недостатке ресурсов. До поставки измерить реальные сценарии, обновление и восстановление; при недостаточности не объявлять такую конфигурацию работоспособной и не рисковать рабочими данными.

## Risks / Trade-offs

- [Общий VPS] → раздельные среды и локальные backup не защищают от потери сервера, исчерпания ресурсов и компрометации хоста; пользователь выбрал локальные копии, требуются мониторинг и явная фиксация этого ограничения.
- [Общий пароль SSH и приложения] → компрометация одного открывает другой; пользователь явно запросил совпадение, ограничить доступ к файлу и предложить последующую замену.
- [Доступ и callbacks] → gate должен перекрывать прямые пути, включая API; банковские callbacks не открывать по умолчанию. Переход к реальному банку требует отдельного дизайна.
- [Новая схема и DNS] → новые passkeys надо регистрировать заново; сертификаты, DNS и внешние интеграции проверяются до переключения.

## Migration Plan

Проверить ресурсы и финансирование вне планирования; собрать образы локально; подготовить зоны и ключи; инициализировать базы; проверить HTTPS, isolation и gate, авторизованные сценарии и восстановление копий; затем по разрешению пользователя переключить DNS. Старый стенд сохранить до принятия. Возврат DNS и предыдущих образов описать с TTL и ограничениями схемы; старую БД не накатывать поверх новых рабочих данных.
