## Context

- Форма `/enquiry` построена как серверная форма React Router: каждое действие подбора
  (`change`, недели, страницы, `choose|…`, `choose-rule|…`) отправляет POST, и после ответа
  страница оказывается в начале. На test 13.11.2026 выбор технически сохранялся
  (`picking`/`desiredSessionId` менялись), но блок подбора высотой около 1400 px и
  прокрутка к началу делают его неработающим для посетителя.
- Справочник направлений (`age_directions`, V25) публично отдаётся
  `GET /api/v1/public/age-directions`; афиша сопоставляет занятие с направлением функцией
  `directionFor` (`frontend/app/ui/schedule-poster-rows.ts`): точное совпадение границ,
  затем первое пересечение. Публичная выборка расписания идентификатор направления не отдаёт.
- Контракт заявки версионирован полем `contractVersion` (сейчас 2: тип участника и возраст).
  В `develop` последняя миграция — V28 (Java-миграция Альфа-интеграции), test уже на V28.
- Уведомления: `enquiry_notification_settings` на test — Telegram включён, push выключен;
  `telegram_outbox`, `browser_push_outbox` и `enrollment_requests` пусты. Наличие токена
  бота, чата и VAPID на test агенту под `lastochka-agent` не видно.

## Goals / Non-Goals

**Goals:**
- Короткая форма: имя, телефон, категория, необязательные имя занимающегося, занятие, комментарий.
- Выбор занятия без перезагрузки при JS и с сохранением позиции без JS.
- Обратная совместимость: старый frontend и ранее открытые формы (контракт 2) работают
  с новым backend; прежние заявки читаются без изменений.
- Доказанная доставка новой заявки в Telegram и push на test.

**Non-Goals:**
- Удаление столбцов `participant_type`/`participant_age`/`child_*` и прежнего контракта.
- Изменение справочника направлений, афиши или правил расписания.
- Новые каналы уведомлений, редактор шаблонов сообщений, кнопка «проверочное уведомление».
- Выпуск в production (только по отдельной отмашке).

## Decisions

1. **Контракт версии 3.** `EnquiryInput` получает `ageDirectionId` (UUID) и
   `participantName` (необязательно, ≤100). Для `contractVersion = 3` категория обязательна,
   `participantType`/`participantAge`/`childAge` должны отсутствовать; версия 2 проверяется
   прежними правилами без категории. Альтернатива — сделать категорию необязательной в
   версии 2: отвергнуто, т.к. не обеспечивает обязательность и смешивает семантику.
   Имя занимающегося хранится в отдельном `participant_name`, а не в `child_name`, чтобы
   взрослый из категории 14+ не помечался «ребёнком».
2. **Снимок категории в заявке (V29, аддитивно).** Столбцы `enrollment_requests`:
   `age_direction_id uuid NULL REFERENCES age_directions(id)` (без каскада),
   `age_direction_title varchar(100)`, `age_direction_from int`, `age_direction_to int`,
   `age_direction_open_ended boolean`, `participant_name varchar(100)` — все NULL для прежних
   строк, CHECK согласованности границ при наличии снимка. Снимок нужен, потому что
   справочник редактируется и архивируется (требование age-directions). Альтернатива —
   хранить только FK: отвергнуто, текст заявки изменился бы молча.
3. **Проверка категории в backend.** Сервис `enquiries` читает активное направление через
   публичный контракт владельца справочника (`scheduling`), не через его repo/entity; в той
   же транзакции, что и сохранение заявки. Архивное/неизвестное → 400 с ошибкой поля
   `ageDirectionId` из `messages.properties`. Idempotency-хеш включает категорию и имя.
4. **Список занятий в форме — данные с сервера, фильтр на клиенте.** Loader отдаёт
   активные направления и ближайшие доступные занятия на 14 дней вперёд (тот же
   `selectable=true`, постранично до исчерпания, с верхним пределом), каждое с вычисленным
   `directionId` через общий `directionFor`. Блок — `<details>`; внутри радиокнопки
   `desiredChoice` со значением `choiceValue(entry)`. Видимость по категории: CSS `:has()`
   от выбранной радиокнопки категории плюс JS-фильтр как запасной путь; показ «ещё» —
   локально (первые 5, затем по 5). Так выбор не делает POST и не сбрасывает прокрутку.
   Без JS показывается весь список категории за 14 дней (ограничение «Показать ещё»
   включается только после гидратации), а выбор — обычная радиокнопка формы, поэтому
   серверный шаг подбора не нужен.
   Альтернативы: `fetcher` с отдельным ресурсным маршрутом (больше кода, всё равно нужен
   no-JS путь); оставить недели и страницы (именно они перегружают форму).
5. **Разрешение выбора при отправке.** `desiredChoice` разбирается на сервере в
   `desiredSessionId/Version` или `calculatedSession`; прежняя проверка ревизии и 409
   сохраняются. Если выбранное занятие не относится к выбранной категории, action снимает
   его с пояснением, а не отправляет противоречивую заявку.
6. **Предвыбор.** `?session=`/`?series=&date=&revision=` — как раньше, категория
   вычисляется `directionFor`; новый `?direction=<id>` — только категория. Его получают
   ссылки «Оставить заявку» в строках возрастных категорий афиши. Форматы главной
   (мини-группа, индивидуально, первое занятие) с возрастом не связаны и ведут на `/enquiry`.
7. **Telegram.** Новый шаблон `enquiry.telegram-category` в `user-messages.properties`:
   номер, время, заявитель, телефон, категория, занимающийся (если указан), занятие,
   комментарий. Прежние шаблоны `-child`/`-self` для заявок контракта 2 остаются.
   Push-текст не меняется (без персональных данных).
8. **Приёмка уведомлений — проверка, а не новая функция.** Порядок: через операторский
   доступ сверить наличие токена/чата бота и VAPID в env test (без вывода значений); при
   отсутствии запросить у пользователя бота и чат. ADMIN включает оба канала в настройках,
   подключает push на своём устройстве; агент отправляет одну синтетическую заявку
   «Проверка уведомлений» с тестовым номером, затем read-only сверяет `telegram_outbox`/
   `browser_push_outbox` = доставлено, пользователь подтверждает получение в чате и на
   устройстве. Найденные дефекты исправляются здесь же.

## Risks / Trade-offs

- [CSS `:has()` не поддерживается старым браузером] → JS-фильтр; без JS и без `:has()`
  показываются все занятия с подписью категории — выбор остаётся корректным, сервер
  снимает несоответствующий выбор с пояснением.
- [Занятие с нестандартным возрастом не попадает ни в одну категорию] → такие занятия
  в форме не предлагаются (как строка «без направления» в афише); общая заявка доступна.
- [Старый frontend после выпуска backend] → контракт 2 принимается; frontend выпускается
  после backend. Обратный порядок (новый frontend на старом backend) не поддерживается.
- [Откат backend после появления заявок v3] → прежний backend читает строки (новые столбцы
  NULL-допустимы и им не нужны), но не покажет категорию; откат frontend возможен отдельно.
- [Синтетическая заявка остаётся в БД test] → агент имеет только чтение; заявка явно
  помечена комментарием «Проверка уведомлений», без реальных контактов. Удаление — только
  по решению пользователя.
- [Секреты бота] → значения не выводятся в журнал/отчёт, проверяется только наличие.

## Migration Plan

1. Backend: V29 + контракт 3 (принимает 2 и 3). Перед выпуском на test — копия БД test
   и проверка V28→V29 на отдельной локальной восстановленной копии.
2. Выпуск backend на test, проверка старой формы (контракт 2) против нового backend.
3. Выпуск frontend на test, проверка новой формы desktop/mobile, Chromium/WebKit, без JS,
   прежние ресурсы доступны; TLS 1.2 без 1.3 сохранён.
4. Приёмка уведомлений (решение 8).
5. Откат: frontend на предыдущий образ отдельно; backend — на 0.22.x допустим, т.к. V29
   аддитивна (новые заявки потеряют показ категории, но не данные).
6. Production — только по новой отмашке пользователя.
